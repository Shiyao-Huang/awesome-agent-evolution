# 第3章：方法分类

> 撰写时间戳：2026-05-21T19:05:06+08:00  
> 素材来源：`raw-papers/`、`paper-reviews/`、`research/` 中截至 2026-05-21 已收集的 Agent Self-Evolution / Agent Evolution 论文、深度 review 与研究索引。

## 3.0 本章概述

Agent Evolution 方法众多，名称也不统一。为了避免把论文按年份或应用领域简单堆叠，本章按“主要选择压力与主要可变对象”进行分类：基于奖励的进化主要优化策略或行为分布；自博弈进化主要生成任务、对手和验证信号；提示词进化主要改变上下文、反思、原则和输出修订流程；架构搜索主要改变代码、工具、控制流和多智能体拓扑；基于记忆的进化主要改变长期经验、技能库和检索策略；混合方法则把多种机制组合成端到端闭环。每一类方法都可以用第2章的统一形式化描述，但它们在数据需求、评估可靠性、成本、安全风险和可迁移性上差异很大。

## 3.1 基于奖励的进化

基于奖励的进化是最接近传统强化学习和后训练的一类方法。它的核心思想是：把智能体交互轨迹、推理过程或输出结果映射为标量或偏好信号，再通过策略优化、偏好学习、筛选微调或 archive selection 使后续行为更可能获得高奖励。STaR 是早期代表。它让模型先基于少量 rationale examples 对大量问题生成推理链，筛选正确答案对应的推理，再用这些推理微调模型；对错误样本还可用正确答案进行 rationalization，从而扩大可训练数据。STaR 的重要性在于，它把“模型自己生成可学习材料”组织成闭环：生成、验证、训练、再生成。虽然它主要作用于推理链和模型权重，还不是完整 agent，但其 bootstrapping 逻辑成为后续自演化研究的基础模板。

Self-Rewarding Language Models 把奖励信号进一步内生化。系统让同一个模型既生成候选回答，又作为 judge 评价候选，并用 Iterative DPO 进行多轮偏好优化。这样做的动机是减少对人类偏好数据的依赖，同时让模型的指令遵循能力和奖励建模能力共同提升。Meta-Rewarding 进一步区分 actor、judge 和 meta-judge，让模型不仅评价回答，还评价评价本身。这类工作展示了自奖励的吸引力：数据生成速度快，任务覆盖面广，训练信号与模型自身偏好一致。但它们也暴露出典型风险：judge 偏差会被放大，模型可能学会迎合自身评分规则，且缺乏真正独立的外部验证时，奖励质量提升不一定等于真实任务能力提升。

IterAlign 代表另一条奖励/偏好进化路径：使用宪法原则或规则集合构造迭代对齐过程。与 Self-Rewarding 依赖模型自评不同，IterAlign 强调原则驱动的反馈，使模型在多轮迭代中向预设价值约束靠拢。它说明 Agent Evolution 不只追求能力增长，也可以追求规范一致性。对于未来部署型 agent，奖励函数往往需要同时编码任务成功、用户偏好、合规要求和安全边界；只优化任务分数会诱导策略捷径，只优化安全则可能牺牲实用性。因此，多目标 reward shaping 是基于奖励方法的核心难点。

RISE、Agent-R 和 RAGEN 更接近 agent 轨迹层面的训练。RISE 将单轮问题改写为多轮 MDP，让模型学习在测试时递归自省和修正；其关键是把“再想一轮”从 prompt trick 变成可训练策略。Agent-R 关注多轮交互中从错误恢复的问题，使用 MCTS 构造从错误轨迹回到正确轨迹的训练数据，并用模型引导的 critique 强化反思能力。RAGEN 则提出 StarPO，把 state、thinking、actions、reward 联合建模为轨迹级强化学习框架，系统研究 LLM agent 在多轮随机环境中训练时的稳定性，并识别 Echo Trap 等现象。它们共同推动基于奖励的方法从静态 answer reward 走向完整 trajectory reward。

在代码和软件工程场景中，奖励通常来自可执行测试。SICA 使用 SWE-Bench Verified 等基准验证自修改 coding agent 的改进，DGM 使用 SWE-Bench 和 Polyglot 评估 agent 代码变体，AlphaEvolve 使用程序化 evaluator 判断算法候选是否提升性能。可执行奖励的优势是客观、可复现、可自动化；缺点是覆盖面有限。测试通过并不等于代码优雅、安全或可维护；算法 benchmark 速度提升也可能牺牲可读性和鲁棒性。基于奖励的进化最需要“评估器不可篡改”和“隐藏测试集”两道防线，否则 agent 可能通过修改测试、利用环境漏洞或生成不可泛化补丁获得虚假高分。

基于奖励的方法通常适用于三类场景。第一是答案可验证的推理任务，如数学、代码、逻辑和结构化问答；第二是环境可给出明确 reward 的交互任务，如游戏、网页自动化和 API 操作；第三是偏好可由 judge 或人类比较表达的开放文本任务。它们的共同优势是闭环清晰：reward 提供选择压力，优化器提供更新方向，分数曲线提供评估证据。共同局限是 Goodhart 风险、样本效率、奖励稀疏、泛化不确定和训练成本。一个成熟系统必须报告 validation/test 隔离、reward 来源、训练轮数、失败样本、成本、方差和消融，否则很难判断提升来自真正自演化还是来自 benchmark 调参。

## 3.2 自博弈进化

自博弈进化把“数据从哪里来”这个问题推到系统内部。传统训练依赖人工数据或固定任务集；自博弈方法让模型自己生成任务、对手、论证、挑战或游戏局面，再从解决这些自生成问题的过程中学习。Self-Play Fine-Tuning 探索用模型与自身对抗来提升弱模型；SPIRAL 让语言模型在多轮零和游戏中自我博弈，发现可迁移的推理能力；Absolute Zero 提出在零外部数据条件下，由同一个模型提出最大化自身学习进度的任务并尝试解决，用代码执行器提供验证。它们的共同目标是突破“人类题库有限”的瓶颈。

Absolute Zero 是自博弈进化的典型案例。系统中的模型不仅是 solver，也是 proposer。Proposer 生成具有学习价值的任务，Solver 尝试求解，执行器或验证器给出结果，强化学习更新模型。这里的关键不是让模型随意出题，而是让任务生成与学习进度挂钩：太简单的任务没有训练价值，太难的任务无法提供有效反馈，只有位于能力边界附近的任务最有用。这与开放式进化中的 stepping stone 思想一致。自博弈的价值在于自动发现课程，而不是重复已有数据。

SPIRAL 和多智能体自博弈方法强调对抗结构。零和游戏天然提供清晰胜负信号，且对手强度随自身提升而提升，因此能形成持续选择压力。语言模型在博弈中需要计划、欺骗识别、反事实推理和策略调整，这些能力可能迁移到数学和通用推理任务。多智能体辩论虽然不总被称为自博弈，但也具有类似结构：多个模型实例提出不同答案并相互质询，最终答案由辩论过程筛选。Multi-Agent Debate 证明，多实例竞争可以提升事实性和推理质量；MAE、ASL 等后续工作则把 proposer、solver、judge 等角色制度化，并尝试用 RL 优化整个闭环。

自博弈方法的核心优势是可扩展数据生成和自动课程。只要验证器可靠，系统就能不断提出新任务并学习。它特别适合代码、数学、逻辑、游戏和可程序化环境，因为这些场景可以自动判定成功与否。Self-Challenging agents 使用 Code-as-Task 格式生成可验证任务，再通过评估反馈训练；这种设计避免了纯文本自评的主观性。对于网页、机器人和企业流程，自博弈也可以通过模拟环境、世界模型或数字孪生生成挑战，但验证器设计更困难。

自博弈的风险同样明显。第一，任务生成器可能塌缩到狭窄分布，导致系统只擅长自己会出的题。第二，solver 与 judge 如果同源，可能形成互相迎合的闭环。第三，自生成任务可能偏离真实用户需求。第四，对抗环境可能诱导欺骗、操纵 judge 或利用规则漏洞。第五，学习进度奖励难以稳定估计，可能导致课程震荡。RAGEN 中的 Echo Trap 现象提醒我们，多轮 RL agent 很容易在自身生成的状态—思考—动作模式中重复错误。因此，自博弈系统需要多样性约束、外部 holdout、任务难度校准、跨域迁移评估和人工抽检。

从方法设计看，自博弈进化至少有三种形态。第一是同体自博弈：一个模型扮演 proposer、solver、judge 或通过不同 prompt 分身扮演多角色。优点是成本低，缺点是偏差共享。第二是异体自博弈：不同模型、不同 checkpoint 或不同 agent 变体相互竞争。优点是多样性更强，缺点是系统复杂。第三是环境自博弈：agent 与由世界模型或程序生成器产生的环境对抗，例如 web tasks、游戏关卡、代码测试或数学问题。未来更强的自演化系统可能把三者结合：用 archive 中不同代际 agent 生成任务，用外部验证器评分，用人类或隐藏 benchmark 校准方向。

## 3.3 提示词进化

提示词进化是最轻量、最容易部署的一类 Agent Evolution。它不要求修改模型权重，也不一定要求修改代码，而是通过自反馈、反思、上下文重组、原则抽取和 prompt/program refinement 改变模型调用时的行为条件。Self-Refine 是基础模式：模型生成初稿，模型给出反馈，再根据反馈迭代修订。这个循环适用于写作、代码、问答、推理、对话等多类任务，优势是无需训练数据和额外模型；局限是每个样本内部改进较强，跨任务长期学习较弱。若反馈不被保存，系统下一次仍从零开始。

Reflexion 把提示词进化推进到跨 episode 学习。它将 actor、evaluator 和 self-reflection 分开：actor 执行任务，evaluator 判断成功与失败，self-reflection 模型把失败压缩成自然语言经验，并存入情景记忆。下一次尝试时，actor 在上下文中读取这些反思。这里的“进化”发生在 memory-conditioned prompt 上：底层模型不变，但策略因记忆而改变。Reflexion 的贡献是把稀疏 reward 转化为“语义梯度”。相比仅告诉模型失败，反思文本能指出失败原因和改进方向。它的限制也很清楚：记忆窗口小，反思质量不稳定，缺乏收敛保证，错误反思可能持续误导后续尝试。

ExpeL、ICE、ACE 和 EvolveR 代表提示词进化的长期化趋势。ExpeL 从训练任务中自主收集经验，抽取自然语言 insights，并在测试时回忆；ICE 通过 Investigate-Consolidate-Exploit 把任务间轨迹整合为简化工作流，从而减少 API 调用并提升执行；ACE 把上下文工程定义为可演化 playbook，使用结构化增量更新避免上下文坍缩；EvolveR 把离线自蒸馏、在线交互和策略演化组织成经验驱动生命周期。这些工作说明，提示词不再只是一次性手写 instruction，而可以成为动态知识库和策略库。

提示词进化也包括 prompt optimization 和 textual backpropagation。符号学习方法把 agent 看作符号网络，提示、工具及其组合是可学习权重，通过自然语言模拟反向传播和梯度下降；EvoMAC 与 Agentic Neural Networks 把多智能体网络中的节点和边视为可更新单元，用文本反馈调整协作结构。与梯度下降不同，文本梯度没有严格数学可微性，但它具有可解释性：更新原因、失败类型和修改建议可以被人读懂。这使 prompt evolution 特别适合需要审计的 agent 系统。

提示词进化的优势有四点。第一，部署成本低，适用于黑盒 API 模型。第二，更新可读、可回滚、可人工审查。第三，能快速吸收领域经验和用户偏好。第四，与记忆、工具和评估器天然兼容。其局限也不可忽视。提示词长度受上下文窗口限制；长上下文可能引入噪声和冲突；模型可能忽视旧原则或过度遵守错误规则；提示词更新容易被当前任务过拟合；缺乏独立评估时，自我反思可能只是解释性幻觉。因此，ACE 强调结构化上下文维护，ReasoningBank 强调策略级蒸馏而不是原始轨迹堆积，这些都是对提示词进化局限的回应。

在工程实践中，提示词进化适合用作安全的第一层自改进。系统可以先冻结模型和代码，只允许更新可审查的 playbook、few-shot examples、failure notes、tool-use rules 和 retrieval policies；每次更新都经过单变量 ablation 和回归测试；若收益稳定，再考虑更深层的代码或权重更新。这样的分层策略比直接让 agent 修改自身代码更安全，也更容易定位改进来源。

## 3.4 架构搜索

架构搜索关注的问题是：agent 的结构本身能否自动设计和改进。传统 agent 系统往往由人类手工选择 ReAct、planner-executor、reflection、debate、toolformer、multi-agent role 等模式；架构搜索则把这些模式编码为可变对象，让系统在反馈中寻找更优组合。ADAS 是这一方向的代表。它提出 Automated Design of Agentic Systems，让 meta agent 用 Python 编写新 agent architecture，在任务上评估后把有效设计加入 archive。由于 Python 是图灵完备的，搜索空间理论上包含任意 agent 控制流、工具调用、子代理组织和自检逻辑。

ADAS 的重要启示有三点。第一，agent design 可以像 neural architecture search 一样被自动搜索，但搜索空间更加语义化和程序化。第二，LLM 生成的代码不仅是候选答案，也可以是候选智能体。第三，发现的结构具有可解释性，人类可以检查代码并总结设计模式。例如 meta agent 可能发现多视角推理、自我辩论、迭代精炼或工具验证等模式。与纯 prompt 优化相比，代码化 agent design 可以表达循环、条件、状态、缓存、工具编排和复杂控制流，因此能力上限更高。

Gödel Agent、SICA 和 DGM 把架构搜索推向自我指涉。Gödel Agent 允许 agent 动态修改自身行为逻辑；SICA 让 coding agent 消除 meta-agent 与 target-agent 的区分，直接编辑自己的代码库以提升 SWE-Bench Verified 表现；DGM 让每一代 coding agent 都可能产生自身修改版本，并通过 archive 保存多样化谱系。它们与 ADAS 的差异在于：ADAS 由固定 meta agent 设计其他 agent，而 DGM/SICA 让被改进对象参与改进自身。这个内生优化器结构使能力增长有可能递归放大，但也显著提高安全和可复现要求。

EvoMAC、Agentic Neural Networks 和符号学习方法则把架构搜索扩展到多智能体网络。多智能体系统不仅有单个 agent 的内部 prompt，还有角色分配、通信边、协作顺序、critic 位置、投票机制和任务分解方式。EvoMAC 使用文本反向传播更新多智能体协作网络，用 rSDE-Bench 和 HumanEval 验证软件开发任务上的效果。它说明“协作拓扑”本身是可学习对象。相比单 agent 自改进，多 agent 架构搜索能利用角色多样性和互相纠错，但也面临通信成本、协调失败和错误共振。

AlphaEvolve 和 FunSearch 展示了架构搜索在算法发现中的另一种形态。它们不一定改进 agent 自身，而是使用 LLM 与进化框架搜索程序或算法。AlphaEvolve 通过 LLM 生成代码变体、程序化 evaluator 评分、迭代选择与改写，在矩阵乘法、数据中心调度、硬件设计和训练效率优化中发现高价值候选。其经验对 Agent Evolution 很关键：只要候选空间可以表示为代码，评估函数可以自动执行，LLM+evolution 就能成为强大的发现系统。将这一逻辑回套到 agent 本身，就得到 DGM 这样的自改进 coding agent。

架构搜索的优势是表达力强。它可以改变工具流程、引入新模块、重写错误处理、增加审查机制、优化上下文管理、实现缓存和并行、设计多 agent protocol。它的局限也同样强。第一，搜索空间巨大，评估成本高。第二，代码变体可能有副作用，必须沙箱运行。第三，性能提升可能来自 benchmark-specific hacks。第四，archive 管理和谱系追踪复杂。第五，可修改代码越多，越需要不可修改的评估器、权限边界和回滚机制。DGM 论文中关于沙箱、评估成本和冻结基础模型的限制，正是架构搜索自演化必须面对的现实边界。

实际应用中，架构搜索应采用“外圈强评估、内圈可解释变异”的原则。外圈评估器必须独立于 agent，可重复执行，并包含隐藏测试、安全扫描和成本约束；内圈变异应以小 diff、清晰 changelog 和单变量 ablation 为主，避免一次性大规模重构。每个候选 agent 应记录父代、修改摘要、触发原因、评估分数、失败样本和回滚路径。只有这样，架构搜索才能从炫目的自动改代码 demo 变成可靠的软件工程过程。

## 3.5 基于记忆的进化

基于记忆的进化把“经验如何长期保留并影响未来行为”作为核心。与奖励训练不同，记忆方法通常不修改模型权重；与提示词进化不同，记忆更强调跨任务、跨时间、跨环境的长期积累和检索。Generative Agents 展示了经验记录、反思和计划检索如何让多个模拟智能体产生可信社会行为；Voyager 在 Minecraft 中维护可执行技能库，让 agent 通过自动课程探索世界、通过迭代提示生成技能、通过自验证把有效代码保存下来。Voyager 的技能库是记忆型进化的经典例子：经验不是文本日志，而是可执行、可组合、可迁移的行为模块。

Reflexion 和 ExpeL 也属于广义记忆方法。Reflexion 保存失败反思，ExpeL 保存任务经验抽取出的 insights。二者区别在于粒度：Reflexion 更接近 episode-level failure note，ExpeL 更接近跨任务 general lesson。ICE 进一步将轨迹调查后整合为工作流，减少未来执行成本。EvolveR 则把经验生命周期分为离线自蒸馏、在线检索和策略演化。可以看到，记忆型进化的关键不是“存得越多越好”，而是“把轨迹压缩成未来可用的形式”。未经整理的日志会淹没上下文，错误经验会污染决策，重复经验会增加成本。

ReasoningBank、Memory-R1 和 AriadneMem 代表 2025—2026 年记忆研究的深化。ReasoningBank 强调从成功和失败经验中蒸馏 generalizable reasoning strategies，而不是简单保存原始轨迹；测试时根据新任务检索策略，辅助 agent 推理。Memory-R1 关注 agent 如何管理和利用记忆，用强化学习训练何时写入、更新、删除和读取记忆。AriadneMem 面向终身记忆中的两个难题：分散证据的多跳连接和状态随时间更新。它们共同说明，记忆系统本身也需要学习策略；“记忆”不是被动数据库，而是 agent 的可演化认知结构。

基于记忆的进化有几类常见记忆对象。第一是情景记忆，即某次任务的轨迹、失败、观察和反思。第二是语义记忆，即从多个事件中抽取出的规则、原则和概念。第三是程序性记忆，即技能、工具脚本、代码片段和工作流。第四是世界模型记忆，即环境状态、网页结构、用户偏好、软件版本和因果假设。第五是社会记忆，即多 agent 协作中的角色信誉、沟通历史和冲突解决经验。不同记忆对象需要不同检索和更新机制；把它们混在一个向量库中往往会导致语义相似但功能不匹配的检索错误。

记忆方法的优势在于低成本、可解释和适合长期部署。一个企业 agent 可以在不训练模型的情况下记住组织流程；一个 coding agent 可以记住项目风格和常见 bug；一个 web agent 可以记住网站结构和失败操作；一个科研 agent 可以记住假设、实验结果和负面发现。记忆也是安全审计的重要来源，因为它记录了系统为何改变行为。其局限包括：记忆污染、过期信息、隐私风险、检索错误、上下文膨胀、灾难性坚持错误经验，以及难以区分相关经验和巧合相关。

因此，记忆型自演化需要生命周期管理。写入前要判断经验是否新颖、可靠、可泛化；写入时要包含来源、时间戳、任务范围、置信度和失效条件；检索时要根据任务类型、上下文约束和时间切片过滤；使用后要记录是否帮助成功；长期要进行合并、删除、冲突检测和版本化。Memory-R1 用 RL 管理记忆操作，ACE 用结构化上下文更新避免坍缩，ReasoningBank 用策略蒸馏减少原始轨迹噪声，AriadneMem 处理多跳证据和状态更新，这些都是记忆生命周期管理的不同解法。

## 3.6 混合方法

最有前景的 Agent Evolution 系统往往不是单一方法，而是混合闭环。一个完整自演化 agent 可能先用自课程生成任务，再用奖励或测试验证结果，用反思总结失败，把有效策略写入记忆，必要时修改 prompt 或代码，最后通过 archive 保留多个变体。DGM 结合代码级自修改、经验评估和开放式 archive；WebEvolver 结合 web agent、世界模型和自我改进；RAGEN 结合多轮环境、轨迹级 RL 和稳定训练机制；EvolveR 结合离线自蒸馏、在线检索和策略演化；ACE 结合上下文工程、记忆组织和增量更新；Agent0、AgentEvolver、InfiAgent 等新框架也都倾向于把任务生成、经验复用、奖励分配和结构调整整合起来。

混合方法的动机很简单：单一选择压力不够。奖励能提供方向，但可能稀疏或被 hack；反思能解释失败，但可能幻觉；记忆能保留经验，但可能污染；架构搜索表达力强，但成本和风险高；自博弈能生成数据，但可能偏离真实需求。混合系统通过相互制衡提高可靠性。例如，任务成功分数上升后，反思模块解释原因，记忆模块只保存可迁移策略，隐藏测试检查泛化，安全门控检查副作用，archive 保留旧版本以便回滚。这样的多层验证比单一 benchmark 分数更可信。

混合方法也更接近真实部署。以 coding agent 为例，系统可以采用以下闭环：从真实 issue 或 benchmark 生成任务；agent 尝试修复并运行测试；失败后生成反思；成功补丁进入候选；critic 检查可维护性和安全；若多次失败，架构搜索模块提出工具或流程修改；有效修改写入 agent playbook 或代码；长期经验进入项目记忆；每轮改动都经过回归测试和成本记录。SICA 和 DGM 已经展示代码自修改的可能性，ReasoningBank 和 ACE 可补充长期策略记忆，AlphaEvolve 式 evaluator 可增强自动验证。

以 web agent 为例，WebEvolver 指出单纯反复执行网页任务会遇到探索瓶颈，因此需要 world model 协同进化。一个混合 web agent 需要记忆网页状态和交互结果，生成新的探索任务，用环境反馈训练策略，用反思总结失败操作，用世界模型预测页面变化，再用安全规则限制真实操作。这里的“进化对象”不只是 agent policy，也包括 world model、task curriculum、retrieval memory 和 browser tool-use rules。

以科学发现 agent 为例，AlphaEvolve 和 FunSearch 表明程序化 evaluator 是关键，但科学问题常常不只有单一指标。混合系统需要 LLM 生成假设和代码，实验环境执行验证，文献记忆提供背景，critic 检查统计有效性和可解释性，archive 保留负结果和 stepping stones，人类专家审查高风险结论。若只优化一个实验分数，系统可能发现无意义捷径；若没有 archive，负结果无法积累；若没有人类审查，科学价值和安全边界难以保证。

混合方法的主要挑战是归因。多个模块同时变化时，很难知道性能提升来自哪里。一个系统可能同时更新 reward model、prompt、memory、code 和 task curriculum；若最终分数提高，不能简单说“自演化有效”。因此，混合系统必须做单变量消融：冻结记忆、冻结 prompt、冻结 code modification、替换 judge、固定任务生成器、移除 archive、多随机种子复跑。第5章评估体系强调的迭代增益、迁移、成本、安全和 ablation，对混合方法尤其重要。

另一个挑战是治理。混合系统拥有更大自主性，也需要更强权限控制。可写记忆可能泄漏隐私，可改代码可能引入漏洞，可生成任务可能制造有害内容，可自评估可能掩盖失败，可调用工具可能造成真实世界副作用。安全设计应遵循最小权限、不可篡改评估器、沙箱执行、人工审批阈值、版本化回滚和审计日志。自演化不是让系统随意改变自己，而是让变化发生在被边界化、被记录、被验证的轨道上。


## 3.7 方法选择矩阵：从任务属性到进化机制

为了在实际研究中选择合适方法，可以把任务属性映射到自演化机制。若任务答案可自动验证，例如代码、数学、SQL、程序优化和部分网页操作，优先使用基于奖励或程序化评估的进化，因为验证器能够提供强选择压力。STaR、AlphaEvolve、DGM 和 Absolute Zero 都依赖相对明确的验证信号。若任务需要开放式探索，例如 Minecraft、科研假设生成、产品调研或长程网页任务，则应加入自课程、技能库和 archive，避免系统只围绕固定题集优化。Voyager、WebEvolver 和 DGM 的共同经验是，开放问题不能只保留当前最高分个体，还要保留未来可能成为 stepping stone 的多样化经验。

若任务反馈主要是主观质量，例如写作、总结、对话、规划和偏好对齐，提示词进化、自奖励和人类/模型混合评价更合适。Self-Rewarding 与 Meta-Rewarding 可以扩大偏好数据，ACE 和 EvolveR 可以把长期策略写入上下文，但这类系统必须定期接受外部 judge 或人工抽检，否则容易形成自洽但错误的评价标准。若任务需要适应长期用户或组织环境，例如个人助理、企业流程和软件项目维护，则记忆型进化应成为基础层：记录偏好、项目约束、失败原因、工具经验和合规规则，并通过时间戳和失效条件控制过期信息。

若任务要求 agent 改变自身操作流程，而手工设计已经成为瓶颈，则可以引入架构搜索。ADAS 适合发现可解释的 agent 控制流，EvoMAC 适合多智能体协作拓扑，SICA 和 DGM 适合代码型 agent 的自修改。但架构搜索不应作为第一步使用。更稳妥的顺序是：先冻结代码，优化 prompt 和 memory；再在小范围内搜索工具调用流程；最后才允许代码级改动。每次提升都应由独立测试确认，并与上一版本做差异对比。这样可以避免把一个本可由简单规则解决的问题升级成高风险自改代码问题。

还可以按可变对象选择方法。如果希望改进输出表达，用 Self-Refine、Reflexion 或 ACE；如果希望改进任务选择，用自课程、Absolute Zero 或 Self-Challenging；如果希望改进推理策略，用 STaR、RISE、Agent-R、ReasoningBank；如果希望改进工具使用，用 WebEvolver、Memory-R1 或经验学习；如果希望改进系统结构，用 ADAS、EvoMAC、DGM、SICA；如果希望改进底层模型偏好或策略，用 Self-Rewarding、IterAlign、RAGEN 或 SPIRAL。这个矩阵强调一个原则：不要让更新机制比问题本身更复杂。Agent Evolution 的目标是可验证能力增长，而不是为了“自演化”而引入额外自治性。

## 3.8 消融与失败模式：方法分类的反向视角

从失败模式看，各类方法有不同脆弱点。基于奖励的方法容易 reward hacking：模型可能学会生成 judge 喜欢的格式、利用测试漏洞或过拟合验证集。自博弈方法容易 curriculum collapse：任务生成器反复产生相似题，或生成 solver 永远无法解决的难题。提示词进化容易 context rot：历史原则堆叠造成冲突，模型选择性忽视重要约束。架构搜索容易 structural bloat：为了通过少数任务引入复杂控制流，导致维护成本和失败面增加。记忆进化容易 memory poisoning：错误经验、过期信息或恶意输入被长期保存并影响后续决策。混合方法则容易 attribution failure：模块太多，无法解释哪一处变化带来收益。

因此，方法分类不应只用于综述，也应转化为实验设计。每篇 Agent Evolution 论文至少应回答六个消融问题。第一，若冻结更新对象，性能是否消失？例如冻结记忆、冻结 prompt 或冻结代码。第二，若替换评估器，提升是否仍存在？这能检测 judge overfitting。第三，若换任务时间切片，系统是否仍提升？这能检测污染和过拟合。第四，若限制成本，收益是否仍有性价比？自演化系统常用大量 token 和评估预算换分。第五，若移除 archive 多样性，只保留最高分个体，长期表现如何变化？这能检验开放式探索价值。第六，若注入错误反馈或噪声记忆，系统是否有恢复机制？这能检验鲁棒性。

失败案例同样应被纳入 archive。当前许多论文只报告成功迭代和最终最佳分数，但 Agent Evolution 的科学价值恰恰在于理解哪些更新没有继承、为何失败、失败是否启发后续 stepping stone。DGM 的开放式 archive 思路可以推广到所有方法：失败 prompt、失败工具流程、失败任务、失败记忆和失败代码 patch 都应保留摘要、原因和适用边界。这样，系统学到的不只是“什么有效”，也包括“什么在什么条件下无效”。这对于长期部署尤其重要，因为真实世界任务分布会变化，过去失败的方案在新环境中可能变成有用起点，过去成功的策略也可能过期。

最后，失败模式还提示我们要区分“自我改进”和“自我确认”。一个 agent 如果只读取自己的输出、用自己的 judge 评分、在自己生成的任务上训练，并把自己的反思写入记忆，它可能形成封闭认知回路。真正的自演化需要外部摩擦：真实环境、隐藏测试、不同模型、用户反馈、人工审计、对抗样本和时间切片。外部摩擦越强，改进结论越可信；外部摩擦越弱，系统越可能只是把已有偏差组织得更一致。

## 3.9 横向比较

从改进深度看，提示词和记忆方法最浅，代码和权重更新最深。浅层方法安全、便宜、可解释，但上限受限；深层方法能力强、可表达复杂变化，但风险和成本高。从反馈可靠性看，程序化测试和环境 reward 最强，LLM-as-a-judge 次之，纯自反思最弱；但程序化测试覆盖范围窄，LLM judge 覆盖范围广。 从数据需求看，自博弈和自奖励最能减少外部数据依赖，但最容易形成内源偏差；人类数据最可靠但成本最高。从迁移性看，经验规则、架构模式和技能库如果抽象得好，可能跨任务迁移；直接针对 benchmark 的 reward optimization 则最容易过拟合。

从时间维度看，Agent Evolution 正从“单样本自我修订”走向“跨任务长期自演化”。Self-Refine 主要发生在一次输出内；Reflexion 跨多次尝试；ExpeL、ACE、EvolveR、ReasoningBank 跨任务积累经验；Voyager 和 WebEvolver 跨环境探索；DGM 和 SICA 跨代码版本自修改；AlphaEvolve 跨候选程序搜索科学算法。这个趋势说明，未来研究重点会从“如何让模型多想几步”转向“如何维护一个长期成长的 agent 生态系统”。

从系统边界看，早期方法往往假设基础模型固定，优化外部 prompt 或 memory；后续方法开始训练模型策略；最新方法则把 agent 代码、评估器、世界模型、课程和 archive 都纳入系统。边界扩张带来能力，也带来评估难度。一个系统越能改变自己，就越需要不可改变的外部规范。DGM、Gödel Agent 和 SICA 的经验表明，递归自我改进的工程版本必须依赖强评估和强审计，而不是依赖系统自己的承诺。

## 3.10 小结

Agent Evolution 的方法谱系可以概括为六种互补机制：奖励提供选择压力，自博弈提供数据和课程，提示词进化提供轻量行为更新，架构搜索提供高表达力结构变异，记忆进化提供长期经验积累，混合方法把这些机制组合成可部署闭环。没有任何单一机制足以解决全部问题。奖励会被 Goodhart，反思会幻觉，记忆会污染，架构搜索会昂贵且危险，自博弈会分布塌缩。因此，未来最可靠的系统很可能是分层自演化系统：先在低风险上下文和记忆层学习，再在强验证环境中尝试代码或策略更新，最后通过独立评估、隐藏测试、消融和人工审计决定是否继承。

本章的分类也为后续章节奠定基础。第4章可深入分析代表性系统如何具体实现闭环；第5章可讨论如何评估这些闭环是否真的带来能力增长；第6章可比较工业框架如何支持记忆、工具、工作流和回滚；风险章节则需要关注自奖励、自修改和长期记忆带来的新型安全问题。Agent Evolution 的关键结论是：智能体的能力增长不再只发生在模型训练阶段，而会越来越多地发生在运行时、部署后和系统生态层。如何让这种增长可靠、可控、可复现，将决定该方向能否从研究 demo 走向基础设施。
