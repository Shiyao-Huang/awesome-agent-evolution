\section{User Pain Points: What Practitioners Actually Struggle With}\label{ch:painpoints}

The previous chapters describe how self-evolving agents can be organized as feedback loops, search procedures, memory systems, self-training pipelines, and automatically evaluated software artifacts.  This chapter changes the unit of analysis.  Instead of asking what a paper or framework claims to improve, it asks what users, maintainers, and builders repeatedly report as painful when they try to move agents from impressive demonstrations into durable workflows.  The distinction matters because agent self-evolution is unusually vulnerable to evaluation theater.  A system can improve a benchmark score while increasing debugging cost, hiding prompts, consuming more budget, corrupting memory, or making a deployment less auditable.  For a practical research agenda, those failures are not secondary concerns; they are the actual frontier between a research prototype and a dependable self-improving system.

Our evidence base is a Mom Test style analysis of community discussions and project materials collected for this survey.  The consolidated file reports 131 analyzed posts across Reddit, Hacker News, and X/Twitter, from which 97 distinct pain points were extracted and grouped into 15 categories.  The cross-platform distribution is not uniform.  Reddit threads provide long-form accounts of failed production usage, cost blowups, framework abandonment, and workarounds.  Hacker News comments provide adversarial engineering critiques: API hallucination, prompt optimization failure, benchmark contamination, and self-modification risks.  X/Twitter contributes the fastest-moving diffusion layer: short claims about systems such as DGM, AgentEvolver, Reflexion, SWE-Bench, MCP, and production reliability.  The framework crosswalk further connects these pain points to local repository categories: general orchestration, memory/state, benchmarking, self-evolution, code agents, tools/MCP/security, and workflow automation.

\subsection{Research Methodology: Applying the Mom Test to Agent Evolution}\label{sec:ch7-methodology}

The Mom Test principle is simple: do not ask users whether they like an idea; observe what they have already tried, where they spent time or money, what they abandoned, and what workarounds they constructed.  This is especially important for AI agents because stated preferences are noisy.  Many users say they want autonomous agents, self-improving systems, or long-term memory.  Their actual behavior is more revealing: they replace agent frameworks with plain API calls, manually inspect agent output line by line, add budget kill switches, refuse to let agents modify production code, or abandon frameworks whose abstractions hide the prompt and tool trace.  Those actions are stronger evidence than enthusiasm about future autonomy.

We therefore treat each pain point as valid only when it is grounded in a concrete complaint, failure mode, or workaround.  The extraction protocol used three rules.  First, the evidence must describe something a user encountered or did, not merely a speculative fear.  Second, a workaround counts as strong evidence because it reveals an unmet need: if teams build their own explicit control loops after trying a framework, the missing feature is not another wrapper but observability and controllability.  Third, repeated complaints across platforms are weighted more heavily than isolated anecdotes.  For example, production reliability appears as Reddit's ``80\% reliability ceiling'', HN's skepticism that anyone can demonstrate robust self-improving production agents, and X/Twitter's observation that large engineering effort often yields modest benchmark deltas.

The source set has limitations.  Public community discussions overrepresent technically vocal users, open-source developers, early adopters, and people motivated enough to complain.  They underrepresent silent enterprise deployments and failures that companies cannot disclose.  The data also mixes direct experience with second-hand commentary.  We mitigate this by separating platform-specific evidence types.  Reddit is interpreted as deployment-friction evidence; HN as engineering and falsifiability evidence; X/Twitter as diffusion and narrative evidence; GitHub issues, when available, as maintenance evidence.  The chapter does not claim that all users face all listed problems.  It claims that the same classes of problems recur often enough that any credible self-evolving agent architecture must address them explicitly.

\subsection{Pain Point Taxonomy by Severity}\label{sec:ch7-taxonomy}

Across the consolidated Mom Test analysis, 97 distinct pain points were grouped into 15 categories.  The largest categories are agent reliability in production and self-improvement feasibility, each with 12 items.  Framework/tooling gaps follow with 11, knowledge and memory persistence with 10, evaluation and benchmarking with 9, and safety/security/cost with 7.  This distribution is telling.  The most severe concerns are not about whether a model can call a tool once or produce an impressive trace.  They concern whether an agent can keep working after the first happy-path demo: whether it fails safely, learns without drifting, exposes enough internal state to be debugged, and can be evaluated by metrics that cannot be gamed.

We organize severity into four levels.  \emph{Critical} pain points can destroy trust or make deployment impossible: production unreliability, circular self-improvement, runaway cost, remote-code-execution exposure, and unintended evolution.  \emph{High} pain points block serious adoption but can sometimes be mitigated by engineering: memory persistence, benchmark gaps, deployment friction, and framework observability.  \emph{Medium} pain points slow adoption or create repeated friction: unclear definitions, interaction-model mismatch, practitioner accessibility, and modest gains relative to complexity.  \emph{Low} concerns are not unimportant, but they are less visible in the current data than the first three levels.

\subsection{Reliability and Robustness Pain Points}\label{sec:ch7-reliability}

Reliability is the dominant pain point because agent systems are evaluated less like single-turn chatbots and more like junior operators embedded in workflows.  A one-off answer may be forgiven if it is wrong; an agent that silently corrupts a file, calls a non-existent API, overwrites exact data, or spends a budget overnight is a different kind of risk.  The most repeated complaint is that agents work on demos and fail in production.  In the source material this appears as the ``80\% reliability ceiling'', as claims that benchmark success does not transfer to real workflows, and as frustration that there are few credible examples of self-improving agents operating over long time horizons without heavy human supervision.

A recurring HN pattern is API hallucination.  Developers describe LLMs producing structurally plausible code that calls APIs or libraries that do not exist.  Even when the user points out the error, the model may fail to repair it because it lacks a grounded verification loop against real documentation, installed packages, or executable tests.  This is a critical distinction between code generation and code operation.  A code model can generate a plausible function; an agent must know whether the function exists in the current environment, whether a package version changed, whether permissions are available, and whether the proposed edit preserves exact data.  Without that grounding, self-improvement loops can simply refine hallucinations.

Another repeated robustness failure is poor out-of-distribution behavior.  Users report that agents perform well on common patterns but become ``next to useless'' on niche, domain-specific work.  This aligns with benchmark concerns: widely used public tasks reward interpolation over familiar distributions.  Real production work often involves custom APIs, private schemas, legacy code, unusual constraints, and ambiguous organizational context.  An agent that cannot detect when it is outside its competence boundary becomes dangerous precisely because its outputs remain fluent.  The desired capability is not only better reasoning but calibrated uncertainty, tool-grounded verification, and safe refusal or escalation when evidence is insufficient.

Long-horizon planning is the third reliability failure.  In small demonstrations, an agent can decompose a task, call a tool, and summarize a result.  In real workflows, tasks include evolving requirements, partial failures, authentication changes, hidden state, and dependency conflicts.  Users report replacing autonomous agents with explicit sequential prompts and control loops because those loops are easier to monitor, debug, and recover.  This is not a rejection of automation; it is a demand for automation whose state transitions are visible.  Robustness therefore requires event logs, replayable traces, deterministic checkpoints, rollback, and failure-class taxonomy, not merely more powerful base models.

\subsection{Development and Debugging Pain Points}\label{sec:ch7-debugging}

The second major cluster concerns development experience.  Agent frameworks promise orchestration, memory, tools, multi-agent communication, and workflow management.  In practice, users often complain that these abstractions hide the very information required to debug failure.  The clearest example is the LangChain-style framework critique: prompts and responses become buried under layers of abstractions, simple use cases become complex, and complex use cases become difficult to adapt.  The workaround is revealing: teams remove the framework and rebuild the workflow with direct API calls, explicit prompts, and transparent control logic.

For self-evolving agents, hidden state is more than an inconvenience.  It undermines scientific and operational validity.  If an agent modifies its own prompt, tool instructions, memory, or code, a developer must be able to answer: what changed, why it changed, what evidence justified the change, what evaluation accepted it, what rollback point exists, and whether the change affects other tasks.  Many frameworks expose final messages but not the causal chain that produced them.  That is unacceptable for systems that claim to learn across runs.

Users also complain about dependency bloat and fragile installation.  A framework may require large environments, multiple services, vector stores, browser drivers, tool servers, and model-provider configuration before a simple example works.  This pushes teams toward narrower, explicit implementations.  The lesson is that developer experience must be evaluated by time-to-debug and time-to-rollback, not only by time-to-first-demo.  An agent framework that makes a demo easy but a failure opaque transfers cost from initial setup to every subsequent debugging session.

Prompt optimization creates a related pain point.  Users who tried automated prompt improvement describe the search space as too large for naive optimization.  Minor improvements are possible, but systematic search is hard because prompts interact with model versions, task distribution, tool descriptions, memory content, and evaluator behavior.  When one LLM writes prompts for another, errors can compound: a generated prompt may encourage an agent to build against imaginary APIs or overgeneralize from a narrow success.  This indicates that prompt evolution should be treated as configuration management with tests, diff review, and staged rollout, not as unbounded natural-language mutation.

\subsection{Production and Deployment Pain Points}\label{sec:ch7-production}

Production deployment introduces constraints that research demonstrations usually simplify away.  A production agent must run under identity and permission boundaries, interact with changing external systems, handle partial observability, preserve user data, recover from tool failures, and produce logs that satisfy internal review.  The Mom Test data repeatedly shows that users do not merely ask for smarter agents; they ask for agents that fail within operational boundaries.

Cost transparency is one such boundary.  Agent loops can multiply calls through planning, reflection, tool retries, verifier calls, debate, self-consistency, and memory retrieval.  A system that improves quality by five percentage points while tripling cost may be unacceptable.  Worse, failures can trigger runaway loops: repeated retries, browser actions, or tool calls that continue after the objective is already impossible.  Users cite examples of agents burning large budgets overnight.  The missing metric is not average cost per call but cost per accepted output, cost per recovered failure, and maximum possible cost under worst-case loop behavior.

Security is another deployment blocker.  Tool-using agents expand the attack surface.  MCP and similar tool protocols make it easier to connect agents to files, browsers, databases, and internal services; they also make prompt injection and permission escalation more consequential.  A malicious web page, poisoned memory, or compromised tool description can influence an agent's future behavior.  Self-modifying agents add a second-order risk: the attack can become persistent if the system writes the malicious instruction into memory, prompt templates, or tool policies.  Therefore, production self-evolution requires memory sanitation, tool-result trust labels, least-privilege tool scopes, sandboxed candidate generation, and approval gates for persistent changes.

Enterprise governance appears with low frequency but high severity.  Organizations need audit trails, data residency, access control, compliance evidence, and predictable support.  A self-evolving agent complicates each requirement because its behavior changes over time.  Governance cannot be bolted on after deployment; it must be part of the evolution loop.  Every accepted change should have provenance, evaluator evidence, affected scope, rollback pointer, and policy review status.  Without that lineage, the system becomes impossible to certify even if it performs well in a benchmark.

\subsection{Framework Gap Analysis}\label{sec:ch7-framework-gap}

The framework crosswalk reveals a supply--demand mismatch.  Open-source activity is heavy in orchestration, memory, benchmarking, and self-evolution.  Yet the strongest pain points are precisely in the production properties those categories are supposed to solve.  General agent frameworks are visible and widely discussed, but users complain about prompt opacity, dependency bloat, deployment difficulty, and long-chain failure.  Memory and RAG projects are abundant, but users still report memory pollution, retrieval noise, context bloat, and drift.  Evaluation repositories are numerous, but public benchmarks remain contaminated, gameable, and misaligned with production labor.  Self-evolution projects are exciting, but users describe real ``self-improvement'' as manual log review, prompt rewriting, and human-controlled rollback.

This crosswalk reframes the maturity question.  The issue is not whether there are enough agent frameworks.  There are many.  The issue is whether frameworks internalize the operational lessons from user pain.  A mature framework should expose prompt and tool traces by default, support state replay, provide cost guards, classify failure modes, preserve exact data during edits, maintain memory provenance, and connect benchmarks to session-level production metrics.  In other words, it should be less like a magic autonomy wrapper and more like an operating system for controlled evolution.

\subsection{Implications for Self-Evolving Agent Research}\label{sec:ch7-implications}

The pain-point evidence implies five design requirements for self-evolving agents.  First, every improvement loop needs an independent evaluator.  Self-critique alone is useful but insufficient because users already distrust circular evaluation.  The evaluator should be separated from the mutator, versioned, tested, and periodically checked against hidden or human-reviewed tasks.  Second, every persistent change needs lineage.  If an agent modifies a prompt, memory, tool policy, or code path, the system must record the diff, evidence, expected benefit, rollback plan, and affected scope.

Third, memory must be governed like a database, not appended like a chat log.  Long-term memory should support provenance, expiration, deduplication, conflict detection, retrieval-quality evaluation, and rollback.  Otherwise, memory becomes a contamination vector.  Fourth, cost must be a first-class safety variable.  Agent loops should have hard caps, predicted cost envelopes, and metrics such as cost per successful task and cost per prevented regression.  Fifth, production evaluation must be session-level.  Single benchmark scores are insufficient; evaluation should include recovery from tool errors, exact-data preservation, human handoff quality, latency, cost, permission behavior, and rollback success.

The central conclusion is that the path from agent demos to self-evolving production systems is not blocked by a single missing model capability.  It is blocked by a stack of missing operational guarantees.  Users want agents that learn, but they also want to know what changed, why it changed, whether it helped, how much it cost, how it can be rolled back, and whether it introduced new risk.  A self-evolving agent that cannot answer those questions is not autonomous in the useful sense; it is merely opaque.

For the broader Awesome-Evolution project, these findings clarify what resources are most valuable.  The list should not only catalog papers and repositories by novelty.  It should identify which projects provide production evidence, which expose traces, which support rollback, which report cost, which evaluate sessions rather than isolated tasks, and which address memory governance and security.  The most useful index for practitioners is therefore not a popularity ranking but a trust map: what can be tried safely, what is research-only, what requires strong external validators, and what should not be deployed without additional controls.

\paragraph{Why reliability complaints are stronger than benchmark deltas.}
A recurring pattern in the community evidence is that users do not deny that benchmarks are improving.  They object that benchmark deltas do not explain the failures that dominate their day-to-day work.  A SWE-Bench improvement can be meaningful for research and still fail to tell a team whether an agent will preserve a configuration file, avoid rewriting exact URLs from memory, or stop when a tool returns a misleading response.  In this sense, benchmark deltas and user pain are measuring different objects.  Benchmarks often measure whether the final answer can be accepted under a clean evaluation protocol.  Practitioners measure how much supervision was needed, how many hidden assumptions broke, how much state was lost, and how costly it was to diagnose the failure.  The gap between these objects explains why users can admire systems such as Reflexion, DGM, or AlphaEvolve while still refusing to trust a self-evolving agent with production authority.

A practical evaluation suite should therefore include negative and operational cases.  For code agents, it should include tasks where the correct behavior is to preserve data exactly, refuse to edit, ask for missing context, or detect that a library version does not support a proposed API.  For browser and workflow agents, it should include changed page structure, expired sessions, partial form submission, permission denial, and recovery after a tool timeout.  For memory agents, it should include contradictory memories, obsolete facts, poisoning attempts, and long intervals between related tasks.  For self-modifying agents, it should include proposed improvements that increase benchmark score while harming cost, security, or maintainability.  These tests are less glamorous than leaderboard tasks, but they correspond more closely to the situations in which users lose trust.

\paragraph{The false economy of opaque abstraction.}
Many framework complaints can be interpreted as a false economy.  The framework saves time when the task follows the intended path, but it increases cost when the task fails.  Hidden prompts, implicit tool routing, automatic memory injection, and unclear retry behavior can make a system look concise while shifting complexity into the debugging phase.  For a one-off prototype, this tradeoff may be acceptable.  For a self-evolving agent, it is dangerous because the system's future behavior depends on traces that developers may not be able to inspect.  If a framework cannot show exactly which context, memory, prompt, tool result, and evaluator judgment led to an accepted update, then it cannot support trustworthy self-improvement.

The framework lesson is not that abstractions are bad.  It is that abstractions must be inspectable.  A database abstraction is acceptable because queries can be logged, transactions can be rolled back, and schemas can be inspected.  An agent abstraction should offer analogous properties: trace logs, state snapshots, transition IDs, prompt diffs, memory provenance, tool-call schemas, and replay harnesses.  The user pain data suggests that frameworks are often judged not by how elegant their API looks but by whether they make failures legible.  This should be a central benchmark for future framework research.

\paragraph{Memory as a governance problem.}
The popularity of memory systems reflects a real demand.  Users want agents to learn from previous trajectories, remember project-specific constraints, avoid repeating mistakes, and accumulate domain knowledge.  However, the pain points show that memory is also a governance problem.  A memory item can be wrong, stale, overgeneralized, private, adversarial, duplicated, or contextually inappropriate.  If such items are retrieved automatically, the agent may behave worse while appearing more personalized.  Long-term memory therefore requires policies for admission, retrieval, revision, and deletion.

A robust memory architecture should distinguish at least five classes of memory: episodic traces of what happened, semantic facts about a project or domain, procedural lessons about how to act, preferences about how a user wants work done, and safety constraints that should not be casually overwritten.  Each class has different lifecycle rules.  Episodic traces may be compressed but should retain provenance.  Semantic facts require freshness checks.  Procedural lessons require validation across more than one task.  Preferences should be user-editable.  Safety constraints require higher authority to modify.  Current agent demos often collapse these classes into generic context snippets.  The resulting system may appear to have memory while lacking the controls needed for reliable learning.

\paragraph{Self-improvement requires evidence, not self-confidence.}
The phrase ``self-improving agent'' is often interpreted too loosely.  If an agent rewrites a prompt and then claims that the new prompt is better, nothing has been proven.  If it passes the same public benchmark it optimized against, the evidence is stronger but still incomplete.  If it improves on a hidden validation suite, preserves old capabilities, reduces or maintains cost, and passes safety checks, the claim becomes more credible.  The Mom Test findings show that users implicitly demand this evidence ladder.  They are not satisfied with self-confidence, because they have seen agents fabricate logs, overfit benchmarks, or become more verbose without becoming more useful.

This suggests a minimal acceptance protocol for self-evolution.  Every candidate change should be evaluated against a baseline, a target task set, a regression set, a cost envelope, and a safety policy.  The system should record not only whether the candidate won but how it won.  Did it solve more tasks?  Did it use more calls?  Did it rely on a brittle shortcut?  Did it break older tasks?  Did it increase security exposure?  A candidate that improves one number while worsening several operational variables should not be called a net improvement.  This multi-objective view aligns self-evolution with engineering reality.

\paragraph{Production proof as a missing evidence class.}
One of the most important but least standardized evidence classes is production proof.  Papers report benchmark scores; repositories report stars; demos report videos; users ask whether anyone has run the system continuously under real constraints.  Production proof does not need to mean that a company exposes private data.  It can mean reporting anonymized session counts, failure rates, average and tail costs, human intervention frequency, rollback frequency, incident classes, and time-to-diagnosis.  These metrics would make agent claims more comparable and would directly address the pain points surfaced in Reddit and HN discussions.

For self-evolving systems, production proof should also include change history.  How many self-generated modifications were proposed?  How many were rejected?  Why were they rejected?  How many were rolled back after acceptance?  Which validators caught harmful changes?  How often did hidden tests prevent regressions?  This information would transform self-evolution from a narrative into an auditable engineering process.  The absence of such reporting is one reason users remain skeptical even when research results are impressive.

\paragraph{Human-agent collaboration is not a temporary weakness.}
A common assumption is that human-in-the-loop design is merely a transitional phase before full autonomy.  The pain-point evidence suggests a different interpretation.  Human-agent collaboration is a durable design requirement because many real tasks involve ambiguous preferences, organizational risk, and irreversible actions.  The question is not whether to remove humans entirely, but where to place human judgment so that it is high-leverage rather than constant babysitting.  Users do not want to approve every token; they want to approve risky changes, inspect summarized evidence, and intervene when uncertainty or cost crosses a threshold.

This reframes collaboration metrics.  A useful agent should reduce low-value human labor while preserving meaningful control.  Evaluation should measure review burden, quality of escalation, clarity of diffs, and whether the agent asks for help at the right time.  In self-evolving agents, the human role may shift from executor to governor: defining constraints, reviewing candidate policies, approving high-impact memory, and auditing anomalies.  Systems that make this role easy will be more deployable than systems that insist on binary autonomy.

\paragraph{A research agenda derived from pain points.}
The pain-point taxonomy implies a concrete research agenda.  First, create session-level benchmarks that include tool failures, state drift, user handoff, and cost accounting.  Second, develop memory evaluation suites that test poisoning, staleness, contradiction, retrieval precision, and deletion.  Third, design self-modification protocols with lineage, rollback, and independent validation.  Fourth, build observability standards for agent traces, analogous to logs and distributed tracing in cloud systems.  Fifth, report cost and safety metrics alongside performance.  Sixth, evaluate framework ergonomics by debugging time and failure transparency, not only by API brevity.

This agenda is less spectacular than open-ended recursive improvement, but it is more aligned with the failures users actually report.  If self-evolving agents are to become trusted infrastructure, they must become boring in the best engineering sense: observable, bounded, reproducible, recoverable, and auditable.  Only then can more ambitious forms of open-ended improvement be safely layered on top.

\paragraph{Operational personas behind the pain points.}
The pain points also differ by persona.  A research author primarily worries that an improvement method is novel, measurable, and publishable.  A framework maintainer worries that the abstraction is general enough to support many users.  A startup builder worries about time-to-demo and customer-facing reliability.  An enterprise platform team worries about access control, audit, data boundaries, and incident response.  A security engineer worries about tool permissions, prompt injection, and persistence of malicious instructions.  A finance or operations owner worries about unpredictable token and tool spend.  Many disagreements in public discussions arise because these personas use the same word, ``agent'', for different risk profiles.

For example, a research user may accept an agent that fails often if failures produce useful experimental data.  A production user may reject the same system because one silent failure can corrupt a customer workflow.  A framework author may celebrate composability, while a developer debugging an incident experiences composability as a larger state space.  A benchmark designer may focus on final accuracy, while a manager cares about how many human reviews were needed before the final answer was safe.  A useful survey of self-evolving agents must therefore preserve these persona distinctions.  The user pain data is not anti-research; it is a reminder that research claims are interpreted through operational roles.

\paragraph{Reliability should be decomposed, not averaged.}
The ``80\% reliability ceiling'' phrase is useful because it captures frustration, but it can hide several different failure modes.  Reliability can fail at task understanding, planning, tool selection, tool execution, memory retrieval, code editing, verification, communication, or escalation.  Averaging these failures into one success rate makes diagnosis difficult.  A self-evolving system might improve planning while making memory retrieval worse, or improve code generation while increasing tool-call cost.  The correct response is not only a higher average score but a decomposed reliability model.

A decomposed model should record failures by stage.  Did the agent misunderstand the goal?  Did it choose an unavailable tool?  Did it call a real tool with wrong arguments?  Did it ignore a tool error?  Did it hallucinate a successful test?  Did it overwrite exact data?  Did it fail to ask for clarification?  Did it continue after the budget should have stopped it?  These categories are actionable.  They also support targeted self-improvement: a memory update should not be accepted as a fix for a tool-permission failure, and a prompt change should not be accepted as a fix for missing environment validation.  This is how pain-point analysis can improve the design of evolution loops.

\paragraph{Benchmark contamination as a trust problem.}
Benchmark contamination is often discussed technically: whether tasks appeared in training data, whether test cases are public, or whether benchmark-specific heuristics can be learned.  The pain-point data shows that contamination is also a trust problem.  Users ask whether a reported improvement indicates general ability or familiarity with the test.  When systems optimize public benchmarks, users suspect Goodhart's Law: the metric becomes a target, and the target ceases to represent value.  This suspicion grows when a system's real-world behavior remains brittle despite strong scores.

The response should be layered evaluation.  Public benchmarks are useful for comparability and should not be discarded.  But they should be paired with private regression suites, newly generated tasks, real workflow replays, and adversarial failure cases.  For self-evolving agents, the evaluation set should change over time faster than the agent can overfit to it, while preserving a stable subset for regression tracking.  Reports should explicitly separate in-distribution benchmark gains, cross-benchmark transfer, and production-like session results.  This separation would make claims more credible and help practitioners decide whether a method is relevant to their risk profile.

\paragraph{Cost as an alignment signal.}
Cost is usually treated as an engineering constraint, but in agents it is also an alignment signal.  An agent that solves a task by calling a model 200 times may be optimizing for completion while ignoring the user's real objective: useful work under a budget.  A self-improving system that learns to add more reflection, more debate, more verification, and more sampling can improve accuracy while becoming economically misaligned.  Users notice this quickly because they pay the bill and operate under latency constraints.

Cost-aware self-evolution should therefore treat budget as part of the reward.  Candidate policies should be compared by quality, latency, model-call count, tool-call count, and worst-case loop bound.  A candidate that improves success rate by 2\% while doubling cost may be rejected unless the task is high value.  Conversely, a candidate that maintains quality while reducing calls may be a major improvement.  This suggests that agent leaderboards should report Pareto curves rather than single scores: success versus cost, success versus latency, and success versus human review time.  Such reporting would directly address a major class of user pain.

\paragraph{Security pain is amplified by persistence.}
Prompt injection is harmful in ordinary tool-using agents, but self-evolving agents amplify it because they can preserve the injected instruction.  If a malicious webpage convinces an agent to store a rule, modify a tool description, or rewrite a prompt, the attack can outlive the original session.  This makes memory and self-modification security-critical.  The pain-point data's concern about MCP, tool permissions, and self-modification should therefore be read as one combined issue: agents increasingly connect to powerful tools while also gaining mechanisms for persistent adaptation.

A safe architecture should label every external input by trust level.  Web content, tool output, user instruction, developer policy, system policy, and verified test results should not enter memory with the same authority.  Persistent changes should require high-trust evidence.  Low-trust content may inform a task but should not rewrite global behavior.  The architecture should also support quarantine: suspicious memories or proposed changes can be stored for review without being used automatically.  These controls are standard in security-conscious systems but are often absent from agent demos.

\paragraph{Exactness as an underrated capability.}
Several user complaints involve agents rewriting precise content from memory rather than preserving it.  This is a different skill from creativity or reasoning.  Many production tasks require exactness: URLs, configuration keys, legal clauses, database identifiers, code comments, environment variables, and customer-specific values must not be paraphrased.  LLMs are trained to generate plausible continuations, so they may treat exact strings as content to be regenerated rather than artifacts to be preserved.  Users experience this as silent corruption.

Self-evolving agents need explicit exactness modes.  Before editing a file, an agent should classify regions as semantic text, executable code, structured data, or immutable exact data.  Edits to immutable regions should require either exact copying or explicit approval.  Diff tools should highlight not only line changes but invariant violations.  For code agents, tests should include data-preservation assertions.  For document agents, exact spans may need checksums.  These requirements may appear mundane, but they directly address why developers hesitate to let agents operate on production repositories.

\paragraph{From taxonomy to scoring rubric.}
The pain taxonomy can be converted into a scoring rubric for repositories and papers in the Awesome-Evolution index.  Each project can be evaluated on eight dimensions: production evidence, trace visibility, evaluator independence, rollback support, memory governance, cost control, security boundary, and benchmark breadth.  A project with strong benchmark results but no trace visibility or rollback should be labeled research-promising but deployment-risky.  A framework with modest model novelty but excellent observability may be more valuable to practitioners.  A memory system without deletion and contradiction handling should not be described as production-ready merely because it persists context.

Such a rubric would also reduce hype.  Stars, demos, and benchmark scores would remain visible, but they would be contextualized by operational maturity.  This aligns with the user's stated goal for the broader project: not merely collecting links, but building a high-quality information and data analysis layer around the Self Evolve brand.  Pain-point scoring turns community complaints into structured evaluation criteria.

\paragraph{Chapter summary.}
The strongest conclusion from the Mom Test analysis is that practitioners are not asking for less capable agents.  They are asking for capability under control.  They want agents that can improve, but only through evidence; remember, but only with governance; use tools, but only within permissions; act autonomously, but only within budget and rollback boundaries; and report success, but only with metrics that match real work.  This is the practical definition of trustworthy self-evolution.  It is not a single algorithm.  It is a socio-technical contract between models, tools, evaluators, developers, users, and organizations.

\paragraph{What should be reported in future papers.}
Future self-evolving-agent papers should include a pain-point-aware reporting checklist.  In addition to task success, they should report the number of candidate modifications generated, the acceptance rate, the rejection reasons, the number of regressions caught, the number of rollbacks, the evaluator used for each gate, the cost of search, and the latency overhead of verification.  They should state whether the evaluator was public, hidden, model-based, programmatic, or human-reviewed.  They should disclose whether the same model proposed and judged the change.  They should show at least one negative example where a proposed self-improvement was rejected and explain why.  Negative evidence is valuable because it demonstrates that the system has a real gate rather than a narrative of inevitable improvement.

The same principle applies to framework papers.  A framework should report not only supported features but failure observability.  Can a user replay a run?  Can they inspect the exact prompt sent to each model?  Can they see which memory entries were retrieved?  Can they disable automatic memory injection?  Can they simulate tool failures?  Can they set budget policies?  Can they export traces for external audit?  These questions map directly to the development and production pain points in the source material.  A framework that answers them clearly may have more practical value than a framework with more agent roles but weaker debugging support.

\paragraph{What should be reported in project indexes.}
For an Awesome-style index, the pain-point analysis suggests that each listed project should carry operational metadata.  Suggested fields include: target domain, evidence level, benchmark coverage, production evidence, trace support, rollback support, memory type, evaluator type, security boundary, cost controls, maintenance status, and known limitations.  The index should distinguish paper code from production frameworks, benchmarks from harnesses, memory stores from memory-governance systems, and tool protocols from security-reviewed tool runtimes.  This prevents a common failure of ecosystem maps: placing all projects with similar keywords into the same bucket even though their risk profiles differ.

A time-decay dimension is also important.  The user's broader instruction emphasizes that classification should adapt as new material arrives and that time order should decay appropriately.  In the pain-point setting, this means recent production complaints and current maintenance status should weigh more heavily than older launch announcements.  A repository with many historical stars but inactive maintenance may be less useful than a smaller project with current releases, visible issue triage, and concrete production case studies.  Likewise, a benchmark score from an older model should not dominate current evidence if the benchmark is now saturated or contaminated.

\paragraph{The positive reading of the pain data.}
Although this chapter is critical, the pain data should be read constructively.  Users complain because they are trying to use agents.  They abandon frameworks because they care enough to build replacements.  They worry about memory because they want agents that learn.  They criticize benchmarks because they need evaluation that matters.  They fear self-modification because they recognize its power.  In this sense, pain points are demand signals.  They show where the next generation of self-evolving-agent research can create real value.

The most promising systems will likely combine the strengths described in earlier chapters with the constraints described here.  They will use reflection, self-training, evolutionary search, and memory, but only inside architectures that expose traces, enforce budgets, isolate tools, validate changes, and preserve rollback.  They will not treat users as obstacles to autonomy; they will treat user feedback, operational telemetry, and incident reports as the data stream from which practical self-evolution should learn.  That is the bridge from the research frontier to a durable Self Evolve ecosystem.
