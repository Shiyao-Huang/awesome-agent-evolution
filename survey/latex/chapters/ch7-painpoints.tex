\section{用户痛点}\label{ch:painpoints}

\subsection{研究方法}

本章基于\textbf{The Mom Test}方法论，从Reddit (62帖)、Hacker News (46帖)和X/Twitter (23帖)的真实社区讨论中提取用户痛点。遵循以下原则：(1) 从实际用户体验提取，非理论观点；(2) 关注用户做了什么，而非声称想要什么；(3) 识别变通方案作为未满足需求的证据。

\subsubsection{Theme 1: ``Demo有效，生产失败''}

\begin{itemize}[nosep]
\item Reddit: ``80\% reliability ceiling'' — agents通过benchmark但在真实workflow中失败
\item HN: ``Nobody can demonstrate real production success with self-improving agents''
\item X: 改进百分比有限（DGM: 20\%$\to$50\% on SWE-bench）
\end{itemize}

\subsubsection{Theme 2: ``自改进是神话（目前）''}

\begin{itemize}[nosep]
\item Reddit: ``Feedback loops require human labor, drift, plateau without verifiers''
\item HN: ``LLMs are bad at prompting other LLMs, the prompt search space is too large''
\item GitHub Issue: ``Self-improving AI agent is a myth''
\end{itemize}

\subsubsection{Theme 3: ``框架被抛弃''}

\begin{itemize}[nosep]
\item Reddit: ``Zero prompt visibility, 1GB dependency bloat, state management nightmares''
\item HN: ``LangChain abstractions hide debugging, frameworks fail in production''
\item 开发者: ``AutoGen, LangGraph, CrewAI, PydanticAI, Swarm, Agno — zero survive months of real use''
\end{itemize}

\subsubsection{Theme 4: ``Benchmark被操控''}

\begin{itemize}[nosep]
\item Reddit: ``No session-level evals, benchmarks ignore 92\% of labor''
\item HN: ``SWE-Bench is contaminated/saturated/gameable, Goodhart's Law applies to every metric''
\item X: ``Research optimizes for benchmarks, not real-world value''
\end{itemize}

\subsubsection{Theme 5: ``自修改是危险的''}

\begin{itemize}[nosep]
\item Reddit: ``RCE vulnerabilities in open platforms, agents burning \$2K overnight''
\item HN: ``Self-modification is a prompt injection attack vector. The skills hub is poisoned.''
\item X: ``Agents evolve in harmful, unintended directions''
\end{itemize}

\subsection{对awesome-evolution项目的启示}

基于这些发现，最有价值的资源方向是：

\begin{enumerate}[nosep]
\item \textbf{生产就绪框架}：具有已验证部署记录的系统
\item \textbf{评估工具包}：超越benchmark的session级评估
\item \textbf{安全/治理模式}：针对自修改agent的安全沙箱和回滚机制
\item \textbf{记忆架构}：不膨胀上下文的持久记忆方案
\item \textbf{实用自改进模式}：无需人工验证循环的可行改进路径
\end{enumerate}

\subsection{扩展分析：用户痛点作为负面证据基}
\label{sec:ch7-english-recovery}

本节重建第~\ref{ch:painpoints} 章的分析层，不覆盖上方已有的材料。目标是将 Mom Test 发现转化为研究级别的分析，说明为什么智能体自进化仍然难以部署。实证基础是本地痛点语料库：131条社区帖子、97个独立痛点和三个平台切片（Reddit、Hacker News和X/Twitter）。关键方法论选择是将投诉、变通方案、被抛弃的框架、成本事件和调试经历视为证据。在 Mom Test 传统中，最可靠的信号不是用户声称想要什么，而是他们已经尝试了什么、什么失败了、替换了什么、以及容忍了哪些变通方案。

因此，本章与方法和系统章节形成互补。前几章描述了自进化智能体在受控环境下能做什么：生成推理链、修正答案、存储反思、更新策略、搜索架构或在自动评估器下进化代码~\cite{reflexion2023,adas2024,dgm2025}。本章提出不同的问题：当这些机制接触真实工作流时，在哪里会崩溃？答案在各个平台间一致。用户主要不是抱怨智能体缺乏令人印象深刻的演示。他们抱怨的是演示无法经受生产环境的考验：可靠性停留在运营阈值以下，框架隐藏调试所需信息，记忆要么缺失要么不可控，基准测试未能衡量真实劳动量，自改进循环仍需要人工判断，而安全/成本风险随自主性增长而扩大。

由此生成的痛点图谱不应被解读为反智能体情绪。许多帖子来自积极使用智能体构建产品的人——他们付费使用API、测试框架、维护仓库、尝试自动化真实工作。他们的挫败感恰恰有用，因为它是操作性的。他们知道当前系统在哪里节省时间，也知道节省的时间在哪里消失在监控、修复、提示调试、依赖管理或回滚中。对于智能体进化综述而言，这些证据可以防止方法乐观主义变成产品神话。

\subsubsection{研究方法论：将 Mom Test 应用于智能体进化}
\label{sec:ch7-methodology-english}

Mom Test 方法旨在减少客户发现中的假阳性。它不询问用户是否喜欢某个想法，而是询问具体的过去行为：他们尝试了什么、为什麽付费、放弃了什么、自己构建了什么、以及产生了什么后果。这对智能体自进化尤其重要，因为该领域的语言是愿景性的。``autonomous''（自主的）、``self-improving''（自改进的）、``recursive''（递归的）、``production-ready''（生产就绪的）和``agentic''（智能体的）等术语听起来令人信服，即使底层系统仍然依赖人工审查、隐藏的提示调优、脆弱的基准测试或人工救援。

在本章中，Mom Test 证据通过四个过滤器解读。第一，投诉必须基于实际使用场景，如构建商业智能体、使用框架、运行编码助手、部署工作流或评估自改进声明。第二，变通方案与投诉同等重要。如果开发者移除了框架并用纯 API 调用替代，这个行为比笼统声称框架不好是更强的证据。第三，跨平台重复投诉比孤立意见权重更高。同一主题出现在 Reddit 部署故事、HN 工程辩论和 X/Twitter 研究评论中，表明这是一个结构性问题。第四，声明与测量需分离。关于基准提升的病毒式帖子对追踪叙事有用，但生产痛点需要关于可靠性、成本、安全和维护的证据。

本地语料库包含三个互补的证据来源。Reddit 线程倾向于提供生活经验：长时间运行的智能体、本地自动化尝试、成本意外、框架采用失败、记忆挫折和实际评估差距。Hacker News 讨论倾向于提供工程批判：抽象泄漏、API 幻觉、基准污染、自修改风险和对递归改进的怀疑。X/Twitter 贡献高速研究和产品叙事：新系统、声称的增益、新兴安全问题和压缩比较。这些平台单独都不具有代表性。但组合起来，它们构成了当智能体进化从论文走向实践时构建者注意到的三角验证图。

将97个痛点编码为15个类别创建了实证分类而非理论分类。排名靠前的类别是生产环境中的智能体可靠性、自改进可行性、框架/工具缺陷、评估与基准测试、知识与记忆持久化、安全/成本治理。这些计数不应被解读为精确的市场普遍程度，因为语料库是社区采样且存在平台偏差。它们更适合理解为摩擦密集方向的方向性证据。项目较少但严重度极高的类别，如误进化或生产证明缺失，仍可能值得高研究优先级，因为单次故障就可能使部署变得不可接受。

\subsubsection{按严重度划分的痛点分类}
\label{sec:ch7-taxonomy-english}

严重度不同于频率。一个频繁出现的烦恼，如依赖膨胀，可能减缓采用但可通过更好的打包解决。一个不太频繁的问题，如不安全的自修改或失控支出，可能直接阻止部署。因此，分类将痛点分为四个严重度层级：关键阻断因素、高严重度工程缺口、中等采用摩擦和长尾标准化问题。

关键阻断因素是阻碍对自主或自进化系统建立信任的故障。语料库识别出六个反复出现的阻断因素。第一，智能体对于生产工作流仍然过于不可靠——80\%的成功率是失败而非进步。第二，自改进尚未获得信任，因为反馈循环仍需要人工参与，缺乏验证器时会漂移，在浅层增益后停滞。第三，当智能体调用工具、循环重试或变异提示时，安全和成本事件可能快速放大。第四，生产证明稀缺：用户反复要求真实部署的自改进智能体证据而非演示。第五，误进化引入动态风险：智能体可能学到错误教训、存储它并在之后应用。第六，当智能体、评判者和基准测试不独立时，评估是循环的。

高严重度工程缺口是不一定阻止部署但使其昂贵且脆弱的问题。框架不透明性是一个典型例子。开发者无法检查导致故障的确切提示、状态、工具载荷、重试规则或模型响应时就会抱怨。记忆持久性是另一个问题：智能体在跨会话时从零开始，但简单的记忆实现会导致上下文膨胀、过时规则和隐私风险。基准不匹配也是高严重度的。静态编码基准有用，但许多用户需要行政、法律、销售、运营、研究或客户支持方面的可靠性。排行榜分数不自动转化为这些领域。

中等严重度摩擦影响采用速度和维护。包括框架更替、碎片化API、不明确的标准、令人困惑的多智能体抽象以及真实部署示例不足。它们不如安全故障灾难性，但会累积。一个团队可能放弃框架不是因为一次失败，而是因为每次调试会话都需要剥开抽象、修补依赖并猜测智能体实际观察到的状态。

长尾标准化问题包括``agent''、``self-evolution''、``memory''和``production-ready''定义不一致。这些问题听起来是语义性的，但它们塑造评估。如果一个仅仅重试提示的系统被宣传为自改进，用户无法区分浅层控制流与持久学习。如果框架将每个角色提示称为智能体，多智能体声明就变得难以比较。如果基准测试忽略成本和人工干预，生产声明就会被夸大。

\subsubsection{可靠性与鲁棒性痛点}
\label{sec:ch7-reliability-english}

可靠性是最常被提及的实际问题。用户报告智能体在演示中表现出色，但在真实工作流中失败，因为真实工作流包含模糊输入、过时API、缺失权限、部分失败、冲突指令和长状态历史。在短基准测试上成功的模型可能在需要调用工具、从工具错误中恢复、维护计划、避免幻觉API并决定何时停止时失败。

可靠性痛点有多个层次。在输出层，智能体会幻觉事实、API、文件路径、引用或工具能力。在过程层，它们无法从错误中恢复、重复操作或偏离原始目标。在会话层，它们丢失上下文、遗忘约束或凭记忆重写代码而非保留精确已有内容。在工作流层，它们无法保证跨多步骤完成。在组织层，它们的错误产生隐性人工劳动：检查、重运行、调试、解释和清理。

语料库中反复出现的短语是可靠性天花板。用户需要的不是一个在低风险演示中大部分时间有效的智能体；他们需要的是一个失败率与业务流程兼容的系统。在客户支持中，小的幻觉率可能造成政策违规。在编码中，一个通过可见测试但破坏隐藏行为的补丁可能比手工工作成本更高。在运营中，无限循环的智能体可能触发成本和安全警报。因此，可靠性不是单一分数，而是任务、时间和失败后果上的分布。

鲁棒性需要错误恢复。一个可靠的智能体应该知道何时不确定、工具结果何时与计划矛盾、生成的API何时未被文档记录、文件何时在它之下被更改、何时应该寻求帮助。许多当前系统不是这样，而是通过尝试另一个看似合理的补全来响应失败。这对头脑风暴可能可接受，但对生产不可接受。所需行为更接近容错软件：检测、隔离、带约束重试、优雅降级和升级。

自进化只有在反馈循环有根据时才能帮助可靠性。Reflexion 风格的记忆可以存储失败教训，但不正确的教训可能恶化未来行为。Self-Refine 风格的批评可以捕获遗漏，但无根据的批评可能只产生更自信的文本。代码执行可以暴露错误，但测试可能不完整。因此语料库支持一个保守设计原则：可靠性循环应优先使用外部证据而非自我判断。如果任务可以由编译器、测试、模式、数据库约束或独立评估器检查，该信号应主导自然语言自我评估。

\subsubsection{开发与调试痛点}
\label{sec:ch7-debugging-english}

开发痛点的核心是可观测性。构建者反复抱怨智能体框架隐藏了调试故障所需的信息：提示在内部组合、工具调用被抽象包装、状态分散在回调中、重试没有清晰追踪。当系统失败时，开发者无法轻松回答基本问题：模型看到了什么、它决定了什么、它产生了什么工具参数、返回了什么、记忆中存储了什么、下一步为什么发生？

这就是为什么一些团队放弃高级框架并回归显式控制循环。纯 API 调用、类型化模式、小函数和可见提示可能看起来不如完整智能体框架优雅，但它们使调试可行。痛点不是反框架；而是反黑箱。一个有用的框架应该使智能体比手写粘合代码更可观测，而非更不可观测。

对于自进化智能体，调试更困难，因为系统可能在故障之间发生变化。静态应用有固定代码路径；进化智能体可能已更改其提示、记忆、工具集、路由策略或评估器。开发者调试昨天的故障需要确切的祖先状态，而不仅仅是当前系统。这产生了对谱系的需求：版本化的提示、版本化的记忆、版本化的工具、版本化的评估器和可重放的追踪。

语料库还强调了依赖和部署摩擦。大型虚拟环境、快速变化的API、未文档化的框架行为和不兼容的插件生态系统使智能体系统的长期维护变得困难。这些问题不够吸引眼球，但它们决定采用率。一个需要脆弱基础设施的自改进方法将被需要稳定运营的团队忽略。

生产级自进化智能体调试栈应包括：完整提示可见性；结构化工具调用日志；状态快照；尽可能的确定性重放；成功和失败运行之间的追踪级差异；记忆来源；每步成本归因；包含输入的评估器决策；以及每个持久变更的回滚指针。没有这些功能，自进化增加调试面的速度快于增加能力。

\subsubsection{生产与部署痛点}
\label{sec:ch7-production-english}

生产差距是最强的跨平台主题：在演示中令人信服的系统在真实运营约束下失败。生产施加了基准测试很少测量的要求。智能体必须满足延迟预算、控制成本、处理格式错误的输入、遵守权限、保留数据边界、与现有系统集成、在依赖更新后存活、暴露遥测、支持事件响应并提供可预测的失败模式。

一个主要的生产痛点是成本不透明性。多步骤智能体可以通过规划、工具选择、反思、验证、重试和摘要成倍增加模型调用。多智能体系统通过添加管理者、工作者、批评者、审查者和评判者角色再次倍增。自进化通过生成变体、测试候选者和保留归档进一步倍增。用户报告对失控循环和意外账单的恐惧，因为系统不知道探索何时已停止产生价值。

另一个生产痛点是人工劳动替代与人工劳动转移。智能体可能自动化初稿或简单任务，但劳动以监控、提示修复、数据清理、评估设计和手动验证的形式重新出现。基准测试可能计算已解决的任务，但忽略决定解决方案是否安全所花费的人工时间。这就是为什么用户要求会话级评估而非仅最终答案准确率。监督成本是系统的一部分。

部署还需要组织适配。自进化智能体不能被视为孤立的模型。它成为变更管理的一部分。谁批准记忆更新？谁审查自修改的提示？谁拥有失败的工具调用？谁可以暂停智能体？保留什么日志？可以存储什么数据？哪些操作需要人工批准？这些问题很平凡，但它们决定智能体能否在企业中部署。

因此，从演示到生产的路径应该是分阶段的。第一阶段是使用冻结数据和明确指标的离线实验。第二阶段是影子模式，智能体提议行动但人类执行或拒绝。第三阶段是在低风险任务上的有限自主性，有严格预算。第四阶段是有回滚和事件响应的监控自主性。第五阶段是选择性自进化，仅低风险组件可以自动更新，高风险变更需要审查。语料库表明许多失败发生在团队从第一阶段直接跳到第四阶段时，没有构建中间控制。

\subsubsection{框架差距分析}
\label{sec:ch7-framework-gap-english}

框架投诉是最清晰的 Mom Test 信号之一，因为用户经常通过迁移揭示偏好。当开发者在尝试后移除一个框架时，痛点不是理论性的。语料库识别出五个框架差距：透明性、状态管理、部署简易性、评估集成和治理。

透明性意味着提示、模型输入、工具载荷、记忆检索和输出必须可检查。将提示隐藏在链或角色抽象之后的框架使调试和审计行为变得困难。状态管理意味着长时间运行的工作流需要显式的、类型化的、可重放的状态而非隐式对话历史。部署简易性意味着框架不应为简单工作流需要重度依赖、不明确的运行时假设或脆弱的插件栈。评估集成意味着测试、追踪和回归套件应是一等组件。治理意味着权限、预算、审批和回滚应内置在框架中而非事后附加。

框架差距部分源于演示人机工程学与生产人机工程学之间的不匹配。演示框架优化快速构建：定义角色、添加工具、运行任务。生产框架必须优化检查：发生了什么、为什么、在什么版本下、以什么成本、带有什麽风险。使第一个演示容易但第十个事件处理困难的框架将被抛弃。

多智能体抽象值得特别谨慎。团队隐喻直观，但可能隐藏成本和可靠性问题。多个智能体可能产生更丰富的审议，但也可能放大幻觉、趋同于共同错误或在协商上花费 token 而不增加证据。因此，多智能体框架应该用独立信息源、评估器或责任边界来证明每个角色的合理性。否则，角色增殖只是昂贵的采样。

一个有用的自进化框架会将进化循环暴露为受控流水线：候选生成、评估、选择、持久化、回滚和审计。它会使每个持久产物可见：提示、记忆、技能、工具、测试、策略和评估器。它允许本地实验同时防止未经审查的全局变更。它将可观测性和治理视为产品功能，而非企业事后补充。

\subsubsection{数据驱动的痛点量化}
\label{sec:ch7-quantification-english}

语料库级别的计数为定性分析提供了定量骨架。在131篇分析帖子中，本地 Mom Test 摘要提取了97个独立痛点。平台分布为 Reddit 47个痛点、Hacker News 36个痛点和 X/Twitter 14个痛点。按计数排名靠前的类别是生产环境中的智能体可靠性、自改进可行性、框架/工具缺陷、知识与记忆持久化、评估与基准测试和安全/成本治理。这些类别占观察到摩擦的大部分。

量化应谨慎解读。语料库不是所有用户的随机样本。它过度代表技术参与社区和有动力发布成功或失败的人。但这种偏差对早期技术领域有用：高级用户往往在主流用户之前遇到生产失败模式。他们的投诉是领先指标。

最重要的定量结果是痛点围绕运营信任的集中。可靠性、自改进可行性、记忆持久化、评估和安全/成本不是独立问题。它们是一个信任栈的组成部分。如果智能体不可预测地失败，它不被信任。如果它不能解释或从失败中改进，它不被信任。如果记忆缺失或不安全，它不被信任。如果基准测试可以被操控，它不被信任。如果成本和权限不受控制，它不被信任。因此，孤立地解决任何一个类别都不够。

第二个定量观察是框架/工具投诉几乎与算法投诉一样频繁。这对研究策略很重要。更好的自改进算法不会自动转化为采用率，如果开发者无法观察、测试、部署和治理它们。反之，强框架中适度的算法可能比不透明研究原型中复杂的算法创造更多实际价值。

第三个观察是低频类别仍可能是高优先级。误进化出现频率低于可靠性，但其严重度是关键的，因为它描述了动态的、持久的和潜在复合的故障。企业治理作为小计数出现，但任何大规模部署智能体的组织最终都需要它。计数识别痛苦常见之处；严重度识别痛苦致命之处。

\subsubsection{对智能体自进化研究的启示}
\label{sec:ch7-research-implications-english}

痛点证据以五种方式改变了研究议程。第一，可靠性必须进行纵向评估。一次性基准分数对于声称能学习的系统是不够的。研究者应报告跨重复会话、环境变化、记忆更新和回归套件的性能。第二，反馈质量应被视为一等变量。没有可靠反馈的自改进仅仅是自修改。第三，记忆应作为进化数据库评估，而非更长的提示。它需要来源追踪、冲突解决、压缩、遗忘和投毒防御。

第四，成本应成为每个方法声明的一部分。一个通过增加十倍调用来提高成功率的方法可能在研究中有用但在生产中不可接受。报告应包括 token 成本、工具调用成本、挂钟时间、失败候选比率和人工审查时间。第五，安全必须集成到循环中。事后沙箱不够，如果智能体可以将不安全教训写入记忆或削弱自己的评估器。循环本身必须设计有权限、门控和回滚。

痛点还表明哪些研究方向可能具有高实际影响。验证器构建是核心，因为许多自改进循环在没有可信反馈时停滞。会话级评估是核心，因为用户关心完整工作流而非孤立答案。记忆治理是核心，因为跨会话学习是最被请求的能力之一，也是朴素实现中最危险的能力之一。框架可观测性是核心，因为隐藏的提示和状态阻止采用。成本感知搜索是核心，因为开放式进化否则可能变得经济上不合理。

\subsubsection{对 Awesome-Evolution 资源项目的启示}
\label{sec:ch7-awesome-evolution-implications-english}

对于 Awesome-Evolution 项目，痛点语料库意味着有用的资源不应仅仅赞颂新论文和仓库。它应该按生产问题分类资源。一个提供基准提升的仓库应标记其评估器类型、成本概况和安全边界。一个框架应标记提示是否可见、状态是否可重放、工具是否被记录、记忆是否有版本、回滚是否存在。一篇论文应标记改进是推理时、训练时、基于记忆的、基于自博弈的还是代码修改的。

项目还应展示负面证据。用户不仅需要知道哪些系统有效，还需要知道它们在哪里失败。一个成熟的资源可以包含痛点徽章：生产可靠性、记忆治理、评估独立性、成本控制、框架透明性、安全边界和部署证明。它可以分离研究原型和生产案例研究。它可以维护基准注意事项和已知污染风险列表。它可以将每个自进化机制链接到所需的安全保障。

最有价值的实用产物可能是自进化智能体部署检查清单。在采用系统之前，团队应问：什么随时间变化？谁或什么评估变更？评估器可以被操控吗？是否有隐藏测试或独立门控？成本预算是多少？什么被存储在记忆中？记忆可以被检查和删除吗？智能体有什么权限？循环失败时会发生什么？如何执行回滚？谁批准高风险变更？如果项目无法回答这些问题，无论其演示多么令人印象深刻，它都不是生产就绪的。

\subsubsection{结论：痛点作为设计需求}
\label{sec:ch7-conclusion-english}

Mom Test 证据将用户挫败转化为设计需求。生产可靠性需要鲁棒的错误恢复，而非仅仅是更好的提示。自改进可行性需要有根据的反馈和独立评估，而非仅仅是反思。框架有用性需要可观测性，不仅仅是抽象。基准可信度需要隐藏、动态、过程感知的评估，而非仅仅是公开排行榜。记忆持久性需要治理，而非更大的上下文窗口。安全需要权限、沙箱、预算和回滚，而非仅仅是事后警告。

这些需求不矛盾于智能体自进化的承诺。它们定义了该承诺可以变为现实的条件。该领域已经表明智能体可以修正输出、存储教训、在过滤推理上训练、生成任务和在程序上搜索。痛点语料库表明在信任这些机制之前需要添加什么：运营指标、透明框架、评估器独立性、记忆谱系、成本控制和高风险变更的人工治理。

简言之，从演示到生产的路径不仅仅是扩展自主性。它是使自主性可观测、有界和可逆。智能体进化只有在每个改进循环都配对问责循环时才能在实践中成功：接受变更的原因证据、变更了什么的记录、旧能力完好的测试，以及当进化出错时停止或回滚系统的机制。

\subsubsection{从痛点语料库推导的操作检查清单}
\label{sec:ch7-operational-checklist-english}

以下检查清单总结了自进化智能体项目在呈现为生产就绪之前应提供的最低证据。它刻意实用，因为 Mom Test 语料库表明用户不是被术语缺失阻碍；他们被缺失的操作答案阻碍。

\begin{enumerate}[nosep]
\item \textbf{可变对象}：说明系统是否更改提示、记忆、工具、代码、数据集、权重、工作流或评估器。
\item \textbf{反馈来源}：说明接受是基于自我判断、同伴判断、奖励模型、程序化验证器、隐藏测试还是人工审查。
\item \textbf{可追溯性}：记录确切的提示、检索的上下文、工具载荷、模型输出、评估器输入、评估器输出和选定的更新。
\item \textbf{预算控制}：定义每个任务和每个进化周期的最大 token 数、工具调用数、挂钟时间、重试次数和美元成本。
\item \textbf{记忆治理}：为每个持久记忆项记录来源，并提供删除、过期、冲突解决和隔离功能。
\item \textbf{回归保护}：在接受任何持久变更之前运行旧任务套件。
\item \textbf{安全边界}：将外部内容隔离为数据，限制工具权限，高风险操作需要审批。
\item \textbf{回滚}：保留提示、记忆、工具、代码和评估器的祖先状态。
\item \textbf{人工升级}：定义智能体何时必须停止并请求审查而非继续自主操作。
\item \textbf{负面结果报告}：报告失败候选、被拒绝的更新、成本峰值、回归和安全触发。
\end{enumerate}

此检查清单不是新算法的替代品。它是让算法在用户描述的部署环境中存活的桥梁。本章的核心教训是痛点不是边缘投诉；它们是下一代智能体进化基础设施的规格说明。

\subsubsection{附加扩展分析：从痛点到评估需求}
\label{sec:ch7-additional-evaluation-requirements}

本节深化用户痛点与自进化智能体所需评估架构之间的联系。

Mom Test 语料库的核心教训是评估必须测量用户在智能体周围实际执行的工作。标准基准通常测量答案是否正确、程序是否通过测试或最终输出是否获得更高分数。然而，用户体验的是整个会话。他们为澄清、重试、上下文收集、工具配置、等待、检查、撤销和解释付费。一个在许多隐藏尝试后解决基准项的系统，如果运营循环缓慢、昂贵且不透明，仍然可能是糟糕的产品。

这激发了会话级评估模型。设会话 $\sigma$ 包含模型调用、工具调用、记忆读取、记忆写入、评估器决策、用户干预和最终结果：
\[
  \sigma = (m_{1:n}, t_{1:k}, r_{1:p}, w_{1:q}, e_{1:s}, h_{1:u}, y).
\]
其中 $m$ 为模型交互，$t$ 为工具调用，$r$ 为检索的记忆，$w$ 为记忆写入，$e$ 为评估器事件，$h$ 为人工干预，$y$ 为最终交付物。生产指标应评分整个会话：
\[
  U(\sigma)=\alpha S(y)-\beta C(\sigma)-\gamma H(\sigma)-\delta R(\sigma),
\]
其中 $S$ 为任务成功度，$C$ 为计算和工具成本，$H$ 为人工干预负担，$R$ 为风险或策略违规。这个公式反映了痛点证据：用户拒绝在提高最终答案质量的同时增加成本、隐性劳动或风险的系统。

同一模型适用于自进化。提议的更新不应仅仅因为它改善了局部基准而被接受。它应该改善真实工作负载下的期望会话效用。如果一个记忆更新减少了重试但增加了幻觉性自信，它是模糊的。如果一个框架抽象缩短了代码但隐藏了提示载荷，它可能减少开发工作量同时增加事件响应成本。如果一个自博弈课程改进了 HumanEval 但在真实仓库上失败，它优化了不完整的效用函数。因此痛点语料库要求多目标评估。

\subsubsection{记忆作为产品痛点，不仅是研究模块}
\label{sec:ch7-memory-product-pain}

语料库中的记忆投诉值得特别强调，因为记忆经常被呈现为智能体进化的显而易见的解决方案。用户希望智能体记住项目约定、之前的失败、个人偏好、组织策略和成功流程。然而同样的用户害怕过时上下文、被污染的技能、不相关的检索、隐私泄漏和不受控制的提示增长。这种双重性使记忆成为智能体进化中最难的产品问题之一。

一个产品质量的记忆系统必须回答五个问题。第一，什么被允许进入记忆？原始转录、压缩教训、验证的事实、用户偏好和生成的工具有不同的风险级别。第二，谁或什么验证记忆？一个自生成的教训不应自动成为可信规则。第三，如何检索记忆？仅靠相似性搜索可能返回看似合理但不相关的教训。第四，记忆如何被遗忘？旧API、已更改的策略和临时用户偏好必须过期。第五，记忆如何被审计？用户和管理员需要检查、编辑、导出或删除持久知识。

痛点证据建议以下生命周期：
\[
  \text{观察} \rightarrow \text{候选教训} \rightarrow \text{隔离} \rightarrow \text{已验证记忆} \rightarrow \text{检索的建议} \rightarrow \text{结果审计} \rightarrow \text{提升或删除}.
\]
此生命周期防止单次失败成为永久策略。它还使记忆可测量：记忆项应在检索改善结果时获得积分，在检索导致错误时被降级。

记忆还与成本交互。朴素方法存储一切并检索过多，增加 token 和混淆。更严格的方法仅存储高置信度教训，但可能遗漏有用的隐性知识。生产系统因此应测量记忆投资回报：
\[
  \mathrm{MemoryROI} = \frac{\Delta S - \lambda \Delta R}{\Delta C_{\mathrm{storage}} + \Delta C_{\mathrm{retrieval}} + \Delta C_{\mathrm{review}}}.
\]
其中 $\Delta S$ 为成功改进，$\Delta R$ 为额外风险，分母包括存储、检索和人工审查成本。这是许多演示中缺失的运营指标类型。

\subsubsection{隐性劳动问题}
\label{sec:ch7-hidden-labor}

多个痛点可以统一为隐性劳动。智能体看似自动化工作，但人类仍执行不可见的支持任务：设计提示、检查输出、编写粘合代码、构建评估数据、管理记忆、管理成本、调试追踪和修复故障。如果一项研究报告智能体解决了任务但忽略了这种隐性劳动，它就夸大了自动化程度。

隐性劳动与自改进尤其相关。声称的自主反馈循环可能依赖人工检查每次失败、决定提议的修复是否有效、更新提示、批准记忆写入或在漂移后重置系统。在这种情况下，系统在生产意义上不是自改进的；它是借助 LLM 辅助的人工改进。这可能仍有价值，但应准确命名。

一个有用的报告指标是人工干预率：
\[
  \mathrm{HIR}=\frac{\#\text{需要人工纠正或批准的会话}}{\#\text{总会话数}}.
\]
另一个是人工节省分钟数：
\[
  \mathrm{NetTimeSaved}=T_{\mathrm{manual}}-(T_{\mathrm{agent\_run}}+T_{\mathrm{review}}+T_{\mathrm{debug}}+T_{\mathrm{maintenance}}).
\]
许多在最终输出指标下看起来有用的系统，在净节省时间下可能看起来较弱。Mom Test 语料库表明从业者隐含地计算这个数量，当他们放弃框架或限制智能体到狭窄任务时。

\subsubsection{故障恢复作为核心产品功能}
\label{sec:ch7-failure-recovery}

语料库中一个引人注目的模式是用户不期望智能体完美。他们期望智能体以可恢复的方式失败。挫败感来自智能体静默失败、编造成功、循环、丢失状态或要求用户诊断整个问题。因此故障恢复应被视为核心产品功能。

一个可恢复的故障有五个属性：被检测、被定位、被解释、有界和可逆。检测意味着系统知道出了问题。定位意味着它可以识别可能的组件：提示、工具、记忆、检索、模型、评估器或环境。解释意味着它可以以人或未来智能体可用的方式总结故障。有界意味着它在消耗无限资源或造成损害之前停止。可逆意味着系统可以返回已知安全状态。

自进化如果存储已验证的故障教训并从中构建新测试，可以改善故障恢复。如果它存储错误解释或在没有可追溯性的情况下修改自身，则可能恶化故障恢复。区别在于治理。一个故障应产生候选教训、候选测试，或许还有候选补丁，但每个产物应有验证路径。故障驱动的进化仅在故障证据与更新保持关联时才有用。

\subsubsection{无冲突协作的框架需求}
\label{sec:ch7-conflict-free-collaboration}

促成此次恢复工作的文件覆盖事件本身就是一个更广泛智能体痛点的例子：自主工作者需要围绕共享状态的协调协议。在软件团队中，共享文件受版本控制、代码审查、锁、合并和冲突解决保护。多智能体写作或编码系统需要等效的安全保障。没有它们，并行智能体即使在各自看起来遵循本地任务的情况下，也可能覆盖彼此的工作。

团队采用的新规则——将扩展内容写入单独文件并稍后合并——是一个简单但强大的协调模式。它将高冲突的共享文件编辑转换为低冲突的产物生成。同样的模式可以泛化到智能体框架。智能体在工作可以暂存为候选产物时应避免直接变更共享生产状态。候选提示、候选记忆更新、候选代码补丁、候选报告和候选评估器变更应由协调器或自动化门控合并。

智能体的无冲突协作协议应包括：写入目标的显式所有权；写入前的文件大小或内容哈希检查；共享笔记的仅追加日志；大型重写的独立候选文件；合并权限分配给协调器；以及自动检测较小文件替换较大文件的情况。痛点语料库抱怨框架不透明和状态管理；覆盖事件证明了这些抱怨为何重要。自主系统需要共享状态纪律。

\subsubsection{从第7章综合的设计原则}
\label{sec:ch7-design-principles}

重建的本章可以总结为十条设计原则：

\begin{enumerate}[nosep]
\item 优化会话效用，而非孤立的最终答案。
\item 只要可用，优先使用外部证据而非自我判断。
\item 将记忆视为受治理的状态，而非无限转录。
\item 使提示、工具、状态和评估器决策可检查。
\item 将成本和人工干预作为一等结果测量。
\item 保持自修改是分阶段的、可审查的和可逆的。
\item 使用基准作为一层证据，而非生产证明。
\item 在扩展自主性之前设计故障恢复。
\item 避免没有所有权和合并协议的共享状态变更。
\item 报告负面结果、被拒绝的更新、回归和成本峰值。
\end{enumerate}

这些原则将社区痛苦转化为工程议程。它们也阐明了为什么智能体自进化仍然有前景。造成风险的相同循环——记忆、反思、自修改、验证器引导的搜索——如果嵌入透明和可逆的基础设施中，可以变得可靠。该领域的任务不是在自主性和控制之间选择，而是设计携带自身证据链的自主性。

\subsubsection{将痛点映射到五个进化循环}
\label{sec:ch7-painpoints-to-loops}

本文其他地方使用的五循环框架也有助于解读用户痛点。在规格到执行循环中，用户抱怨智能体将模糊目标翻译为错误计划、忽略约束或编造工具能力。需求是更强的规格捕获：类型化输入、显式假设、澄清问题和可执行的验收标准。在搜索循环中，用户抱怨提示优化空间过大、进化系统扔很多候选到问题上而不解释为什么候选更好。需求是有成本感知的搜索，带有多样性控制和有意义的停止标准。

在评估器循环中，用户抱怨最为激烈。他们观察到基准操控、循环自评估、伪造测试日志和古德哈特效应。需求是评估器独立性：隐藏测试、外部工具、必要时盲审人工审查和评估器版本化。在反思循环中，用户抱怨反思增加了延迟但不解决边界情况，或错误反思导致漂移。需求是基于证据的反思和记忆隔离。在种群循环中，用户抱怨维护许多变体的成本和治理复杂性。需求是谱系管理：每个变体应有祖先、变异描述、评估记录、成本和回滚路径。

\subsubsection{什么算作生产证明？}
\label{sec:ch7-production-proof}

语料库反复要求生产证明。研究原型可能展示基准提升；生产证明必须展示系统在运营约束下工作。对于自进化智能体，生产证明应至少包含六种形式的证据。

第一，应包含时间跨度。运行一次演示的系统与跨变化任务运行数周的系统不同。第二，应包含工作负载多样性。系统应处理常规、边界情况和对抗性输入。第三，应包含干预数据：人类需要纠正、批准或救援智能体的频率。第四，应包含成本数据：平均、尾部和最差情况支出。第五，应包含事件数据：安全触发、回滚、失败更新和回归。第六，应包含版本数据：随时间变化了什么以及为什么。

一个简洁的生产证明报告可能包含：
\[
  (T, N, S, C_{avg}, C_{p95}, HIR, IR, RR, \Delta_{regression}, L),
\]
其中 $T$ 为部署持续时间，$N$ 为会话数，$S$ 为成功率，$C$ 为成本，$HIR$ 为人工干预率，$IR$ 为事件率，$RR$ 为回滚率，$\Delta_{regression}$ 为旧任务回归，$L$ 为谱系完整性。这个元组可以回答用户目前非正式提出的许多问题。

生产证明也应是领域特定的。编码智能体需要仓库级 CI 证据。客户支持智能体需要策略合规和升级证据。研究智能体需要引用准确性和新颖性审查。工作流智能体需要集成可靠性和权限审计。关于``智能体能力''的通用声明过于宽泛，无法满足真实买家或工程团队。

\subsubsection{最终重建总结}
\label{sec:ch7-final-rebuild-summary}

仅追加的重建恢复了本章在论文中的功能。它展示了用户痛点语料库不仅仅是轶事色彩；它是结构化的实证对抗力量，平衡算法乐观主义。语料库识别了在信任自进化智能体之前必须满足的条件：可靠会话、可检查框架、受治理记忆、独立评估、受控成本、安全权限、回滚和生产证明。

启示是具体的。研究论文应报告反馈来源、评估器独立性、成本、回归和失败候选。框架应将提示、状态、工具和记忆暴露为可审计产物。产品团队应逐步部署自主性，带有预算和人工升级。基准设计者应评估过程和长期行为，而非仅最终答案。开源资源应按安全保障分类项目，而非仅按星标数或声称的基准改进。

如果忽略这些需求，自进化将仍然是令人印象深刻的演示后随之放弃的循环。如果实施这些需求，让用户担忧的相同机制——反思、记忆、自博弈、架构搜索和代码修改——可以成为持续改进的实用工具。因此本章的最终信息是谨慎建设性的：用户不是在拒绝智能体进化；他们是在指定使其成为现实所需的缺失基础设施。
