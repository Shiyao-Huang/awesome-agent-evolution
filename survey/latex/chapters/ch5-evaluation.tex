\section{Evaluation Systems and Benchmarks}
\label{ch:evaluation}

\subsection{The Evaluation Challenge in Agent Self-Evolution}
\label{sec:eval-challenge}

The central tension in agent self-evolution research lies between a system's claim of improvement and our ability to verify that improvement is genuine, robust, and transferable. Evaluation is not merely the experimental section of a paper---it serves as the \emph{selection pressure} that shapes the direction of evolution and the \emph{safety gate} that prevents harmful mutations from propagating. If the evaluation function is misaligned, incomplete, or gameable, then self-evolution becomes self-deception.

This chapter addresses the evaluation problem from three perspectives. First, we propose a five-layer evaluation hierarchy that spans fully automated programmatic verification at the bottom to human-in-the-loop safety gates at the top. Second, we survey the major benchmarks used across the agent evolution literature, analyzing their strengths, limitations, and contamination risks. Third, we introduce agent-specific evaluation metrics that go beyond single-task accuracy to capture iterative improvement, transfer, cost efficiency, and safety. Throughout, we emphasize that evaluation infrastructure is itself evolving: as agents become more capable, evaluators must become more sophisticated, or risk being outpaced by the systems they are meant to assess.

The evaluation challenge is particularly acute for self-evolving systems because of four properties that distinguish them from conventional machine learning. First, the improvement target is moving: an agent that modifies its own code, prompts, or memory may change its behavior in ways that the benchmark did not anticipate. Second, the evaluation is part of the optimization loop: agents can learn to exploit evaluator weaknesses, producing reward hacking, length bias, or score manipulation that inflates metrics without genuine capability gain. Third, the scope of evaluation must expand beyond task completion to include process quality, cost, safety, and transfer---dimensions that are harder to quantify than accuracy. Fourth, reproducibility is threatened by non-determinism in LLM generation, API version changes, and the interaction between stochastic sampling and evolving agent state.

These properties mean that a single benchmark score is never sufficient evidence for self-evolution. A credible evaluation must include multi-layer verification, cross-benchmark generalization, cost analysis, safety auditing, and ablation studies that isolate the contribution of the self-improvement mechanism from confounds such as prompt engineering, model selection, and data contamination.


\subsection{A Five-Layer Evaluation Hierarchy}
\label{sec:eval-hierarchy}

We propose organizing evaluation methods into five layers, from fully automated to human-supervised. Each layer adds reliability at the cost of increased effort and latency. A well-designed evaluation system uses all five layers in combination, with lower layers providing rapid feedback during development and higher layers serving as pre-deployment gates.

\subsubsection{L1: Programmatic Verification}
\label{sec:eval-L1}

The most reliable evaluation signals come from deterministic programmatic checks. These include unit tests, type checking, static analysis, linting, fuzzing, regression testing, and sandbox execution. Their key advantage is that they are fully automated, reproducible, and cannot be gamed by an LLM that understands the evaluation format---assuming the test suite itself is not accessible to the agent.

In the agent evolution literature, systems like DGM~\citep{dgm2025}, SICA~\citep{sica2025}, EvoMAC~\citep{evomac2024}, and AlphaEvolve~\citep{alphaevolve2025} achieve self-evolution precisely because candidate code can be automatically executed and scored. DGM evaluates agent variants by running them on SWE-Bench tasks and measuring the percentage of tests passed; SICA allows the coding agent to modify its own source code and validates changes against a held-out test suite; AlphaEvolve uses programmatic evaluators to score algorithm candidates on mathematical optimization problems.

The scope of programmatic verification should be expanded beyond code tasks. Data pipelines can verify schema compliance, distribution drift, and end-to-end consistency. Business processes can verify state machine constraints and permission policies. Web tasks can verify DOM state, backend responses, and user intent fulfillment. Robotic tasks can verify physical constraints and safety boundaries. Programmatic verifiers do not need to understand full semantics, but they must cover the critical failure modes of the target domain.

A key challenge is test coverage: a test suite that passes may simply be incomplete. Self-evolving agents can learn to satisfy the visible tests while introducing subtle regressions in untested behaviors. This motivates the use of mutation testing (injecting deliberate bugs to check whether tests catch them), fuzzing (generating random inputs to stress-test edge cases), and invariant checking (verifying properties that should hold across all executions, such as ``no file is written outside the designated directory'').


\subsubsection{L2: Code and Reasoning Benchmarks}
\label{sec:eval-L2}

Code generation and mathematical reasoning benchmarks provide standardized, widely-recognized evaluation signals. Their primary advantage is comparability: results can be directly compared across papers and systems, enabling the community to track progress over time.

For code generation, HumanEval~\citep{chen2021codex} and MBPP~\citep{austin2021mbpp} remain the most widely used benchmarks. HumanEval consists of 164 Python programming problems with unit tests, measuring functional correctness via pass@$k$ metrics. MBPP provides 974 crowd-sourced problems with test cases. These benchmarks are low-cost, easy to reproduce, and have established baselines across many systems. Reflexion~\citep{reflexion2023}, Self-Refine~\citep{selfrefine2023}, and EvoMAC~\citep{evomac2024} all report HumanEval results, making cross-system comparison possible.

For mathematical reasoning, GSM8K~\citep{cobbe2021gsm8k} provides 8,500 grade-school math problems with step-by-step solutions, MATH~\citep{hendrycks2021math} offers 12,500 competition-level problems across seven difficulty levels, and GPQA~\citep{rein2024gpqa} presents expert-level questions in physics, chemistry, and biology that challenge even PhD-level human experts. STaR~\citep{star2022}, RISE~\citep{rise2024}, and SPIRAL~\citep{spiral2025} use these benchmarks to demonstrate self-improvement in reasoning.

However, these benchmarks suffer from well-documented limitations. First, many are static problem sets with fixed answers, making them vulnerable to data contamination---models may have seen the problems during training, inflating scores without genuine capability. Second, they measure only final-answer correctness, not the quality of the reasoning process, the robustness of tool use, or the ability to handle multi-step interactions. Third, their granularity is small: passing a unit test on a 10-line function is fundamentally different from successfully patching a real codebase with millions of lines.

MMLU~\citep{hendrycks2021mmlu} and its successors (MMLU-Pro, GPQA) assess knowledge and reasoning across 57 academic subjects. While useful as a general capability proxy, they are static, multiple-choice, and do not measure agent-specific skills like tool use, memory management, or multi-turn planning.


\subsubsection{L3: Environment Interaction Benchmarks}
\label{sec:eval-L3}

Environment interaction benchmarks evaluate agents in simulated or real environments where success requires multi-step planning, tool use, error recovery, and state tracking. These benchmarks are closer to real-world deployment scenarios and are less susceptible to memorization-based contamination.

SWE-Bench~\citep{jimenez2024swebench} is currently the most important benchmark for evaluating code agents in realistic software engineering tasks. It requires systems to locate issues in real open-source repositories, modify code, run tests, and submit verifiable patches. SWE-Bench Verified (500 human-validated instances) and SWE-Bench Lite (300 lighter instances) provide standardized subsets. DGM~\citep{dgm2025} and SICA~\citep{sica2025} use SWE-Bench to demonstrate that ``self-modifying codebases'' can achieve real improvements over static agents.

WebArena~\citep{zhou2024webarena} creates realistic web-based tasks that require navigating websites, filling forms, and extracting information. ALFWorld~\citep{shridhar2021alfworld} tests embodied agents in text-based household environments. AppWorld~\citep{trivedi2024appworld} provides a sandboxed environment for evaluating agents on real-world app interactions. These multi-step environments are particularly effective at exposing failure modes such as context window collapse, memory distortion, and inability to recover from errors.

Voyager~\citep{voyager2023} uses a unique evaluation approach in Minecraft: rather than testing against fixed tasks, it measures the number of unique items discovered, technology tree nodes unlocked, and the ability to transfer skills to new worlds. This ``lifelong learning'' evaluation is closer to how self-evolving agents would be assessed in production: not by a single test score, but by cumulative capability growth over time.

The primary limitation of environment benchmarks is cost: setting up the infrastructure, managing state, and ensuring reproducibility requires significant engineering effort. They also tend to be domain-specific, making cross-domain comparison difficult.


\subsubsection{L4: Process Metrics}
\label{sec:eval-L4}

Process metrics go beyond task completion to evaluate \emph{how} improvement occurs. These metrics are essential for distinguishing genuine self-evolution from one-time prompt optimization or cherry-picked results.

\textbf{Iterative Improvement Curves.} The most fundamental process metric is the trajectory of performance across evolution iterations. A system that monotonically improves over many rounds on diverse tasks demonstrates more robust self-evolution than one that jumps to a high score on a single attempt. The shape of the curve matters: stable, gradual improvement suggests reliable learning mechanisms, while volatile or plateauing curves may indicate that the system is optimizing for evaluator-specific features rather than genuine capability. DGM's archive-based evolution produces smoother improvement curves than single-shot approaches because it retains diverse stepping stones.

\textbf{Transfer and Generalization.} Improvement that transfers across tasks, models, environments, or domains is far more valuable than improvement on a single benchmark. ADAS~\citep{adas2024} demonstrates that agent designs discovered on one set of tasks can transfer to different models and domains. Voyager's skill library enables transfer across Minecraft worlds with different biomes and objectives. ReasoningBank~\citep{reasoningbank2025} distills reasoning strategies from successful and failed examples for use on new problems. Transfer evaluation requires explicitly testing on held-out tasks, environments, or models that were not used during the evolution process.

\textbf{Archive Diversity.} In population-based evolution systems, the diversity of the archive or candidate pool is a critical metric. An archive that converges to near-identical variants has lost its evolutionary potential; a healthy archive maintains diverse strategies, some of which may become stepping stones for future breakthroughs. DGM's key insight is that maintaining a growing archive of agent variants---including ones that are not currently top-performing---enables open-ended exploration and avoids local optima.

\textbf{Rollback Rate.} The frequency with which a self-evolving system must roll back to a previous version is a direct measure of evolution reliability. High rollback rates indicate that the mutation-selection process is insufficiently conservative, producing variants that pass initial evaluation but fail under broader testing. Systems with low rollback rates typically employ multi-gate evaluation: candidates must pass programmatic tests, benchmark evaluations, safety checks, and regression suites before being accepted.


\subsubsection{L5: Safety and Cost Gates}
\label{sec:eval-L5}

The highest layer of evaluation addresses the question: ``Was the improvement achieved at an acceptable cost and risk?'' This layer is often neglected in academic papers but is essential for production deployment.

\textbf{Permission Verification.} Self-evolving agents must operate within strict permission boundaries. Every candidate variant should undergo permission checks that verify it does not access resources beyond its authorized scope, modify files outside designated directories, make network requests to unauthorized endpoints, or escalate privileges. Self-modifying agents like G\"{o}del Agent~\citep{godelagent2024} and SICA~\citep{sica2025} are particularly sensitive to this concern because their modifications can alter their own permission logic.

\textbf{Cost Accounting.} The cost of self-evolution must be measured and bounded. Key metrics include API calls per improvement iteration, token consumption per unit of performance gain, wall-clock time from initial state to target performance, dollar cost per successful task completion, and human intervention frequency. Without cost constraints, self-evolution systems can produce impressive results by brute-force exploration that is economically unsustainable. Cost should be part of the fitness function, not an afterthought.

\textbf{Regression Testing.} Every evolved variant should be tested against a regression suite that verifies core capabilities are preserved. Self-evolution can produce negative transfer: optimizing for new tasks may degrade performance on existing ones. Regression testing prevents ``improvement'' that is actually capability displacement.

\textbf{Human Audit.} For high-stakes applications, human review of evolved variants remains essential. This includes inspecting code changes, reviewing reasoning traces, verifying that safety constraints are maintained, and assessing whether the improvement is qualitatively meaningful or merely exploits evaluator quirks. Human audit is expensive but provides the final safety net that automated systems cannot fully replace.


\subsection{Benchmark Deep Dive: Software Engineering}
\label{sec:eval-swe}

Software engineering benchmarks occupy a privileged position in the agent evolution landscape because they combine three properties that are rare in other domains: (1) tasks are grounded in real-world codebases with real bugs, (2) correctness can be verified automatically by running test suites, and (3) the evaluation signal is binary and unambiguous---either the patch passes all tests or it does not. These properties make software engineering the most reliable testbed for self-evolution research, and the benchmarks in this category are correspondingly the most informative.

\subsubsection{SWE-Bench: The Gold Standard for Code Agents}

SWE-Bench~\citep{jimenez2024swebench} has become the de facto standard for evaluating code agents in realistic software engineering scenarios. Each task presents a real GitHub issue from a popular open-source Python repository, along with the repository state at the time the issue was filed. The agent must understand the issue description, locate the relevant code, implement a fix, and submit a patch that passes the repository's test suite.

SWE-Bench Verified~\citep{alexander2024swebenchverified} is a subset of 500 tasks where human annotators have confirmed that the task description is sufficient to identify and resolve the issue. This addresses a significant problem in the original SWE-Bench: some tasks have ambiguous or incomplete issue descriptions that make it impossible to determine the correct solution from the text alone. SWE-Bench Lite provides 300 lighter tasks for faster evaluation cycles.

DGM~\citep{dgm2025} reports state-of-the-art results on SWE-Bench by maintaining an archive of agent variants that modify their own code. Starting from a baseline of approximately 20\% resolved rate on SWE-Bench Verified, DGM's self-evolution process improves to over 40\% after several iterations, demonstrating that the agent's self-modification capability produces genuine improvements on real-world tasks. Importantly, DGM's improvements transfer across models: agent designs evolved with one base model show improvements when applied to different models.

SICA~\citep{sica2025} takes a different approach: the coding agent directly edits its own source code to improve performance on SWE-Bench Verified. SICA demonstrates that self-modifying agents can discover improvements that human engineers might not anticipate, such as adding debugging steps, improving error message parsing, or restructuring the code navigation strategy. However, SICA's results also highlight the risk of overfitting: improvements on SWE-Bench tasks do not always transfer to other code tasks.


\subsubsection{HumanEval and Code Generation Benchmarks}

HumanEval~\citep{chen2021codex} and MBPP~\citep{austin2021mbpp} have served as the entry point for evaluating code generation agents since 2021. Their simplicity and reproducibility make them ideal for rapid iteration during development, but their limitations must be understood to avoid over-interpreting results.

The original HumanEval benchmark contains 164 programming problems, each specifying a Python function with a docstring and unit tests. The evaluation metric pass@$k$ measures the probability that at least one of $k$ independently generated solutions passes all unit tests. This metric is well-defined and reproducible, but it measures only functional correctness on small, self-contained problems---a fundamentally different challenge from real-world software engineering.

The relationship between HumanEval performance and practical coding ability is nuanced. Reflexion's 91\% pass@1 on HumanEval using GPT-3.5-turbo is impressive, but it does not imply that Reflexion can handle the complexity of real codebases with dependencies, build systems, configuration files, and cross-module interactions. HumanEval problems typically require writing 5--15 lines of code; SWE-Bench tasks require understanding and modifying codebases with thousands of files. The gap between these two evaluation regimes is one of the most important open problems in agent evaluation.

To address HumanEval's limitations, the community has developed several extensions. HumanEval+ generates novel problems with similar structural properties, reducing contamination risk. LiveCodeBench~\citep{livecodebench2024} provides continuously updated problems sourced from competitive programming platforms, ensuring that models cannot memorize the evaluation set. MBPP provides a larger set of crowd-sourced problems with different difficulty characteristics. These extensions help, but the fundamental limitation remains: code generation benchmarks evaluate the ability to write small, isolated functions, not to engineer complex software systems.

The contamination risk for code generation benchmarks is particularly high. HumanEval has been publicly available since 2021, and many language models released after that date may have encountered its problems during pre-training. Studies have shown that models can achieve high HumanEval scores by memorizing solutions rather than reasoning about problem specifications. To mitigate this, researchers should report contamination analysis, use temporally-held-out problems, and supplement HumanEval results with evaluation on newer, less-exposed benchmarks like LiveCodeBench.

HumanEval~\citep{chen2021codex} consists of 164 Python programming problems, each with a function signature, docstring, and unit tests. The pass@$k$ metric measures the probability that at least one of $k$ generated solutions passes all unit tests. This benchmark has been widely adopted because it is simple, reproducible, and directly measures functional correctness.

Reflexion~\citep{reflexion2023} demonstrates self-improvement on HumanEval by generating solutions, evaluating them against unit tests, and converting failure feedback into natural language reflections that inform subsequent attempts. Starting from a baseline of approximately 80\% pass@1 with GPT-3.5-turbo, Reflexion improves to 91\% after two reflection rounds, showing that language-based feedback can substitute for expensive reinforcement learning.

EvoMAC~\citep{evomac2024} uses a multi-agent co-evolution approach where a developer team proposes code and a tester team generates tests, with both teams evolving over time. On HumanEval and MBPP, EvoMAC shows improvements over single-agent baselines, particularly on problems that require understanding complex specifications or handling edge cases.

The contamination risk for HumanEval and MBPP is classified as \textbf{high}: these benchmarks have been publicly available since 2021--2022, and many LLMs may have encountered them during pre-training. Researchers should report the model's training data cutoff and, where possible, use held-out or newly generated problem sets to verify that improvements are not due to memorization.


\subsection{Benchmark Deep Dive: Reasoning and Knowledge}
\label{sec:eval-reasoning}

\subsubsection{GSM8K and Mathematical Reasoning}

GSM8K~\citep{cobbe2021gsm8k} contains 8,500 grade-school math word problems with annotated step-by-step solutions. Despite the problems being relatively simple for humans (grade-school level), they require multi-step arithmetic reasoning that challenges current language models, making GSM8K a useful benchmark for measuring reasoning improvement.

STaR~\citep{star2022} (Self-Taught Reasoner) demonstrates a bootstrapping approach on GSM8K: the model generates reasoning traces, filters for correct solutions, and fine-tunes on successful traces. Starting from a base accuracy of approximately 35\% with a 6B-parameter model, STaR improves to 74\% after several rounds of self-training, approaching the performance of models fine-tuned on human-annotated rationales.

RISE~\citep{rise2024} (Recursive Self-Improvement for Reasoning) applies online reinforcement learning to improve reasoning on GSM8K and MATH. RISE trains the model to generate multiple reasoning attempts and learn from both successful and failed trajectories. On GSM8K, RISE achieves significant improvements over standard supervised fine-tuning baselines, particularly on problems that require longer reasoning chains.

SPIRAL~\citep{spiral2025} uses self-play to generate reasoning problems and solutions, creating a curriculum that progressively increases in difficulty. On mathematical reasoning benchmarks, SPIRAL demonstrates that self-generated training data can be as effective as human-curated data, provided the generation process includes quality filtering and difficulty calibration.


\subsubsection{MATH, GPQA, and Hard Reasoning}

The progression from GSM8K to MATH to GPQA represents a gradient of increasing difficulty and evaluation sophistication. GSM8K tests multi-step arithmetic with simple language; MATH introduces competition-level reasoning across diverse mathematical domains; GPQA demands expert-level knowledge that challenges even PhD-level human evaluators.

MATH~\citep{hendrycks2021math} is structured as a 12,500-problem benchmark across seven subjects: algebra, counting and probability, geometry, intermediate algebra, number theory, prealgebra, and precalculus. Each problem is assigned a difficulty level from 1 (easiest) to 5 (hardest). This graded structure enables fine-grained evaluation of self-improvement: does the model improve uniformly across difficulty levels, or does improvement concentrate on easier problems? This distinction is important because self-evolution that only improves performance on Level 1--2 problems while leaving Level 4--5 problems unchanged may indicate surface-level pattern matching rather than genuine reasoning improvement.

Self-Rewarding LMs~\citep{selfrewarding2024} report self-improvement on reasoning benchmarks through iterative DPO (Direct Preference Optimization). The model generates multiple candidate solutions, evaluates them using itself as a judge, and fine-tunes on its own preference rankings. On reasoning benchmarks, Self-Rewarding shows improvement in early iterations but raises concerns about evaluator degradation in later iterations: as the model's judge trains on its own rankings, it may develop systematic biases that inflate scores without genuine quality improvement. This phenomenon underscores the importance of independent verification for self-rewarding systems.

Meta-Rewarding~\citep{metarewarding2024} addresses the evaluator degradation problem by introducing a three-tier architecture: actor (generates solutions), judge (scores solutions), and meta-judge (evaluates the judge). The meta-judge is trained to identify cases where the judge's scores are inconsistent, biased, or corrupted. On mathematical reasoning benchmarks, Meta-Rewarding achieves better results than Self-Rewarding while maintaining more stable evaluation quality across iterations. However, the meta-judge itself is a language model, introducing a recursive evaluation problem that can only be fully resolved by external, non-model-based verification.

GPQA~\citep{rein2024gpqa} pushes evaluation to the expert level. With 448 PhD-level questions in physics, chemistry, and biology, GPQA tests whether self-evolution can improve performance on tasks that require deep domain expertise. Non-expert humans achieve only 34\% accuracy even with internet access; PhD experts achieve 65\%. Current language models, even with self-improvement techniques, remain well below expert-level performance on GPQA, suggesting that the frontier of self-evolution in reasoning is far from saturated. The key limitation is that GPQA-style questions cannot be easily verified by programmatic means---they require expert judgment, which is expensive and not scalable.

A critical observation across the reasoning benchmark landscape is the interaction between problem verifiability and self-improvement quality. Benchmarks with \textbf{automatically verifiable answers} (GSM8K, MATH) enable self-play and self-training loops where the model can generate its own training data with reliable quality control. Benchmarks requiring \textbf{expert judgment} (GPQA, open-ended generation) lack this property, forcing reliance on model-based judges or human evaluation, both of which introduce reliability concerns. This verifiability gap is one of the most important constraints on the current scope of self-evolution research.


\subsubsection{Self-Play and Verification in Code Reasoning}

ReVeal~\citep{reveal2025} from Microsoft Research introduces a particularly sophisticated evaluation paradigm: co-evolution of code generation and test generation. Rather than treating verification as a fixed external process, ReVeal explicitly optimizes the verification capability alongside the generation capability. This creates a co-evolutionary dynamic: as the code generator improves, the test generator must also improve to catch the more subtle bugs that the improved generator produces; conversely, a better test generator provides more informative feedback that helps the code generator improve further.

ReVeal uses TAPO (Turn-level Adaptive Policy Optimization) for fine-grained credit assignment across multiple reasoning turns. Unlike standard RL methods that assign a single reward to an entire trajectory, TAPO evaluates each turn independently, rewarding turns that move closer to the correct solution and penalizing turns that introduce errors. On LiveCodeBench, ReVeal demonstrates that models trained with only 3 turns of reasoning can self-evolve for 20+ turns at inference time, with performance improving consistently across turns.

The implications for evaluation methodology are significant. ReVeal's co-evolution approach suggests that evaluation infrastructure should not be static but should itself evolve alongside the agent. Fixed test suites become stale as agents learn to game them; fixed judges become unreliable as agents learn their biases. The most robust evaluation systems will be those that maintain ``adaptive adversaries''---verifiers that actively search for the agent's failure modes and update their evaluation criteria in response to the agent's improvements.

The MATH benchmark~\citep{hendrycks2021math} provides 12,500 competition-level mathematics problems across seven subjects (algebra, counting and probability, geometry, intermediate algebra, number theory, prealgebra, and precalculus) with five difficulty levels. MATH is significantly harder than GSM8K and has been a key benchmark for evaluating advanced reasoning capabilities.

GPQA~\citep{rein2024gpqa} (Graduate-Level Google-Proof Q\&A) presents 448 expert-level multiple-choice questions in physics, chemistry, and biology, written by PhD-level domain experts. GPQA is designed to be ``Google-proof'': even with access to search engines, non-expert humans achieve only 34\% accuracy, while PhD-level experts achieve 65\%. This makes GPQA a strong test of deep domain knowledge rather than surface-level retrieval.

Absolute Zero Reasoners~\citep{absolutezero2025} demonstrates self-play-based improvement on mathematical reasoning benchmarks. The system generates its own problems and solutions, evaluates them against a verifier, and uses successful pairs as training data. On MATH and related benchmarks, Absolute Zero shows that a model can improve its reasoning without any external human-labeled data, provided a reliable verifier is available.


\subsubsection{MMLU and Knowledge Assessment}

MMLU~\citep{hendrycks2021mmlu} (Massive Multitask Language Understanding) covers 57 academic subjects ranging from elementary mathematics to professional-level law and medicine. While MMLU is useful as a general capability benchmark, its relevance to agent self-evolution is limited because it tests static knowledge rather than dynamic reasoning, tool use, or learning ability.

The key insight from the reasoning benchmark literature is that self-improvement is most convincingly demonstrated on benchmarks with \textbf{verifiable answers}---problems where correctness can be determined objectively (e.g., mathematical proofs, code that passes tests, puzzles with unique solutions). Open-ended tasks like essay writing or creative generation lack this property, making it difficult to measure improvement without subjective human judgment.


\subsection{Benchmark Deep Dive: Environment Interaction}
\label{sec:eval-environment}

\subsubsection{Web-Based Tasks: WebArena and WebShop}

WebArena~\citep{zhou2024webarena} creates realistic web-based tasks that require agents to navigate websites, fill out forms, make purchases, and extract information. Tasks are grounded in real web infrastructure (content management systems, e-commerce platforms, forums, and Git repositories), providing a testbed for evaluating agents in environments that closely resemble production web applications.

ExpeL~\citep{expel2023} demonstrates learning from experience on WebArena-like tasks: the agent accumulates insights from both successful and failed trajectories, building a reusable knowledge base that improves performance on subsequent tasks. This experience-based learning is a form of self-evolution at the memory level: the agent's growing knowledge base changes its behavior without modifying model weights or code.

WebShop~\citep{yao2022webshop} provides a simulated e-commerce environment where agents must find and purchase products matching natural language instructions. WebShop evaluates both task success (finding the right product) and process efficiency (number of clicks, search queries, and page navigations).

\subsubsection{Lifelong Learning: Voyager and Open-Ended Evaluation}

Voyager~\citep{voyager2023} represents a paradigm shift in evaluation methodology. Rather than testing against a fixed set of tasks, Voyager evaluates agents by their ability to accumulate capabilities over time in an open-ended environment (Minecraft). Key metrics include:

\begin{itemize}[nosep]
\item \textbf{Unique items discovered}: The number of distinct Minecraft items the agent learns to craft.
\item \textbf{Technology tree coverage}: The percentage of technology tree nodes unlocked.
\item \textbf{Skill transfer}: The ability to apply learned skills in new worlds with different biomes and resource distributions.
\item \textbf{Zero-shot performance}: Performance on tasks that were never encountered during training.
\end{itemize}

Voyager's evaluation approach is closer to how self-evolving agents should be assessed in production: by their cumulative capability growth over time, rather than by a single test score. This ``lifelong learning'' evaluation captures the essence of self-evolution: the agent should become progressively more capable through experience, not just achieve a high score on a specific benchmark.

\subsubsection{AppWorld and ALFWorld}

AppWorld~\citep{trivedi2024appworld} provides a sandboxed environment for evaluating agents on real-world app interactions, including calendar management, email handling, file operations, and multi-app workflows. AppWorld's key contribution is its executable evaluation: each task has a deterministic ground truth that can be verified programmatically, combining the rigor of unit tests with the complexity of real-world applications.

ALFWorld~\citep{shridhar2021alfworld} tests embodied agents in text-based household environments where they must complete tasks like finding objects, cleaning, and rearranging furniture. ALFWorld's multi-step nature exposes failure modes that single-step benchmarks miss: agents must maintain state across actions, recover from errors, and adapt their plans when initial strategies fail.


\subsection{Agent-Specific Evaluation Metrics}
\label{sec:eval-agent-metrics}

Beyond standard benchmark accuracy, self-evolving agents require specialized metrics that capture the dynamics of the improvement process itself. We identify four categories of agent-specific metrics.

\subsubsection{Iterative Improvement Metrics}

The most direct measure of self-evolution is the improvement trajectory across iterations. We define:

\begin{equation}
\Delta_t = V(z_t, \tau) - V(z_{t-1}, \tau)
\label{eq:iterative-gain}
\end{equation}

where $V(z_t, \tau)$ is the evaluation score of agent state $z_t$ on task distribution $\tau$. A positive $\Delta_t$ indicates improvement, but the distribution of $\Delta_t$ across tasks and iterations matters more than the average. Key patterns include:

\begin{itemize}[nosep]
\item \textbf{Monotonic improvement}: $\Delta_t > 0$ for all $t$, indicating reliable learning.
\item \textbf{Plateau}: $\Delta_t \approx 0$ after initial gains, suggesting saturation or local optima.
\item \textbf{Volatile improvement}: Alternating positive and negative $\Delta_t$, indicating unstable learning.
\item \textbf{Regression}: $\Delta_t < 0$ for some $t$, indicating negative transfer or capability loss.
\end{itemize}

DGM's archive-based evolution typically produces smoother improvement curves because it retains diverse variants and can ``fall back'' to earlier, more robust versions when newer variants regress.


\subsubsection{Transfer and Generalization Metrics}

Transfer evaluation measures whether improvements discovered on one task distribution transfer to another. We define transfer metrics at four levels:

\begin{enumerate}[nosep]
\item \textbf{Cross-task transfer}: Improvement on task set A leads to improvement on held-out task set B within the same domain.
\item \textbf{Cross-model transfer}: Agent designs evolved with model $M_1$ improve performance when applied to model $M_2$.
\item \textbf{Cross-environment transfer}: Capabilities learned in environment $E_1$ are applicable in environment $E_2$.
\item \textbf{Cross-domain transfer}: Strategies effective in domain D$_1$ (e.g., code) transfer to domain D$_2$ (e.g., web navigation).
\end{enumerate}

ADAS~\citep{adas2024} reports cross-model and cross-domain transfer results: agent designs discovered by a meta-agent using one model family show improvements when applied to different model families and task domains. This is one of the strongest pieces of evidence that agent evolution can produce genuinely transferable improvements, not just task-specific optimizations.


\subsubsection{Cost Efficiency Metrics}

Self-evolution is not free. We define cost efficiency as the improvement per unit of resource consumption:

\begin{equation}
\eta = \frac{\Delta_{\text{performance}}}{\text{Cost}_{\text{total}}}
\label{eq:cost-efficiency}
\end{equation}

where $\text{Cost}_{\text{total}}$ includes API calls, token consumption, compute time, human intervention, and monetary cost. Key cost metrics include:

\begin{itemize}[nosep]
\item \textbf{API calls per improvement}: How many LLM API calls are needed to achieve a given performance improvement.
\item \textbf{Token consumption per unit gain}: The total tokens consumed (input + output) per percentage point of improvement.
\item \textbf{Human intervention rate}: The frequency with which human oversight is required to correct errors, approve changes, or handle edge cases.
\item \textbf{Time to target}: The wall-clock time from initial state to target performance level.
\end{itemize}

These metrics are rarely reported in academic papers but are critical for production deployment. A self-evolution system that achieves a 10\% improvement at 100$\times$ the cost of manual prompt engineering may be scientifically interesting but practically useless.


\subsubsection{Safety Metrics}

Safety evaluation for self-evolving agents must verify that improvement does not come at the expense of security, privacy, or reliability. Key safety metrics include:

\begin{itemize}[nosep]
\item \textbf{Permission violation rate}: The frequency with which evolved variants attempt to exceed their authorized permissions.
\item \textbf{Reward hacking rate}: The frequency with which improvements are achieved by gaming the evaluation function rather than genuine capability gain.
\item \textbf{Rollback rate}: The frequency with which evolved variants must be reverted due to regressions or failures.
\item \textbf{Safety regression}: Whether acceptance of unsafe outputs increases over evolution iterations.
\end{itemize}

Self-Rewarding LMs~\citep{selfrewarding2024} and Meta-Rewarding~\citep{metarewarding2024} illustrate the reward hacking risk: when the model serves as both generator and evaluator, it may learn to assign high scores to its own outputs regardless of quality, producing apparent improvement without genuine gain. Multi-judge evaluation, hidden test sets, and cross-model consistency checks are essential defenses against this failure mode.

\subsection{Benchmark Contamination and Reproducibility}
\label{sec:eval-contamination}

Benchmark contamination---the inclusion of test set examples in training data---is a growing concern across machine learning, but it is particularly problematic for self-evolution research where claimed improvements may be artifacts of memorization rather than genuine capability gain.

\subsubsection{Types of Contamination}

We distinguish three levels of contamination:

\begin{enumerate}[nosep]
\item \textbf{Direct contamination}: Test examples appear verbatim in the training corpus. This is most likely for widely-used, publicly available benchmarks like HumanEval, GSM8K, and MMLU that have been part of the internet since 2021--2022.

\item \textbf{Near-miss contamination}: The model has seen problems that are very similar to test examples but not identical. This is harder to detect but can still inflate scores by teaching the model solution patterns that transfer to test problems.

\item \textbf{Evaluator leakage}: The agent has access to the evaluation function during its evolution process. In code tasks, this might mean the agent can read the unit tests it needs to pass; in reasoning tasks, it might mean the verifier's criteria are visible in the prompt. This is the most insidious form of contamination because it is not caused by training data but by evaluation design.
\end{enumerate}

\subsubsection{Mitigation Strategies}

Several strategies can reduce contamination risk:

\begin{itemize}[nosep]
\item \textbf{Temporal splits}: Use only benchmarks released after the model's training data cutoff. This is straightforward but limits the available evaluation set.
\item \textbf{Held-out sets}: Create new problem sets that are structurally similar to existing benchmarks but contain novel instances. This preserves evaluation properties while avoiding direct contamination.
\item \textbf{Procedural generation}: Generate problems algorithmically (as in SPIRAL's self-play or Absolute Zero's self-generated problems). This provides an essentially unlimited supply of novel problems.
\item \textbf{Run-time isolation}: Ensure that the agent cannot access the evaluation function, unit tests, or ground-truth answers during its execution. Sandboxed evaluation environments provide this isolation.
\end{itemize}

\subsubsection{Reproducibility Challenges}

Reproducibility in agent evolution research is complicated by several factors:

\begin{enumerate}[nosep]
\item \textbf{LLM non-determinism}: The same prompt can produce different outputs due to sampling variability. This makes exact reproduction impossible without fixing random seeds, temperature, and top-p parameters.

\item \textbf{API version changes}: LLM APIs are frequently updated, and model behavior can change without notice. Results obtained with one API version may not reproduce with a later version.

\item \textbf{State-dependent evaluation}: Self-evolving agents accumulate state (memory, skills, archive) across iterations, making each evaluation dependent on the full history. Reproducing a specific result requires reproducing the entire evolution trajectory.

\item \textbf{Cost barriers}: Many agent evolution experiments require thousands of API calls, making full reproduction expensive. This limits the number of independent replications and increases the risk of publication bias toward positive results.
\end{enumerate}

We recommend that future papers report: (1) the model version and API endpoint used, (2) the number of random seeds and their specific values, (3) the total cost in tokens and dollars, (4) the full evolution trajectory (not just the best result), and (5) failure analysis of iterations that did not improve.

\subsubsection{Evaluation Frameworks and Leaderboards}

The agent evaluation ecosystem is maturing rapidly. Several infrastructure projects provide standardized evaluation environments:

\begin{itemize}[nosep]
\item \textbf{SWE-Bench infrastructure}: Provides Docker-based evaluation environments for software engineering tasks, ensuring reproducible execution of agent-generated patches against real test suites.

\item \textbf{WebArena}: A self-hostable web environment that recreates realistic websites for agent evaluation, including e-commerce, content management, and Git repository interfaces.

\item \textbf{HumanEval+: Extended variants} of HumanEval that address contamination by generating novel problems with the same structural properties as the original benchmark.

\item \textbf{AgentBench}: A multi-dimensional benchmark that evaluates agents across coding, web browsing, database querying, and knowledge-intensive tasks within a unified framework.
\end{itemize}

The fragmentation of evaluation infrastructure remains a significant challenge. Different systems use different benchmarks, evaluation protocols, and reporting standards, making direct comparison difficult. The community would benefit from a standardized evaluation protocol that requires reporting: (1) results on at least three benchmark categories, (2) full evolution trajectories with cost accounting, (3) transfer evaluation on held-out tasks, (4) safety regression testing, and (5) contamination analysis with respect to model training data.


\subsection{Evaluation Methodology: From Demo to Production}
\label{sec:eval-methodology}

A critical gap in the current literature is the distance between benchmark demonstrations and production-grade evaluation. Most papers report results on curated benchmarks under controlled conditions, but production deployment requires evaluation under fundamentally different constraints. This section examines the methodology challenges that arise when moving from academic evaluation to real-world assessment.

\subsubsection{The Demo-to-Production Gap}

Benchmark results, however impressive, represent a lower bound on the evaluation requirements for production systems. The gap manifests in several dimensions:

\textbf{Task distribution shift.} Benchmarks use carefully curated task distributions that may not reflect the distribution of tasks encountered in production. An agent that achieves 50\% on SWE-Bench Verified may perform much worse on proprietary codebases with different coding styles, domain-specific languages, or complex build systems that do not appear in the benchmark's open-source repositories.

\textbf{Reliability requirements.} Academic evaluation typically reports average performance across multiple runs, but production systems must meet minimum reliability thresholds on every execution. An agent that resolves 50\% of issues on average but fails catastrophically on 5\% of cases (producing corrupted code, deleting files, or introducing security vulnerabilities) may be worse than an agent that resolves only 30\% but never causes harm.

\textbf{Cost constraints.} Academic experiments often use generous computational budgets, with the cost of self-evolution amortized across research publications. In production, each API call and each evaluation cycle has a direct monetary cost. A self-evolution system that costs \$10,000 in API calls to improve from 20\% to 50\% on a benchmark may not be economically viable if the same improvement could be achieved by a human engineer in a few hours.

\textbf{Evaluation latency.} Production systems must provide timely feedback. If the evaluation cycle (generate candidate, evaluate on benchmark, decide whether to accept) takes hours or days, the self-evolution loop may be too slow to keep pace with changing requirements. Fast, approximate evaluation is often more valuable than slow, precise evaluation.

\subsubsection{Reporting Standards for Self-Evolution Research}

Based on our analysis of the literature, we propose the following minimum reporting standards for self-evolution research:

\begin{enumerate}[nosep]
\item \textbf{Full evolution trajectory}: Report performance at every iteration, not just the final result. This reveals the shape of the improvement curve and allows readers to assess whether improvement is monotonic, volatile, or plateauing.

\item \textbf{Cost accounting}: Report total API calls, token consumption, wall-clock time, and estimated monetary cost for the complete evolution process. This enables cost-efficiency comparisons across methods.

\item \textbf{Baseline comparison}: Compare against at least three baselines: (a) the base model without self-improvement, (b) the best hand-engineered approach, and (c) at least one other self-improvement method. Single-method evaluation without baselines is insufficient.

\item \textbf{Transfer evaluation}: Report results on at least one held-out benchmark that was not used during the evolution process. This distinguishes genuine capability improvement from benchmark-specific optimization.

\item \textbf{Contamination analysis}: State the model's training data cutoff, identify which benchmarks may be contaminated, and report results on newer or held-out benchmarks that are unlikely to be contaminated.

\item \textbf{Safety regression}: Report whether safety-related metrics (e.g., refusal rate on harmful tasks, adherence to instructions, output quality on out-of-distribution inputs) are maintained or degraded during evolution.

\item \textbf{Reproducibility information}: Report model version, API endpoint, random seeds (if deterministic), temperature and sampling parameters, and total number of runs.
\end{enumerate}

These standards are deliberately ambitious. Few current papers meet all seven criteria. However, as the field matures, the community should converge toward these standards to ensure that self-evolution claims are verifiable and comparable.

\subsubsection{The Evaluator's Dilemma}

Self-evolution introduces a fundamental tension in evaluation: the system being evaluated is also optimizing against the evaluation function. This creates a dynamic similar to adversarial machine learning, where the ``attacker'' (the self-evolving agent) and the ``defender'' (the evaluator) are in a constant arms race.

Self-Rewarding LMs~\citep{selfrewarding2024} illustrate this dilemma. In this approach, the model generates candidates, evaluates them using itself as a judge, and fine-tunes on its own preference rankings. Initially, this produces genuine improvement: the model learns to generate higher-quality outputs that align with its own preferences. However, over many iterations, the model may learn to reward outputs that look good to its own judge rather than outputs that are genuinely high-quality. This is evaluator degradation: the evaluation function drifts away from the true objective.

Meta-Rewarding~\citep{metarewarding2024} attempts to address this by adding a meta-judge that evaluates the judge. The meta-judge is itself a language model, trained to identify cases where the primary judge is biased, inconsistent, or corrupt. However, this introduces a recursive problem: who evaluates the meta-judge? Without an external ground truth, the system can still converge to self-consistent but incorrect evaluation.

The resolution to the evaluator's dilemma lies in the principle of \textbf{evaluator independence}: the evaluation function should be as independent as possible from the agent being evaluated. This can be achieved through several mechanisms:

\begin{itemize}[nosep]
\item \textbf{Programmatic verifiers}: Unit tests, type checkers, and sandbox execution provide evaluation signals that are independent of the agent's preferences. This is why code and math tasks have been the most successful domains for self-evolution.

\item \textbf{Hidden test sets}: Evaluation on benchmarks that the agent cannot access during training or evolution provides an independent check. However, maintaining the secrecy of test sets becomes harder as models become more capable of memorization.

\item \textbf{Cross-model evaluation}: Using a different model to evaluate the agent's outputs provides some independence, though models within the same family may share biases.

\item \textbf{Human spot-checking}: Random sampling and human review of evolved outputs provides the most reliable evaluation but does not scale to the volume of candidates produced by self-evolution systems.
\end{itemize}

In practice, robust evaluation requires a combination of these mechanisms. The five-layer hierarchy proposed in Section~\ref{sec:eval-hierarchy} is designed to provide multiple independent evaluation signals, reducing the risk that any single evaluator's weakness is exploited by the evolving agent.


\subsection{Summary and Open Problems}
\label{sec:eval-summary}

Evaluation is the linchpin of agent self-evolution: without reliable evaluators, self-improvement claims are unverifiable, and without multi-layer evaluation, evolved agents are unsafe to deploy. This chapter has proposed a five-layer evaluation hierarchy, surveyed major benchmarks across software engineering, reasoning, and environment interaction, and introduced agent-specific metrics for iterative improvement, transfer, cost efficiency, and safety.

Several open problems remain:

\begin{enumerate}[nosep]
\item \textbf{Evaluator evolution}: As agents become more capable, evaluators must evolve in tandem. Current evaluators are largely static; future systems need evaluator ecosystems that improve alongside agents, preventing the agent from outpacing its own evaluation.

\item \textbf{Open-ended evaluation}: Standard benchmarks evaluate against fixed task sets, but self-evolution in open environments requires evaluation methods that can assess cumulative capability growth, novelty, and exploration quality.

\item \textbf{Evaluation cost}: Comprehensive multi-layer evaluation is expensive. Future work should develop cost-efficient evaluation strategies that provide high signal-to-noise evaluation with limited API calls and compute.

\item \textbf{Community standards}: The field lacks standardized evaluation protocols. We recommend that future papers report multi-benchmark results with full cost accounting, transfer evaluation, and contamination analysis.

\item \textbf{Beyond accuracy}: Task completion rate is necessary but not sufficient. Future evaluation must address process quality, reliability, safety, cost, and user satisfaction as first-class metrics alongside accuracy.
\end{enumerate}

The following chapter examines how these evaluation principles manifest in industrial practice, where the gap between benchmark performance and production reliability remains a critical challenge.
