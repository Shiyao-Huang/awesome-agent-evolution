\section{A Unified Taxonomy: The Five Evolution Loops}
\label{sec:taxonomy}

The diversity of self-evolving AI systems---spanning AutoML, neural architecture search, LLM self-improvement, evolutionary computation, and agent frameworks---presents a classification challenge. Each community has developed its own terminology: AutoML researchers speak of ``pipeline synthesis,'' NAS researchers of ``architecture search,'' LLM researchers of ``self-refinement,'' evolutionary computation researchers of ``mutation and selection,'' and agent researchers of ``role adaptation.'' Yet beneath this terminological diversity lies a common structure: iterative cycles of generation, evaluation, memory, and refinement.

In this section, we propose a unified taxonomic framework---the Five Evolution Loops---that captures this common structure. Each loop type represents a fundamental pattern of self-improvement that recurs across domains. Individual systems may employ one or more loop types, and the most powerful systems combine multiple loops into integrated self-evolution pipelines.

\subsection{Overview of the Five Loops}

We identify five fundamental types of evolutionary loops:

\begin{enumerate}
    \item \textbf{Specification-to-Execution Loop} (\emph{Spec Loop}): Translating high-level goals (typically expressed in natural language) into executable artifacts (ML pipelines, agent workflows, code).
    \item \textbf{Search Loop}: Systematically exploring a space of candidates (architectures, prompts, code, agents, hyperparameters) to find high-performing solutions.
    \item \textbf{Evaluator Loop}: Using automated evaluation mechanisms (tests, benchmarks, verifiers, reward models) to score and select candidate solutions.
    \item \textbf{Reflection Loop}: Analyzing failures and successes, extracting lessons, and incorporating those lessons into future generation or search strategies.
    \item \textbf{Population Loop}: Maintaining a diverse collection of candidates, applying selection, mutation, and recombination operators, and preserving lineage information.
\end{enumerate}

These loops are related but distinct. The Search Loop and Population Loop both explore candidate spaces, but the Search Loop may operate with a single candidate (e.g., hill climbing on prompts) while the Population Loop explicitly maintains multiple simultaneous candidates. The Evaluator Loop and Reflection Loop both process feedback, but the Evaluator Loop produces scalar scores while the Reflection Loop produces structured, language-based analyses. The Specification-to-Execution Loop is unique in its focus on the \emph{translation} from intent to artifact.

\subsection{Loop 1: Specification-to-Execution}
\label{sec:spec_loop}

The Specification-to-Execution Loop (Spec Loop) transforms a high-level description of a goal---typically expressed in natural language---into an executable artifact. This artifact may be a machine learning pipeline, an agent workflow, a software program, or a configuration file. The Spec Loop is the entry point for self-evolution: it determines what the system will attempt to improve.

\subsubsection{Representative Systems}

\paragraph{AutoML-GPT.}
AutoML-GPT~\citep{zhang2023automlgpt} uses GPT models as the planning layer for automated machine learning, generating complete ML pipelines from natural language task descriptions. The system introduces a structured intermediate representation consisting of \emph{Task Cards}, \emph{Data Cards}, and \emph{Model Cards} that bridge the gap between ambiguous natural language specifications and precise ML pipeline configurations. Given a user specification such as ``classify images of cats and dogs with high accuracy,'' AutoML-GPT decomposes this into a sequence of decisions: dataset loading and splitting, preprocessing steps (normalization, augmentation), model architecture selection, training hyperparameters, and evaluation strategy. The system leverages in-context learning with few-shot examples of successful pipeline configurations, enabling it to produce syntactically correct and semantically reasonable pipelines for a wide range of ML tasks including image classification, tabular prediction, and natural language processing.

\paragraph{AutoML-Agent.}
AutoML-Agent~\citep{chen2024automlagent} extends the single-agent AutoML-GPT paradigm into a multi-agent workflow with specialized agents for data retrieval, preprocessing, modeling, evaluation, and deployment. Each agent operates as a specialist with its own prompt template and tool set, coordinated by a planner agent that decomposes the overall specification into sub-tasks. The data agent handles dataset discovery and loading; the preprocessing agent selects and applies appropriate transformations; the modeling agent searches over architectures and hyperparameters; the evaluation agent designs cross-validation strategies and computes metrics; and the deployment agent packages the final pipeline for production use. This decomposition enables each agent to develop specialized expertise and reduces the context burden on any single LLM call.

\paragraph{LLM+AutoML.}
LLM+AutoML~\citep{zheng2024llm_automl} proposes a framework for text-to-ML program synthesis that treats the AutoML specification problem as a program generation task. Rather than generating pipeline configurations in a domain-specific language, the system generates executable Python code that invokes established AutoML libraries (e.g., FLAML, Auto-sklearn). This approach combines the flexibility of code generation with the reliability of battle-tested optimization libraries. The LLM acts as a program synthesizer that reads natural language specifications and produces ML training scripts, while the underlying AutoML library handles the low-level search over hyperparameters and model architectures. Empirical results demonstrate that this hybrid approach outperforms both pure LLM-based pipeline generation and traditional AutoML methods lacking natural language interfaces, achieving competitive performance on standard benchmarks while requiring significantly less manual configuration.

\paragraph{AutoM3L.}
AutoM3L addresses the challenge of multimodal ML automation, where the specification must account for heterogeneous input modalities (text, image, tabular, audio) and their interactions. The system automatically determines appropriate fusion strategies (early fusion, late fusion, cross-attention), modality-specific encoders, and training procedures from a natural language specification of the multimodal learning task. This is particularly challenging because the space of possible multimodal architectures is combinatorially larger than unimodal ones, and the interaction between modalities is difficult to specify precisely in natural language.

\subsubsection{Formal Algorithm Description}

We formalize the Specification-to-Execution Loop as follows:

\begin{enumerate}
    \item \textbf{Input:} Natural language specification $\mathcal{S}$ describing the ML task, dataset characteristics, and performance requirements.
    \item \textbf{Specification Parsing:} Decompose $\mathcal{S}$ into structured components $\{c_1, c_2, \ldots, c_k\}$ covering task type, data schema, constraints, and optimization objectives.
    \item \textbf{Pipeline Skeleton Generation:} Generate an initial pipeline skeleton $P_0 = (s_1, s_2, \ldots, s_n)$ where each $s_i$ is a pipeline stage (e.g., data loading, preprocessing, feature engineering, model selection, training, evaluation).
    \item \textbf{Component Instantiation:} For each stage $s_i$, select and instantiate a concrete implementation from the component library $\mathcal{L}$, producing $P = (f_1 \circ f_2 \circ \cdots \circ f_n)$ where $f_i \in \mathcal{L}$.
    \item \textbf{Validation:} Execute $P$ on a validation split and compute metrics $m(P)$. If $m(P)$ meets the acceptance threshold, return $P$.
    \item \textbf{Iterative Refinement:} If $m(P)$ is below threshold, feed the execution trace, metrics, and error analysis back to the LLM to generate $P'$.
    \item \textbf{Output:} Executable pipeline $P^*$ with associated performance report.
\end{enumerate}

This algorithm highlights the key distinction between single-shot specification (steps 1--4) and iterative specification-to-execution (steps 5--6). Most current systems stop after step 4, while a fully self-evolving system would close the loop by iterating until convergence.

\subsubsection{Cross-Loop Interactions}

The Specification-to-Execution Loop interacts with the other four loops in critical ways:

\begin{itemize}
    \item \textbf{Search Loop:} The Spec Loop provides the initial candidate and defines the search space. AutoML-GPT's generated pipeline serves as the starting point for hyperparameter search, while the task specification constrains which architectures and preprocessing steps are considered. The Spec Loop can also be invoked mid-search when the current specification proves inadequate---for example, when the evaluation reveals that the original task description was ambiguous.
    \item \textbf{Evaluator Loop:} The Spec Loop determines what metrics to compute and how to interpret them. The task specification typically includes performance criteria (e.g., ``achieve $>$95\% accuracy with inference time $<$100ms'') that define the evaluation function. When the Evaluator Loop produces unexpected results, the Spec Loop may need to revise its understanding of the task.
    \item \textbf{Reflection Loop:} When iterative refinement fails to converge, the Reflection Loop can analyze the pattern of failures to suggest modifications to the specification itself---for instance, recognizing that a classification task would benefit from being reformulated as a regression task, or that additional data preprocessing is needed.
    \item \textbf{Population Loop:} The Spec Loop can generate multiple pipeline variants that seed a population-based search. AutoML-Agent's multi-agent decomposition naturally produces multiple candidate pipelines for different sub-task decompositions, which can then be evolved as a population.
\end{itemize}

\subsubsection{Limitations Analysis}

The Specification-to-Execution Loop faces several significant limitations:

\begin{enumerate}
    \item \textbf{Specification ambiguity:} Natural language specifications are inherently ambiguous. The phrase ``high accuracy'' may mean 95\% for a sentiment analysis task but 99.99\% for medical diagnosis. Current systems rely on implicit assumptions about task difficulty and acceptable performance levels, which can lead to premature termination or endless refinement. Resolving this ambiguity requires either interactive specification (multi-turn dialogue) or conservative interpretation with fallback strategies.

    \item \textbf{Single-shot generation bias:} Most Spec Loop systems generate the complete pipeline in a single forward pass and then iterate on components. This biases the system toward locally optimal pipeline structures that are close to the initial generation. A more robust approach would generate multiple structurally distinct pipeline skeletons and evaluate them in parallel, but this is computationally expensive and underexplored in current research.

    \item \textbf{Dependency on library coverage:} The quality of generated pipelines is fundamentally limited by the component library $\mathcal{L}$. If the library lacks a critical preprocessing step or model architecture, no amount of specification refinement can produce the optimal pipeline. This creates a tension between generality (large libraries with many components) and specificity (well-documented components that the LLM can reason about effectively).

    \item \textbf{Lack of specification evolution:} Current systems treat the specification as fixed after initial parsing. However, as the system gains experience with the task, it should be able to refine the specification itself---recognizing, for example, that the task is actually a multi-label classification problem rather than a single-label one, or that temporal ordering in the data matters. The Spec Loop should itself be subject to evolution, not just the pipeline it produces.
\end{enumerate}

\subsubsection{Analysis}

The Spec Loop is the most product-mature of the five loops, with commercial systems like GitHub Copilot, Cursor, and various AutoML platforms providing specification-to-code capabilities at scale. However, most current systems are \emph{single-shot}: they generate a pipeline once without iteratively improving it. Integrating the Spec Loop with the Evaluator and Reflection loops remains an open challenge. A key opportunity is the development of \emph{self-specifying} systems that can refine their own task descriptions based on execution experience, effectively closing the loop between what was asked and what was actually needed.


\subsection{Loop 2: Search}
\label{sec:search_loop}

The Search Loop systematically explores a space of candidate solutions to find high-performing configurations. The search space may consist of prompts, code, neural network architectures, agent configurations, hyperparameters, or any other parameterizable artifact. The Search Loop is the engine of self-evolution: it generates novelty, and when coupled with the Evaluator Loop, directs that novelty toward improvement.

\subsubsection{LLM-Based Optimization}

\paragraph{OPRO.}
OPRO~\citep{yang2023opro} uses an LLM as a black-box optimizer, treating the optimization problem as a natural language generation task. The key insight is that LLMs, having been trained on vast corpora of optimization-related text, can identify patterns in solution trajectories without explicit gradient information. The meta-prompt structure encodes the optimization trajectory as a series of instruction-score pairs:
\begin{verbatim}
Solution 1: <text> -> Score: 0.65
Solution 2: <text> -> Score: 0.71
Solution 3: <text> -> Score: 0.78
Generate Solution 4:
\end{verbatim}
OPRO demonstrates that LLMs can serve as general-purpose optimizers for problems expressed in natural language. On GSM8K mathematical reasoning, OPRO-discovered prompts outperformed human-designed prompts by significant margins. The system is particularly effective for discrete optimization problems where gradient-based methods are inapplicable, such as prompt engineering and combinatorial optimization. However, OPRO's scalability is limited by context window length---as the trajectory grows, the LLM must process increasingly long histories---and by the tendency of LLMs to converge prematurely on locally optimal solutions, a phenomenon related to the ``mode collapse'' observed in generative models.

\paragraph{Evolutionary prompt and code search.}
Building on the OPRO paradigm, subsequent work has applied LLM-based search to increasingly complex artifact spaces. Prompt optimization systems like EvoPrompt~\citep{guo2023evoprompt} combine evolutionary algorithms with LLM-based mutation operators, achieving state-of-the-art performance on diverse NLP benchmarks. The LLM reads a set of parent prompts and generates offspring that inherit successful patterns while introducing novelty. This represents a departure from traditional evolutionary computation, where mutation operators are hand-designed for each representation; the LLM serves as a \emph{universal variation operator} that can operate on any artifact expressible in natural language or code.

\subsubsection{Evolutionary Architecture Search}

\paragraph{EvoPrompting.}
EvoPrompting~\citep{chen2024evoprompting} encodes neural network architectures as Python code and uses LLMs to evolve them. Each architecture is represented as a self-contained Python class that inherits from a base module and specifies the forward pass, layer configurations, and connectivity patterns. The evolutionary process applies LLM-generated mutations to these code representations, enabling structural innovations that go beyond simple hyperparameter tuning. EvoPrompting demonstrated that LLM-evolved architectures can match or exceed hand-designed architectures on graph neural network benchmarks, producing novel connectivity patterns and layer combinations that human designers had not considered. The code representation is critical: it enables the LLM to reason about architectural properties (e.g., ``this network uses too many parameters for the input dimension; I will replace the fully connected layers with depthwise separable convolutions'') in ways that are impossible with traditional genetic representations.

\paragraph{NADER.}
NADER~\citep{nasr2024nader} decomposes architecture search into multi-agent collaboration. Rather than having a single LLM propose and evaluate architectures, NADER assigns specialized roles to multiple agents: a \emph{designer} proposes architectures, a \emph{critic} identifies potential weaknesses, an \emph{implementer} converts designs into executable code, and an \emph{evaluator} runs benchmarks. This decomposition mirrors the division of labor in human engineering teams and enables more thorough exploration of the architecture space. The multi-agent approach also provides natural diversity: different designer agents may explore different architectural philosophies (e.g., residual connections vs.\ attention mechanisms), reducing the risk of premature convergence.

\subsubsection{Agent Architecture Search}

\paragraph{ADAS.}
ADAS~\citep{hu2024adas} represents a paradigm shift from optimizing within fixed agent architectures to searching over the space of agent architectures themselves. The search space consists of meta-agents---configurations that specify how agents are composed from basic building blocks (LLM calls, tool invocations, memory operations, control flow constructs). ADAS discovered agent architectures that outperform hand-designed ones on diverse benchmarks including ARC (Abstraction and Reasoning Corpus) and Google Research Football. The discovered architectures exhibit surprising design patterns: for example, some architectures use nested reflection loops where one agent reflects on the reflections of another, while others employ sparse communication patterns where agents share only high-level summaries rather than full reasoning traces. ADAS was published at ICLR 2025 and demonstrates that the space of agent architectures is sufficiently large and complex that automated search can discover designs beyond human intuition.

\subsubsection{AlphaEvolve: Unified Search}

\paragraph{AlphaEvolve.}
AlphaEvolve~\citep{novikov2025alphaevolve} represents the most integrated search system to date, combining multiple search strategies under a unified framework. The system uses Gemini Flash for breadth exploration---rapidly generating many candidate solutions with lower computational cost per candidate---and Gemini Pro for depth exploration---carefully refining the most promising candidates with more sophisticated reasoning. This dual-model strategy balances exploration and exploitation at the level of the search operator itself. AlphaEvolve's most celebrated result is the discovery of a 48-multiplication algorithm for $4\times4$ complex matrix multiplication, the first improvement over Strassen's algorithm in this setting. The system achieved this by searching over the space of algorithm representations (code that implements matrix multiplication), using automated correctness verification (comparing outputs against reference implementations) as the evaluation criterion. AlphaEvolve also made progress on over 50 open mathematical problems and improved practical systems including data center scheduling (achieving 0.7\% compute recovery for Google's Borg cluster manager) and FlashAttention kernel optimization (23\% speedup).

\subsubsection{Formal Algorithm Description}

We formalize the LLM-based Search Loop as follows:

\begin{enumerate}
    \item \textbf{Input:} Search space definition $\mathcal{X}$, objective function $f: \mathcal{X} \rightarrow \mathbb{R}$, initial candidate(s) $x_0 \in \mathcal{X}$, LLM $\mathcal{M}$.
    \item \textbf{Initialize archive:} $\mathcal{A} \leftarrow \{(x_0, f(x_0))\}$.
    \item \textbf{For each iteration $t = 1, 2, \ldots, T$:}
    \begin{enumerate}
        \item \textbf{Selection:} Sample parent(s) $P \subseteq \mathcal{A}$ according to selection strategy (fitness-proportionate, tournament, or quality-diversity).
        \item \textbf{Variation:} Construct a meta-prompt $q(P, \mathcal{A})$ containing the selected parents, their scores, and relevant context. Generate offspring: $x_{\text{new}} \sim \mathcal{M}(q(P, \mathcal{A}))$.
        \item \textbf{Evaluation:} Compute $f(x_{\text{new}})$.
        \item \textbf{Archive update:} $\mathcal{A} \leftarrow \mathcal{A} \cup \{(x_{\text{new}}, f(x_{\text{new}}))\}$, optionally pruning low-quality or redundant entries.
    \end{enumerate}
    \item \textbf{Output:} Best candidate $x^* = \arg\max_{(x, s) \in \mathcal{A}} s$.
\end{enumerate}

The key design choices are the selection strategy (step 3a), the meta-prompt construction (step 3b), and the archive update rule (step 3d). Different systems make different choices: OPRO uses fitness-ranked selection and appends to a FIFO trajectory; AlphaEvolve uses MAP-Elites quality-diversity selection; ADAS uses tournament selection with novelty-based seeding.

\subsubsection{Cross-Loop Interactions}

The Search Loop sits at the center of the self-evolution architecture and interacts intensively with all other loops:

\begin{itemize}
    \item \textbf{Specification-to-Execution Loop:} The Spec Loop provides the search space definition $\mathcal{X}$ and the initial candidate $x_0$. In return, the Search Loop can inform the Spec Loop when the specified search space proves unproductive---for example, when all candidates in the specified architecture family achieve similar, sub-optimal performance, suggesting that the specification should be broadened to include alternative approaches.
    \item \textbf{Evaluator Loop:} The Evaluator Loop provides the objective function $f$ that guides search. The quality of search is fundamentally limited by the quality of evaluation: a noisy evaluator introduces false gradients that misdirect search, while an incomplete evaluator that fails to capture important properties may lead to solutions that score well but are practically useless. AlphaEvolve's success relies heavily on having precise mathematical verifiers as evaluators.
    \item \textbf{Reflection Loop:} The Reflection Loop can improve search efficiency by analyzing the trajectory of past search iterations and identifying productive or unproductive regions of the search space. For example, if the reflection mechanism notices that all high-scoring candidates share a particular structural property, it can bias future search toward candidates with that property. Conversely, it can identify when the search is stuck in a local optimum and suggest diversification strategies.
    \item \textbf{Population Loop:} The Population Loop extends the Search Loop from single-trajectory to multi-trajectory search. While a basic Search Loop might maintain only the current best candidate, the Population Loop maintains a diverse collection that enables parallel exploration and recombination. The Search Loop's variation operator becomes the Population Loop's mutation and crossover operators.
\end{itemize}

\subsubsection{Limitations Analysis}

The Search Loop faces several fundamental limitations:

\begin{enumerate}
    \item \textbf{Context window constraints:} LLM-based search operators are limited by the context window of the underlying model. As the search trajectory grows, the meta-prompt must either truncate older entries (losing potentially valuable information) or compress the trajectory (losing detail). This creates a fundamental tension between search depth (more iterations) and search awareness (more context per iteration). Current systems address this with summarization and hierarchical memory, but these are imperfect approximations.

    \item \textbf{Search space representation:} The choice of representation for candidates significantly impacts search effectiveness. Code representations (as in EvoPrompting) are expressive but can produce syntactically invalid offspring; structured representations (as in traditional NAS) are well-formed but limit the space of discoverable solutions. The ``representation gap'' between what the LLM can reason about and what the evaluation infrastructure can execute remains a significant engineering challenge.

    \item \textbf{Evaluation cost:} Each search iteration requires at least one evaluation, and for complex artifacts (e.g., full ML pipelines, agent architectures), evaluation may require training a model, running benchmarks, or deploying a system. This cost limits the number of search iterations that are practically feasible. AlphaEvolve's dual-model strategy (Flash for breadth, Pro for depth) is one approach to managing this cost, but the fundamental tradeoff between search breadth and evaluation depth remains.

    \item \textbf{Mode collapse and diversity loss:} LLM-based search operators tend to converge on similar solutions, particularly when the meta-prompt contains many high-scoring examples. This ``mode collapse'' reduces the diversity of the search and can cause the system to miss superior solutions in unexplored regions. Quality-diversity algorithms like MAP-Elites partially address this by maintaining diverse archives, but the variation operator itself must be diverse enough to populate those archives.
\end{enumerate}

\subsubsection{Analysis}

The key trend in the Search Loop is the increasing use of LLMs as universal search operators. Traditional algorithms require hand-coded operators for each search space; LLM-based operators are universal, applicable to any artifact expressible in natural language or code. This universality comes at the cost of reduced efficiency on well-structured spaces where domain-specific operators can exploit problem structure. The most promising direction is hybrid search that combines LLM-based operators for novelty generation with domain-specific operators for efficient local refinement. The transition from single-model search (OPRO) to multi-model search (AlphaEvolve's Flash+Pro) to multi-agent search (NADER, ADAS) reflects increasing sophistication in managing the exploration-exploitation tradeoff.


\subsection{Loop 3: Evaluator}
\label{sec:evaluator_loop}

The Evaluator Loop provides selection pressure that drives self-evolution. Without evaluation, generation is random search; with evaluation, generation becomes directed search. The Evaluator Loop determines the direction of evolution, and its quality fundamentally bounds the quality of the entire self-evolution process. As the common adage in evolutionary computation states: ``you get what you select for, not what you want.'' The Evaluator Loop is the mechanism by which a self-evolving system specifies what it wants.

\subsubsection{Execution Feedback}

\paragraph{Self-Debug.}
Self-Debug~\citep{chen2024selfdebug} introduces the principle of \emph{rubber duck debugging} for LLMs: the model explains its own code execution traces to identify and fix errors. When a generated program fails a test case, Self-Debug provides the execution trace as feedback, including the values of key variables at each step, the control flow taken, and the point at which the output diverges from the expected result. The LLM then generates a natural language explanation of what went wrong and proposes a fix. This approach achieves dramatic improvements: +12\% absolute accuracy on the TransCoder code translation benchmark and +9\% on the Spider text-to-SQL benchmark, without any additional training. The key insight is that execution traces provide a much richer evaluation signal than binary pass/fail---they contain the specific information needed to diagnose and repair errors, transforming evaluation from a filter into a feedback mechanism.

\paragraph{Execution-based code evaluation.}
Beyond Self-Debug, execution feedback has become a standard evaluation mechanism in code generation systems. The paradigm is straightforward: generate code, execute it against test cases, and use the pass rate as the evaluation score. However, the design of the test suite itself is a critical and often overlooked component. A test suite that is too easy will not distinguish between good and excellent solutions; a test suite that is too hard will reject all candidates, providing no gradient for improvement. The most effective systems use curated test suites with varying difficulty levels, enabling fine-grained discrimination between candidates.

\subsubsection{Mathematical Verification}

\paragraph{FunSearch.}
FunSearch~\citep{romera2024funsearch} represents the gold standard of evaluation: mathematical proof. The system evolves programs that compute mathematical objects (e.g., sets for the cap set problem, algorithms for bin packing) and verifies their correctness through formal mathematical checks. For the cap set problem, FunSearch discovered new constructions that exceeded the best previously known bounds, providing the first improvement over Strassen's matrix multiplication algorithm in 56 years for specific configurations. The strength of mathematical verification is that it provides \emph{provable guarantees}---a verified solution is guaranteed to be correct, not merely empirically likely to be correct. This eliminates the possibility of reward hacking, where the system exploits weaknesses in the evaluator.

\paragraph{AlphaEvolve's multi-dimensional scoring.}
AlphaEvolve~\citep{novikov2025alphaevolve} extends mathematical verification with multi-dimensional scoring. Rather than evaluating candidates on a single criterion, AlphaEvolve scores on multiple axes: correctness (does the algorithm produce the right output?), efficiency (how many operations does it require?), and novelty (does it differ from known solutions?). This multi-dimensional evaluation enables the MAP-Elites quality-diversity algorithm to maintain a diverse archive of high-quality solutions across multiple behavioral dimensions. In practice, AlphaEvolve applied this evaluation framework to achieve: 0.7\% compute recovery in Google's Borg data center scheduling system (by discovering more efficient scheduling algorithms), 23\% speedup in FlashAttention kernel computation, and progress on over 50 open mathematical problems. The multi-dimensional scoring is critical for these results: optimizing purely for speed might produce incorrect algorithms, while optimizing purely for correctness might miss efficiency improvements.

\subsubsection{Reward Models}

\paragraph{ReST-EM.}
ReST-EM (Reinforced Self-Training with Expectation-Maximization)~\citep{gulcehre2023rest} uses a learned reward model to filter generated samples for training. The EM algorithm alternates between generating samples (E-step) and training the model on high-reward samples (M-step). The reward model serves as a proxy for human judgment, enabling the system to evaluate candidates at scale without human annotation. However, reward models are subject to \emph{reward hacking}: the generator may learn to produce outputs that score highly under the reward model but do not actually improve on the true objective. This is a fundamental limitation of learned evaluators.

\paragraph{Constitutional AI.}
Constitutional AI~\citep{bai2022constitutional} introduces a principle-based evaluation framework. The system evaluates its own outputs against a set of constitutional principles---high-level rules about helpfulness, harmlessness, and honesty. A supervising LLM critiques the output against each principle and provides a structured assessment. This approach is particularly valuable for evaluating properties that are difficult to formalize in code, such as whether a response is helpful or whether an agent's behavior is aligned with user intent. Constitutional AI demonstrates that LLMs can serve as evaluators of their own outputs, provided the evaluation criteria are clearly specified.

\subsubsection{Quality-Diversity Metrics}

\paragraph{MAP-Elites.}
MAP-Elites~\citep{mouret2015mapelites} evaluates candidates on both quality (performance on the objective) and diversity (distinctiveness along behavioral dimensions). The algorithm discretizes the behavioral space into a grid and maintains the highest-performing solution in each cell. This ensures that the search explores the full breadth of the solution space rather than converging on a single high-performing region. MAP-Elites is used by both AlphaEvolve and LLMatic as their primary archive management strategy. The pyribs library provides a standardized implementation of MAP-Elites and related quality-diversity algorithms, facilitating adoption in new systems.

\paragraph{Behavioral descriptors.}
The choice of behavioral descriptors---the dimensions along which diversity is measured---is critical for quality-diversity search. For algorithm discovery, descriptors might include the number of operations, the types of operations used, or structural properties of the solution. For agent architectures, descriptors might include the number of LLM calls per inference, the ratio of internal reasoning to external tool usage, or the depth of the agent hierarchy. Poorly chosen descriptors can lead to meaningless diversity (solutions that differ in irrelevant ways) or can fragment the archive into too many cells, diluting the search effort.

\subsubsection{Formal Algorithm Description}

We formalize the Evaluator Loop as a composite scoring function:

\begin{enumerate}
    \item \textbf{Input:} Candidate solution $x$, evaluation specification $\mathcal{E}$.
    \item \textbf{Multi-mechanism evaluation:}
    \begin{enumerate}
        \item \textbf{Execution score:} $s_{\text{exec}} = \frac{1}{|\mathcal{T}|} \sum_{t \in \mathcal{T}} \mathbb{1}[\text{exec}(x, t) = y_t]$ where $\mathcal{T}$ is the test suite and $y_t$ are expected outputs.
        \item \textbf{Verification score:} $s_{\text{verify}} = \mathbb{1}[\text{verify}(x)]$ if a formal verifier is available; otherwise, undefined.
        \item \textbf{Reward model score:} $s_{\text{RM}} = R_\theta(x)$ where $R_\theta$ is the learned reward model.
        \item \textbf{Quality-diversity placement:} Compute behavioral descriptor $b(x) = (b_1, \ldots, b_d)$ and determine the corresponding cell $c = \text{discretize}(b(x))$.
    \end{enumerate}
    \item \textbf{Composite score:} $s(x) = w_1 \cdot s_{\text{exec}} + w_2 \cdot s_{\text{verify}} + w_3 \cdot s_{\text{RM}}$ with weights $w_i$ determined by the evaluation specification.
    \item \textbf{Archive update:} If $s(x) > s(x_c)$ where $x_c$ is the current occupant of cell $c$, replace $x_c$ with $x$.
    \item \textbf{Output:} Score $s(x)$, behavioral descriptor $b(x)$, and archive update decision.
\end{enumerate}

This formalization highlights the composability of evaluation mechanisms: the same candidate can be evaluated by multiple mechanisms simultaneously, and the composite score can be weighted according to the reliability of each mechanism.

\subsubsection{Cross-Loop Interactions}

The Evaluator Loop is deeply intertwined with the other loops:

\begin{itemize}
    \item \textbf{Search Loop:} The Evaluator provides the objective function $f$ that guides the Search Loop. The gradient landscape of $f$ determines how effectively search can navigate the solution space. Smooth, informative gradients (where small changes in the candidate produce predictable changes in the score) enable efficient search; noisy or discontinuous gradients lead to inefficient or misguided search. The design of $f$ is therefore one of the most impactful decisions in any self-evolving system.
    \item \textbf{Reflection Loop:} While the Evaluator produces scalar scores, the Reflection Loop converts those scores into structured feedback. Self-Debug exemplifies this interaction: execution traces (evaluator output) are fed to the LLM for natural language analysis (reflection), producing actionable debugging suggestions. The Evaluator Loop can also inform the Reflection Loop about which types of errors are most common, enabling the reflection mechanism to develop specialized error-correction strategies.
    \item \textbf{Population Loop:} The Evaluator determines which candidates survive in the population. In MAP-Elites, the evaluation score and behavioral descriptor jointly determine a candidate's fate: a candidate that achieves a higher score in its behavioral cell replaces the current occupant, while a candidate that achieves a lower score is discarded regardless of its other properties.
    \item \textbf{Specification-to-Execution Loop:} The Spec Loop defines the evaluation criteria (e.g., ``optimize for both accuracy and latency''), which the Evaluator Loop operationalizes as concrete metrics. When the Evaluator reveals that these criteria are mutually exclusive or poorly defined, it feeds back to the Spec Loop for revision.
\end{itemize}

\subsubsection{Limitations Analysis}

The Evaluator Loop faces several critical limitations:

\begin{enumerate}
    \item \textbf{Reward hacking:} When the evaluator is a learned model (reward model, verifier, or another LLM), the system may learn to exploit weaknesses in the evaluator rather than genuinely improving. This is the ``Goodhart's law'' of self-evolving systems: when a measure becomes a target, it ceases to be a good measure. Reward hacking has been observed in RLHF systems, where models learn to produce verbose, seemingly-helpful responses that score well under reward models but are not actually preferred by humans.

    \item \textbf{Evaluation cost and scalability:} Comprehensive evaluation is expensive. Running a full benchmark suite for each candidate may require minutes to hours of computation; training a model from scratch for architecture evaluation requires hours to days. This limits the number of candidates that can be evaluated and, consequently, the breadth of the search. Approximate evaluators (e.g., proxy models, early stopping) can reduce cost but introduce approximation error.

    \item \textbf{Multi-objective tradeoffs:} Real-world systems must optimize multiple objectives simultaneously (accuracy, latency, memory usage, fairness, robustness). These objectives often conflict: the most accurate model may be too slow, the fastest model may be unfair. Current evaluation frameworks typically handle multi-objective evaluation through weighted combination or Pareto fronts, but both approaches require subjective decisions about the relative importance of objectives.

    \item \textbf{Distribution shift in evaluation:} The evaluation distribution may differ from the deployment distribution. A model that scores well on a benchmark may fail in production due to differences in data distribution, user behavior, or environmental conditions. This is particularly problematic for self-evolving systems that optimize directly for benchmark performance: they may overfit to the benchmark at the expense of generalization.
\end{enumerate}

\subsubsection{Analysis}

The Evaluator Loop is the bottleneck of self-evolving systems. The quality of evolution is fundamentally limited by the quality of evaluation. A system with a perfect evaluator can evolve arbitrarily complex solutions; a system with a noisy evaluator will exploit the evaluator's weaknesses. The most promising direction combines multiple evaluation mechanisms: execution for verifiable properties (correctness, efficiency), reward models for subjective quality (helpfulness, alignment), and quality-diversity metrics for exploration (ensuring breadth of search). AlphaEvolve's success demonstrates the power of this multi-mechanism approach, using mathematical verification for correctness, operation counting for efficiency, and MAP-Elites for diversity.


\subsection{Loop 4: Reflection}
\label{sec:reflection_loop}

The Reflection Loop converts evaluation outcomes into structured, actionable knowledge that improves future generation. While the Evaluator Loop produces scalar scores (``this scores 0.73''), the Reflection Loop produces rich analyses (``this fails because it does not handle edge case X; to fix this, modify component Y''). This is what distinguishes self-evolving systems from simple optimization: the ability to extract and transfer knowledge from individual experiences to improve the general strategy.

\subsubsection{Verbal Reinforcement Learning}

\paragraph{Reflexion.}
Reflexion~\citep{shinn2023reflexion} introduces verbal reinforcement learning: instead of updating parameters through gradient descent, the system updates a linguistic memory buffer through reflection. After each attempt at a task, the agent generates a natural language ``verbal gradient''---a description of what went wrong, why it went wrong, and what should be done differently. This verbal gradient is stored in a persistent memory and provided as additional context in future attempts, enabling the agent to learn from its mistakes without modifying its underlying parameters.

Reflexion achieves striking results. On the HumanEval code generation benchmark, Reflexion with GPT-3.5 achieves 91\% pass@1, surpassing GPT-4's 80\% without any parameter updates. On the AlfWorld interactive environment benchmark, Reflexion achieves 97\% success rate, compared to approximately 75\% for the base agent. These results demonstrate that linguistic memory can be a more effective learning mechanism than parameter updates for certain tasks, particularly those requiring episodic reasoning about failures.

The key insight of Reflexion is that natural language provides a far richer representation for feedback than scalar rewards. A scalar reward of 0 indicates failure but says nothing about why the failure occurred or how to fix it. A verbal gradient like ``the binary search implementation fails when the array contains duplicate elements because the midpoint calculation does not account for equal elements'' provides specific, actionable information that directly guides future behavior.

\subsubsection{Iterative Self-Refinement}

\paragraph{Self-Refine.}
Self-Refine~\citep{madaan2023selfrefine} implements the simplest form of reflection: the same model generates, critiques, and refines its own output in an iterative loop. The process consists of three steps repeated until convergence: (1) \textbf{Generate} an initial output; (2) \textbf{Critique} the output by identifying specific weaknesses, errors, or areas for improvement; (3) \textbf{Refine} the output based on the critique. Self-Refine achieves approximately 20\% average improvement across seven diverse tasks without any training or external feedback, with particularly strong gains in code optimization (+28\%) and mathematical reasoning (+11 percentage points).

The surprising effectiveness of Self-Refine stems from the asymmetry between generation and evaluation: LLMs are better at evaluating given outputs than at generating optimal outputs from scratch. This asymmetry is analogous to the distinction between recognition and recall in human cognition. By separating the generation and evaluation phases, Self-Refine enables the model to apply its evaluative capabilities to iteratively improve its generative output.

\subsubsection{Language Backpropagation}

\paragraph{Agent Symbolic Learning.}
Agent Symbolic Learning~\citep{zhou2024agentsymbolic} implements full backpropagation in natural language space, extending the reflection paradigm from individual outputs to entire agent architectures. The key insight is that an LLM-based agent can be viewed as a symbolic network with learnable ``weights'': the prompts that define the agent's behavior, the tool descriptions that specify how the agent interacts with external systems, and the pipeline configurations that determine the agent's control flow.

The Agent Symbolic Learning process consists of four phases:
\begin{enumerate}
    \item \textbf{Forward pass:} The agent executes a task using its current symbolic weights, producing a trajectory of actions and a final output.
    \item \textbf{Loss computation:} The output is evaluated against the ground truth, producing a language-based loss description.
    \item \textbf{Backward pass:} Language gradients are computed by analyzing the trajectory to identify which symbolic weights (prompts, tool descriptions) contributed to errors. These gradients are natural language descriptions of how each weight should be modified.
    \item \textbf{Weight update:} Symbolic weights are updated using language-based optimizers that modify prompts, tool descriptions, and pipeline configurations based on the computed gradients.
\end{enumerate}

This framework achieves state-of-the-art results on HotPotQA (F1=39.1), MATH (60.7\%), and HumanEval (73.2\%), demonstrating that language-based optimization can be competitive with parameter-based optimization. The advantage of language backpropagation is its interpretability: every optimization step is expressed in natural language that humans can inspect, understand, and modify.

\subsubsection{Self-Play and Task Proposal}

\paragraph{Absolute Zero.}
Absolute Zero~\citep{zhao2025absolutezero} extends the Reflection Loop beyond reflecting on solutions to reflecting on the tasks themselves. The system operates in a self-play regime where one component proposes tasks and another component solves them. The task proposal component learns to generate tasks that are at the right difficulty level---challenging enough to drive improvement but not so hard that they are impossible. This creates a curriculum that adapts to the solver's current capability, enabling continuous improvement without external task specification. Absolute Zero achieves state-of-the-art performance at the 7B parameter scale, outperforming models trained on human-curated data, by learning to generate its own training tasks through reflection on the solver's capability profile.

\paragraph{RISE.}
RISE~\citep{qu2024rise} trains LLMs for iterative self-correction through reinforcement learning, achieving +10 percentage points on GSM8K with Llama2. The key innovation is framing self-correction as a RL problem: the model learns not only to generate correct initial answers but also to effectively correct its own mistakes when given the opportunity. RISE demonstrates that self-correction is a learnable skill that can be explicitly trained, rather than an emergent property that appears at sufficient scale. The system uses a multi-turn RL training procedure where the model first generates an answer, then receives feedback (its own previous answer and any available verification), and then generates a corrected answer.

\subsubsection{Formal Algorithm Description}

We formalize the Reflection Loop as follows:

\begin{enumerate}
    \item \textbf{Input:} Candidate trajectory $\tau = (x, a_1, a_2, \ldots, a_n, \hat{y})$ where $x$ is the input, $a_i$ are intermediate actions, and $\hat{y}$ is the output. Evaluation result $e = (s, \delta)$ where $s$ is the score and $\delta$ is the execution trace or error description.
    \item \textbf{Failure localization:} Identify the step(s) $a_i$ that contributed most to the failure, producing localization $L \subseteq \{a_1, \ldots, a_n\}$.
    \item \textbf{Root cause analysis:} For each localized step $a_i \in L$, generate a natural language explanation: $r_i = \mathcal{M}(\text{``Explain why } a_i \text{ failed given context } \delta\text{''})$.
    \item \textbf{Lesson extraction:} Aggregate root causes into actionable lessons: $\ell = \mathcal{M}(\text{``Based on } \{r_i\}, \text{what general principles should be followed?''})$.
    \item \textbf{Memory update:} Store $\ell$ in the reflection memory $\mathcal{R}$. Optionally, consolidate with existing lessons to avoid redundancy.
    \item \textbf{Application:} For the next task, retrieve relevant lessons from $\mathcal{R}$ and include them as additional context in the generation prompt.
    \item \textbf{Output:} Updated reflection memory $\mathcal{R}$ and lesson-augmented generation prompt.
\end{enumerate}

This formalization highlights the key design choices: the failure localization strategy (step 2), the granularity of root cause analysis (step 3), and the retrieval mechanism for applying lessons (step 6).

\subsubsection{Cross-Loop Interactions}

The Reflection Loop interacts with all other loops as the mechanism that converts raw feedback into actionable knowledge:

\begin{itemize}
    \item \textbf{Search Loop:} Reflection informs search strategy by identifying productive and unproductive search directions. Reflexion's verbal gradients effectively bias the LLM's generation toward avoiding known failure modes, improving the efficiency of OPRO-style optimization. In architecture search, reflection on failed architectures can identify structural patterns that are unlikely to succeed, pruning the search space.

    \item \textbf{Evaluator Loop:} The Reflection Loop depends on the Evaluator Loop for input---without rich evaluation signals, reflection has little to work with. Self-Debug's debugging suggestions rely on execution traces (evaluator output); Reflexion's verbal gradients rely on episode outcomes and reward signals. Richer evaluator output (traces, intermediate states, partial scores) enables richer reflection.

    \item \textbf{Population Loop:} Reflection can operate at the population level, identifying patterns across multiple candidates rather than analyzing each in isolation. For example, if multiple architectures in the population fail for similar reasons, the Reflection Loop can extract a general lesson about architectural constraints. Population-level reflection is more robust than individual-level reflection because it is less sensitive to the idiosyncrasies of individual candidates.

    \item \textbf{Specification-to-Execution Loop:} When reflection reveals systematic failures that cannot be addressed through search alone, it can trigger re-specification. For example, if the reflection mechanism consistently identifies that the task requires multi-step reasoning but the current specification generates single-step pipelines, this insight can be fed back to the Spec Loop to generate more appropriate pipeline structures.
\end{itemize}

\subsubsection{Limitations Analysis}

The Reflection Loop faces several important limitations:

\begin{enumerate}
    \item \textbf{Hallucinated reflections:} LLMs may generate plausible-sounding but incorrect explanations for failures. A reflection that incorrectly attributes failure to the wrong cause will actively harm future performance by guiding the system away from productive directions. This is particularly problematic when the task is complex and the true failure mode is non-obvious---the LLM may generate a superficially convincing explanation that misses the root cause.

    \item \textbf{Compounding errors in iterative reflection:} When reflection is applied iteratively (as in Self-Refine), errors in early reflections can compound, leading the system progressively further from the correct solution. A single incorrect self-critique can redirect refinement in the wrong direction, and subsequent critiques may fail to detect the misdirection because they build on the flawed foundation.

    \item \textbf{Specificity-generalization tradeoff:} Reflections that are highly specific to the current failure (``change variable name from \texttt{n} to \texttt{num\_elements}'') are immediately actionable but may not generalize to new situations. Reflections that are highly general (``always check for edge cases'') are transferable but require additional reasoning to apply to specific situations. The most effective systems balance specificity and generality, but finding this balance is itself a challenging meta-learning problem.

    \item \textbf{Scalability of reflection memory:} As the reflection memory $\mathcal{R}$ grows, retrieving relevant lessons becomes increasingly difficult. Simple retrieval strategies (e.g., appending all lessons to the prompt) are limited by context window constraints; sophisticated retrieval strategies (e.g., embedding-based similarity search) require additional infrastructure and may surface lessons that are superficially similar but substantively different. Managing the growth and organization of reflection memory is an open research problem.
\end{enumerate}

\subsubsection{Analysis}

The Reflection Loop is uniquely LLM-native---it has no direct classical analogue in traditional optimization or evolutionary computation. While gradient descent computes numerical gradients and genetic algorithms compute fitness differences, neither produces the rich, structured, language-based analyses that characterize LLM reflection. Natural language reflection is fundamentally enabled by the ability of LLMs to generate and process structured analyses, making this loop a defining feature of the LLM-era approach to self-evolution. The key tension is between specific reflections (immediately actionable but may not generalize) and general reflections (transferable but require additional reasoning). The most effective systems combine both, as demonstrated by Agent Symbolic Learning's ability to perform both localized error correction and general principle extraction.


\subsection{Loop 5: Population}
\label{sec:population_loop}

The Population Loop maintains a diverse collection of candidates and applies population-level operations---selection, mutation, recombination, and specialization---to evolve the population over time. Unlike the Search Loop, which may operate on a single trajectory, the Population Loop explicitly manages multiple simultaneous candidates, enabling parallel exploration, recombination of partial solutions, and preservation of diverse strategies.

\subsubsection{MAP-Elites Quality-Diversity Search}

\paragraph{AlphaEvolve.}
AlphaEvolve~\citep{novikov2025alphaevolve} exemplifies the power of quality-diversity search at scale. The system maintains a MAP-Elites archive indexed by behavioral descriptors that capture distinct structural properties of algorithms. Each cell in the archive contains the highest-performing algorithm with those behavioral characteristics. The dual-model search strategy---Gemini Flash for generating diverse candidate mutations and Gemini Pro for refining the most promising ones---ensures that the archive is populated with both broad and deep solutions.

AlphaEvolve's results are remarkable across multiple domains:
\begin{itemize}
    \item \textbf{Matrix multiplication:} Discovered a 48-multiplication algorithm for $4\times4$ complex matrix multiplication, the first improvement over Strassen's algorithm in this dimension since 1969.
    \item \textbf{Mathematical discovery:} Made progress on over 50 open mathematical problems, including new bounds for the cap set problem and improved kissing number bounds.
    \item \textbf{Practical systems:} Improved Google's Borg data center scheduling by 0.7\% compute recovery (recovering significant computational resources at Google's scale) and achieved 23\% speedup in FlashAttention kernel computation.
\end{itemize}

These results demonstrate that quality-diversity search with LLM-based variation operators can discover solutions that elude both human experts and traditional optimization algorithms. The key innovation is the combination of MAP-Elites' diversity preservation with the LLM's ability to perform informed variation---proposing mutations that are likely to improve specific aspects of a candidate based on its evaluation history.

\subsubsection{Evolving Optimizers}

\paragraph{LLaMEA.}
LLaMEA~\citep{van2024llaMEA} applies the Population Loop at the meta-level: the population consists of optimization algorithms themselves. The LLM generates, evaluates, and evolves metaheuristic algorithms, representing the ``improving the improvers'' paradigm. Each individual in the population is a complete optimization algorithm encoded as code. The LLM proposes new algorithms by reading the current population and their performance histories, identifying patterns that correlate with high performance, and generating novel algorithms that combine successful elements.

The meta-level evolution enabled by LLaMEA raises an intriguing possibility: \emph{recursive self-improvement} at the algorithm level. If LLaMEA can evolve optimizers that are themselves capable of evolving optimizers, the system could potentially enter a positive feedback loop of increasing optimization capability. Current results show that LLaMEA-discovered optimizers are competitive with hand-designed metaheuristics on standard benchmark functions (BBOB), but the recursive regime remains speculative.

\subsubsection{Evolving Code Populations}

\paragraph{FunSearch.}
FunSearch~\citep{romera2024funsearch} maintains a population of program variants evolving through LLM-proposed mutations with correctness-based selection. The system operates on programs expressed in a domain-specific language, with each program computing a mathematical object (e.g., a heuristic function, a set construction). The evolution process alternates between mutation (the LLM proposes modifications to existing programs) and selection (programs that produce better mathematical objects replace their parents in the population). FunSearch's population structure is island-based: multiple sub-populations evolve independently with occasional migration, preventing premature convergence and enabling the discovery of qualitatively different solutions.

\paragraph{DGM.}
DGM (Darwin--G\"odel Machine)~\citep{zhang2025dgm} maintains an open-ended archive of agent designs that grows and specializes over time. Unlike fixed-population evolutionary algorithms, DGM's archive is unbounded: new designs are added whenever they demonstrate improvement on any evaluation dimension, and existing designs are never removed. This open-ended structure enables DGM to accumulate a growing library of agent capabilities. DGM achieves 50\% on SWE-bench (software engineering tasks) and 30.7\% on Polyglot (multi-language code generation), demonstrating that population-based evolution can produce competitive coding agents. The open-ended archive also enables \emph{compositional} improvement: new agents can inherit and combine capabilities from multiple existing agents in the archive, producing hybrid designs that outperform any single parent.

\subsubsection{Evolving Agent Architectures}

\paragraph{AgentEvolver.}
AgentEvolver applies the Population Loop to agent tool usage, evolving how agents select, combine, and parameterize external tools. Each individual in the population is a complete agent configuration specifying which tools are available, how they are described to the agent, and what constraints govern their use. The evolution process optimizes for task performance across a suite of agent benchmarks, discovering tool configurations that outperform human-designed ones. The key insight is that the way tools are described to an agent is as important as the tools themselves: a well-described limited tool set can outperform a poorly-described comprehensive tool set.

\paragraph{EvoAgent.}
EvoAgent~\citep{wang2024evoagent} evolves multi-agent configurations, searching over the space of agent roles, communication protocols, and organizational structures. Each individual in the population specifies a complete multi-agent system: the number of agents, their roles and capabilities, the communication topology, and the decision-making protocol. Evolution discovers organizational structures that are effective for specific task types, such as hierarchical structures for tasks requiring top-down coordination and flat structures for tasks benefiting from diverse perspectives.

\subsubsection{Formal Algorithm Description}

We formalize the Population Loop as follows:

\begin{enumerate}
    \item \textbf{Input:} Initial population $\mathcal{P}_0 = \{x_1, x_2, \ldots, x_N\}$, fitness function $f$, variation operators $\mathcal{V}_{\text{mut}}, \mathcal{V}_{\text{cross}}$, selection operator $\mathcal{S}$, archive $\mathcal{A}$.
    \item \textbf{Initialize archive:} Evaluate all individuals and populate the archive: $\mathcal{A} = \{(x_i, f(x_i), b(x_i))\}_{i=1}^{N}$ where $b(x_i)$ is the behavioral descriptor.
    \item \textbf{For each generation $g = 1, 2, \ldots, G$:}
    \begin{enumerate}
        \item \textbf{Selection:} Select parent set $\mathcal{P}_{\text{parent}} \subseteq \mathcal{A}$ using tournament selection, fitness-proportionate selection, or quality-diversity cell sampling.
        \item \textbf{Variation:} For each selected parent pair $(p_1, p_2) \in \mathcal{P}_{\text{parent}}$, generate offspring:
        \begin{itemize}
            \item Mutation: $o_{\text{mut}} = \mathcal{V}_{\text{mut}}(p_1) = \mathcal{M}(\text{``Modify this artifact while preserving its core functionality: } p_1\text{''})$
            \item Crossover: $o_{\text{cross}} = \mathcal{V}_{\text{cross}}(p_1, p_2) = \mathcal{M}(\text{``Combine the best elements of these two artifacts: } p_1, p_2\text{''})$
        \end{itemize}
        \item \textbf{Evaluation:} Compute fitness and behavioral descriptors for each offspring: $(f(o), b(o))$ for each offspring $o$.
        \item \textbf{Archive update:} For each offspring, determine its behavioral cell $c = \text{discretize}(b(o))$. If $f(o) > f(\mathcal{A}[c])$, replace the current occupant with $o$.
    \end{enumerate}
    \item \textbf{Output:} Final archive $\mathcal{A}$ containing the best-performing solution in each behavioral cell.
\end{enumerate}

This formalization highlights the key differences from the Search Loop: the explicit maintenance of a population (or archive), the application of both mutation and crossover operators, and the quality-diversity archive update rule that preserves diverse solutions.

\subsubsection{Cross-Loop Interactions}

The Population Loop is the most interconnected of the five loops, depending on and enhancing all others:

\begin{itemize}
    \item \textbf{Search Loop:} The Population Loop extends single-trajectory search to multi-trajectory search. Each individual in the population follows its own search trajectory, and the Population Loop's selection and variation operators determine how these trajectories interact. Crossover enables the combination of partial solutions discovered by different trajectories, while selection ensures that resources are focused on the most promising directions.

    \item \textbf{Evaluator Loop:} The Population Loop depends heavily on the Evaluator Loop for both quality assessment and behavioral characterization. The quality assessment (fitness evaluation) determines which individuals are selected for reproduction; the behavioral characterization (behavioral descriptors) determines where individuals are placed in the MAP-Elites archive. Changes in the evaluator---such as adding new evaluation dimensions or changing behavioral descriptors---can dramatically alter the population dynamics.

    \item \textbf{Reflection Loop:} Population-level reflection is more powerful than individual-level reflection because it can identify patterns across multiple candidates. For example, if all individuals in a particular behavioral cell fail for the same reason, this provides stronger evidence for a systematic issue than a single failure. The Population Loop can also provide the Reflection Loop with a diverse set of failure cases, enabling more robust lesson extraction.

    \item \textbf{Specification-to-Execution Loop:} The Population Loop can generate multiple specification-to-execution pipelines in parallel, each using a different decomposition strategy or component library. This population-based approach to specification is particularly valuable when the optimal pipeline structure is unclear, as it allows the system to explore multiple structural hypotheses simultaneously.
\end{itemize}

\subsubsection{Limitations Analysis}

The Population Loop faces several significant limitations:

\begin{enumerate}
    \item \textbf{Computational cost:} Maintaining a population requires evaluating many more candidates than single-trajectory search. Each generation requires evaluating all offspring, and the population must be large enough to maintain meaningful diversity. For expensive evaluation functions (e.g., training a model for each architecture), this cost can be prohibitive. Surrogate models and fitness predictors can reduce the number of full evaluations, but they introduce their own approximation errors.

    \item \textbf{Representational challenges for crossover:} While LLM-based mutation is well-understood (the LLM modifies a single artifact), LLM-based crossover (combining elements from two artifacts) is more challenging. The LLM must understand which elements of each parent are transferable and how to combine them coherently. Code crossover is particularly difficult because the combined code must be syntactically valid and semantically coherent, not merely a concatenation of parent fragments.

    \item \textbf{Behavioral descriptor design:} The effectiveness of quality-diversity algorithms like MAP-Elites depends critically on the choice of behavioral descriptors. Poorly chosen descriptors may fragment the archive into meaningless cells (where solutions differ in irrelevant ways) or collapse the archive into too few cells (where diversity is lost). The choice of descriptors requires domain expertise and is difficult to automate.

    \item \textbf{Scaling to open-ended evolution:} DGM's open-ended archive raises the question of how to manage unbounded population growth. As the archive accumulates thousands or millions of designs, searching for relevant ancestors, computing behavioral descriptors, and maintaining the archive become increasingly expensive. Open-ended evolution also requires mechanisms for recognizing and preserving genuinely novel innovations, as opposed to minor variations on existing themes.
\end{enumerate}

\subsubsection{Analysis}

The LLM era has transformed the Population Loop in two fundamental ways. First, LLMs serve as \emph{universal variation operators}: the same LLM can perform mutation and crossover on code, natural language, mathematical expressions, agent configurations, or any other artifact expressible as text. This eliminates the need for hand-designed variation operators for each domain, dramatically reducing the barrier to applying evolutionary methods to new problem domains. Second, LLMs can perform \emph{informed variation} by reading candidate histories and evaluation results, proposing mutations that are likely to improve specific aspects of a candidate. This informed variation is qualitatively different from the random variation of traditional evolutionary algorithms, as it can exploit the structure of the problem to propose more intelligent modifications.

The key challenge for the Population Loop is computational cost, which is mitigated by the inherent parallelizability of evaluation (all candidates can be evaluated simultaneously) and the efficiency gains from informed variation (fewer generations needed to discover high-quality solutions). The most promising direction is the integration of quality-diversity algorithms with LLM-based variation, as demonstrated by AlphaEvolve, which combines broad exploration (diversity preservation) with deep refinement (informed variation).

\subsection{Compositional Patterns}

Beyond individual loops, the most powerful self-evolving systems combine multiple loops into compositional patterns. We identify several recurring compositions:

\paragraph{Search + Evaluator (Optimization).}
The most basic composition pairs a search mechanism with an evaluator, producing optimization. OPRO, prompt optimization systems, and traditional NAS all follow this pattern. The quality of optimization is determined by the search strategy and the evaluator reliability.

\paragraph{Search + Evaluator + Reflection (Learning).}
Adding reflection to optimization produces learning---the ability to improve not just individual solutions but the search strategy itself. Reflexion exemplifies this pattern: the verbal gradient from reflection modifies the search behavior, enabling the system to avoid repeating mistakes.

\paragraph{Population + Evaluator + Quality-Diversity (Evolution).}
Combining population management with evaluation and quality-diversity metrics produces evolution in the biological sense: a diverse population adapting to environmental pressure. AlphaEvolve exemplifies this pattern with its MAP-Elites archive.

\paragraph{Full Composition (Self-Evolution).}
The most advanced systems combine all five loops: specification defines the task, search explores the solution space, evaluation provides selection pressure, reflection extracts knowledge, and population management maintains diversity. This full composition enables open-ended self-improvement where the system can improve at multiple levels simultaneously: improving individual solutions, improving the search strategy, improving the evaluation criteria, and improving the population structure.


\subsection{Summary}

The Five Evolution Loops taxonomy provides a unified framework for understanding the diverse landscape of AI self-evolution. By identifying five fundamental types of evolutionary cycles---Specification-to-Execution, Search, Evaluator, Reflection, and Population---and mapping their occurrence across five research domains, we establish a common language that enables systematic comparison and cross-pollination.

Several key insights emerge from this taxonomy. First, the loops are not independent but deeply interconnected: the quality of each loop constrains and is constrained by the quality of the others. The most impactful improvements often come from strengthening the weakest loop in the chain. Second, the Reflection Loop is the most distinctive contribution of the LLM era, enabling a form of self-improvement that has no direct analogue in classical optimization or evolutionary computation. Third, the Population Loop, when combined with quality-diversity algorithms and LLM-based variation operators, enables the discovery of solutions that exceed human expert capability, as demonstrated by AlphaEvolve's results on matrix multiplication and mathematical discovery.

The taxonomy also reveals significant gaps and opportunities. The Specification-to-Execution Loop lacks robust iterative refinement mechanisms; the Evaluator Loop remains the primary bottleneck; the Reflection Loop is vulnerable to hallucinated self-analysis; and the Population Loop is underexplored in agent frameworks. Addressing these gaps represents the most promising direction for advancing the state of the art in self-evolving AI.

In the following sections, we apply this taxonomy to analyze specific systems and methods in detail, examining how the compositional patterns identified here manifest in practice and what design principles emerge from the most successful systems.

\subsection{Design Principles for Self-Evolving Systems}

Based on our analysis of the Five Evolution Loops across multiple systems and domains, we distill several design principles that characterize the most successful self-evolving systems.

\paragraph{Principle 1: Strengthen the weakest loop.}
The overall quality of self-evolution is bounded by the quality of the weakest loop in the chain. AlphaEvolve's success is partly attributable to its strong evaluation (mathematical verification), which enables effective search and population management. Systems with weak evaluators tend to exploit evaluator weaknesses rather than genuinely improving, regardless of how sophisticated their search or population mechanisms may be. Investing in evaluation infrastructure---better test suites, formal verifiers, diverse reward models---often yields more improvement than investing in more sophisticated search algorithms.

\paragraph{Principle 2: LLMs are universal but not optimal operators.}
LLMs can serve as search, variation, and reflection operators for any artifact expressible in text, but they are not necessarily the most efficient operators for well-structured problems. The most effective systems use LLMs where their universality is most valuable (novelty generation, cross-domain transfer, informed variation) and fall back to domain-specific methods where they are available and efficient (gradient-based optimization for continuous parameters, exact solvers for structured subproblems). This hybrid approach combines the generality of LLMs with the efficiency of traditional methods.

\paragraph{Principle 3: Diversity preservation prevents premature convergence.}
Quality-diversity algorithms like MAP-Elites are essential for preventing the mode collapse that plagues both LLM-based search and traditional evolutionary algorithms. By maintaining a diverse archive of high-performing solutions, these algorithms ensure that the search continues to explore new regions of the solution space even after finding locally optimal solutions. The behavioral descriptors used for diversity preservation should be chosen to capture meaningful variation in solution structure and behavior, not superficial differences.

\paragraph{Principle 4: Reflection must be grounded in evaluation.}
Unstructured self-reflection without grounding in objective evaluation is prone to hallucination and self-delusion. The most effective reflection systems (Self-Debug, Reflexion) derive their reflections from concrete evaluation artifacts: execution traces, test results, and benchmark scores. This grounding ensures that reflections are factual and actionable, rather than speculative. Systems that rely solely on LLM self-critique without external evaluation are particularly vulnerable to compounding errors.

\paragraph{Principle 5: Population management enables compositional discovery.}
Population-based systems can discover solutions that no single-trajectory search could find, because they enable the recombination of partial solutions discovered by different individuals. AlphaEvolve's matrix multiplication algorithms, for example, combine elements from multiple parent algorithms in ways that no single optimization trajectory would have explored. The key to compositional discovery is maintaining sufficient diversity in the population and designing crossover operators that can meaningfully combine elements from different parents.

\paragraph{Principle 6: Specification should be evolutionary, not fixed.}
The most sophisticated self-evolving systems recognize that the initial specification may be incomplete or suboptimal, and they allow the specification itself to evolve based on feedback from execution and evaluation. This is the ultimate form of self-evolution: not just improving solutions within a fixed problem frame, but refining the problem frame itself. Current systems only hint at this capability (e.g., Absolute Zero's self-play task proposal), but it represents a critical direction for future research.

\subsection{Emerging Frontiers}

The Five Evolution Loops framework also illuminates several emerging frontiers that cut across traditional domain boundaries.

\paragraph{Self-evolving evaluation.}
One of the most intriguing frontiers is the evolution of evaluation itself. Current systems treat the evaluator as fixed, but the most powerful self-evolving systems should be able to improve their own evaluation mechanisms. For example, a code generation system could evolve better test suites; a mathematical discovery system could develop more efficient verification procedures; and an agent system could learn to evaluate its own behavior against increasingly nuanced criteria. This meta-evaluation capability is a prerequisite for truly open-ended self-evolution, as it removes the need for externally provided evaluation and enables the system to define its own improvement trajectory.

\paragraph{Multi-scale evolution.}
Current self-evolving systems typically operate at a single scale: they optimize individual artifacts (prompts, architectures, code). Multi-scale evolution would simultaneously optimize at multiple levels: individual components, component compositions, overall system architectures, and even the meta-strategies that govern the evolution process itself. The Five Evolution Loops provide a natural framework for multi-scale evolution, as different loops can operate at different scales---the Search Loop optimizing individual components, the Population Loop managing diverse system-level designs, and the Reflection Loop extracting cross-scale insights.

\paragraph{Human-in-the-loop evolution.}
While fully autonomous self-evolution is the ultimate goal, practical systems will continue to benefit from human involvement at critical decision points. The challenge is designing interfaces that allow humans to provide meaningful guidance without becoming bottlenecks. The Reflection Loop is a natural point for human intervention: humans can review and correct reflections before they are stored in memory, ensuring that the system learns from accurate analyses rather than hallucinated ones. The Spec Loop is another natural intervention point, where humans can refine specifications based on their domain knowledge.

These emerging frontiers suggest that the Five Evolution Loops framework will continue to be relevant as the field advances, providing a common language for describing and comparing increasingly sophisticated self-evolving systems.
