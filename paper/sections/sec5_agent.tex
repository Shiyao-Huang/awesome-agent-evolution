\section{Self-Evolving Agent Systems}
\label{sec:agent-evolution}

The evolutionary code systems of Section~\ref{sec:evolutionary-code} optimize programs---functions, heuristics, algorithms---within fixed architectural frameworks. A more radical form of self-evolution targets the \emph{agents} themselves: their architectures, workflows, tool configurations, and learning mechanisms. This section surveys the emerging landscape of self-evolving agent systems, from automated agent design and self-referential architectures, through symbolic learning and zero-data self-training, to multi-agent collaborative evolution. We trace the intellectual lineage from early iterative refinement methods (Reflexion, Self-Refine) through architecture-level search (ADAS, Darwin G\"odel Machine) to the most extreme form of self-evolution: training on self-generated data with zero external supervision (Absolute Zero).

The distinction between code evolution and agent evolution is not merely one of scope. When FunSearch evolves a mathematical function, the evaluation criteria are fixed and the evolution operates within a stable framework. When an agent evolves its own architecture, the evaluation criteria may themselves shift as the agent's capabilities change, creating a recursive dynamic that is both more powerful and more challenging to control. Agent self-evolution thus raises fundamental questions about stability, safety, and the limits of autonomous improvement that do not arise in the code evolution setting.

\subsubsection{Foundational Methods: Reflexion and Self-Refine}

Before examining the architecture-level self-evolution systems, it is important to understand two foundational methods that established the paradigm of agent self-improvement through iterative feedback. These methods---Reflexion and Self-Refine---are the intellectual ancestors of all subsequent self-evolving agent systems.

\textbf{Reflexion}~\citep{shinn2023reflexion} (NeurIPS 2023, Northeastern University + MIT/Princeton) introduces verbal reinforcement learning: agents learn from linguistic feedback stored in a growing memory buffer, without any weight updates. The architecture comprises three specialized models: an \emph{Actor} ($M_a$) that generates actions given the task and accumulated memory, an \emph{Evaluator} ($M_e$) that scores the actor's output (binary or scalar reward), and a \emph{Self-Reflection} model ($M_r$) that generates verbal feedback explaining what went wrong and what to do differently.

The reflexion loop stores failure analyses in a memory buffer that grows across episodes:
\begin{equation}
M_e = M_{e-1} \cup \{f_e\}, \quad f_e = M_r(a_e, r_e, \text{task})
\end{equation}
where $f_e$ is the verbal feedback from episode $e$, $a_e$ is the action taken, and $r_e$ is the reward received. This memory acts as a ``verbal gradient''---natural language guidance for future attempts, analogous to parameter gradients in neural network training but operating in text space.

On HumanEval, Reflexion achieves \textbf{91\% pass@1} using GPT-3.5, surpassing GPT-4's 80\%---a striking demonstration that iterative self-reflection with a weaker model can outperform single-pass generation with a stronger model. On AlfWorld, Reflexion reaches 97\% success (vs.\ 75\% baseline). These results established the principle that episodic memory of failures can serve as a training signal for language agents, directly influencing all subsequent work from Agent Symbolic Learning's structured backpropagation to DGM's archive-based evolution.

\textbf{Self-Refine}~\citep{madaan2023selfrefine} (NeurIPS 2023, AI2 + Google + CMU) demonstrates that a single LLM can iteratively generate, critique, and refine its own output across seven diverse tasks, achieving approximately 20\% average improvement with no external feedback, no training, and no reinforcement learning. The three-step loop (GENERATE $\to$ CRITIQUE $\to$ REFINE) repeats until the critique identifies no further improvements or a maximum iteration count is reached. The same model serves all three roles.

On sentiment reversal (74\% $\to$ 86\%), dialogue response (52\% $\to$ 68\% win rate), and constrained generation (65\% $\to$ 78\% compliance), Self-Refine produces consistent improvements across all evaluated tasks. Self-Refine establishes the principle that self-feedback is a viable alternative to external feedback---a foundational assumption underlying all subsequent self-evolution systems.

Together, Reflexion and Self-Refine demonstrate two key principles that permeate the self-evolving agent landscape: (1) iterative refinement with feedback consistently outperforms single-pass generation, and (2) the feedback can be generated by the agent itself, without external evaluation. These principles are the bedrock upon which all subsequent systems are built.

\subsection{Agent Architecture Evolution}
\label{sec:adas}

The design of agent architectures---prompting strategies, tool compositions, multi-step reasoning chains, and memory systems---has traditionally been a manual, intuition-driven process. Researchers draw on experience and heuristics to design agent architectures, test them on benchmarks, and iteratively refine them. This process is slow, human-limited, and bounded by the designer's imagination. Three recent systems---ADAS, the Darwin G\"odel Machine, and G\"odel Agent---formalize architecture design as a search problem, enabling automated discovery of agent designs that can surpass human intuition.

\subsubsection{ADAS: Automated Design of Agentic Systems}

ADAS~\citep{hu2024adas} (Automated Design of Agentic Systems), developed at UBC and Vector Institute by Shengran Hu, Cong Lu, and Jeff Clune, introduces the Meta Agent Search algorithm, in which a ``meta agent'' (an LLM, typically GPT-4o) iteratively proposes new agent architectures expressed as executable Python code. The search space encompasses all valid Python programs that implement agents using a provided base class (\texttt{LLMAgentBase}), making it Turing-complete: any computable agent architecture can, in principle, be discovered.

\textbf{Core algorithm}: The Meta Agent Search proceeds through the following stages:

\begin{enumerate}
\item \textbf{Initialization}: Seed the archive with known agent architectures---Chain-of-Thought (single-step reasoning with code generation), Self-Refine (iterative self-correction), LLM Debate (multi-role adversarial reasoning, e.g., ``puzzle designer vs.\ logic expert''), CoT with Self-Consistency ($N{=}5$ parallel reasoning paths with majority voting), and Quality-Diversity (diverse candidate generation with top-$k$ selection). Each seed is evaluated to establish baseline fitness.

\item \textbf{Proposal}: The meta agent reviews the entire archive of previously discovered designs and their performance scores, then proposes a new agent architecture. The meta agent prompt includes the complete API specification of \texttt{LLMAgentBase}, the full history of discovered architectures (no pruning), task examples, and explicit encouragement to ``think outside the box.'' The output format requires three fields: a structured \texttt{thought} section (insights and overall idea), a descriptive \texttt{name}, and the complete \texttt{code} implementation as a Python function.

\item \textbf{Dual Reflexion}: The proposal undergoes two rounds of self-reflection. Round 1 assesses novelty (``Is this architecture interestingly different from existing ones?'') and identifies implementation errors. Round 2 corrects against a library of 10 common failure patterns (e.g., incorrect API usage, missing error handling, infinite loops). This dual-reflection mechanism significantly reduces the rate of syntactically invalid or trivially broken proposals.

\item \textbf{Evaluation}: The proposed architecture is dynamically loaded via Python's \texttt{exec()} function and set as the \texttt{forward} method of an \texttt{AgentSystem} class. Evaluation uses multi-threaded parallel execution (\texttt{ThreadPoolExecutor} with 32--48 workers) on benchmark tasks. Fitness is measured using bootstrap 95\% confidence intervals computed from 100,000 resamples, providing robust performance estimates.

\item \textbf{Archive update}: The new architecture and its score are appended to the growing archive. Unlike evolutionary algorithms that prune or replace population members, ADAS retains all discovered architectures, providing the meta agent with an ever-growing library of building blocks and lessons.
\end{enumerate}

\textbf{Architectural design space}: The \texttt{LLMAgentBase} class provides a minimal but flexible interface for constructing agents. It accepts output field specifications, an agent name, a role description, a model selection, and a temperature parameter. The \texttt{\_\_call\_\_} method takes a list of \texttt{Info} objects and a natural language instruction, returning a list of \texttt{Info} objects. This simple interface supports a wide range of architectures: single-pass reasoning, iterative refinement, multi-agent debate, self-consistency voting, memory-augmented reasoning, and any other pattern expressible as Python control flow.

\textbf{Results and cross-domain transfer}: On the ARC (Abstraction and Reasoning Corpus) benchmark, ADAS-discovered agents outperform all hand-designed baselines. The evolution trajectory shows clear architectural innovation: from initial seeds scoring 3--8\%, the system discovers a ``Memory-Augmented Agent'' at generation 4 that achieves 11\% by introducing a memory buffer---a design pattern not present in any seed architecture. This demonstrates that the search process can invent genuinely novel architectural ideas.

A striking finding is \textbf{cross-domain transfer}: architectures discovered on ARC transfer effectively to DROP (reading comprehension), GPQA (graduate-level science QA), MGSM (multilingual math), and MMLU (knowledge reasoning), even without domain-specific adaptation. Moreover, architectures discovered using GPT-3.5 as the inner agent remain effective when GPT-4 serves as the backbone, demonstrating that the discovered designs encode general reasoning patterns rather than model-specific exploits.

The transferability of discovered architectures has profound implications. If architectures discovered on one set of tasks transfer to entirely different tasks, it suggests that the search process is not merely finding task-specific hacks but is discovering genuine reasoning strategies---ways of decomposing problems, coordinating multiple reasoning steps, and aggregating evidence---that are broadly applicable. This finding supports the hypothesis that the space of agent architectures contains universal building blocks that can be composed into effective designs across diverse domains.

The fact that architectures transfer from GPT-3.5 to GPT-4 is equally significant. It implies that the discovered architectures encode strategies that are \emph{model-agnostic}: they work because they represent good problem-solving patterns, not because they exploit specific model quirks. This model-agnosticism is essential for practical deployment, as it means that organizations can invest in architecture search once and benefit from the discovered designs across multiple model generations.

ADAS was accepted at ICLR 2025 and received the NeurIPS 2024 Open-World Agent Workshop Outstanding Paper Award, with over 414 citations, establishing automated agent design as a recognized research direction. The system is implemented in approximately 500 lines of core code per domain, with only OpenAI API as the external dependency---a testament to the power of the meta-search approach.

\textbf{Limitations}: The computational cost is substantial: each proposed architecture requires full benchmark evaluation (32--48 parallel threads), and the reflexion and debugging stages add multiple LLM calls per proposal. The archive grows indefinitely (no pruning), which can overwhelm the meta agent's context window at later generations. The approach is also limited to architectures expressible as Python programs using \texttt{LLMAgentBase}, excluding designs that require custom neural components, external memory systems, or non-textual modalities. The entire system is implemented in approximately 500 lines of core code per domain, with only OpenAI API as the external dependency---a testament to the power of the meta-search approach.

\subsubsection{Darwin G\"odel Machine}

DGM~\citep{zhang2025dgm} (Darwin G\"odel Machine), from the same research group (UBC + Vector Institute, led by Jeff Clune), combines Darwinian evolution with G\"odel machine self-reference. It maintains an open-ended archive of agent implementations, where each entry is a complete agent codebase paired with performance metrics. The key innovation over ADAS is the \emph{open-ended} nature of the archive: rather than searching for a single optimal architecture, DGM maintains a growing collection of diverse, high-performing agents.

\textbf{Algorithm}: The evolution loop proceeds as follows:
\begin{enumerate}
\item \textbf{Sampling}: A parent agent is selected from the archive with probability proportional to fitness multiplied by a diversity bonus:
\begin{equation}
P(a_i) \propto f(a_i) \times \text{diversity\_bonus}(a_i, A)
\end{equation}
The diversity bonus favors agents from underexplored regions of the design space, preventing the archive from being dominated by minor variations of a single successful design.

\item \textbf{Self-modification}: A foundation model (Claude or GPT) proposes code-level modifications to the parent agent, producing a child agent. The modifications can range from small adjustments (changing a prompt, adding a tool) to major restructuring (replacing a single-agent design with a multi-agent architecture).

\item \textbf{Evaluation}: The child agent is evaluated on coding benchmarks, with fitness measured as the fraction of correctly solved tasks.

\item \textbf{Selection}: If the child improves over the parent, it is added to the archive. Optionally, non-improving children may be retained for diversity, enriching the archive with potentially useful building blocks even if they do not immediately improve performance.
\end{enumerate}

\textbf{Open-endedness}: Unlike standard evolutionary algorithms that converge to a single optimum, DGM maintains a diverse archive that enables exploration of qualitatively different agent architectures and discovery of unexpected strategies. The archive grows over time, accumulating a library of agent designs that can be sampled, recombined, and further modified in future iterations. This open-endedness is inspired by the POET (Paired Open-Ended Trailblazer) system from the same research group, which demonstrated that open-ended search can produce qualitatively novel solutions that closed optimization cannot.

\textbf{Key results}: On SWE-bench (the canonical software engineering benchmark), DGM improves verified resolution from \textbf{20.0\% to 50.0\%}---a 150\% relative improvement. On Polyglot (multi-language coding), it improves from \textbf{14.2\% to 30.7\%}---a 116\% relative improvement. Crucially, DGM discovers novel agent structures that human designers did not imagine, and agents show cross-domain transfer: improvements learned on one benchmark benefit performance on others. This transfer suggests that DGM is discovering general-purpose reasoning strategies, not benchmark-specific hacks.

\textbf{Limitations}: Each iteration requires benchmark evaluation, which is computationally expensive. Code modifications are not guaranteed to be syntactically correct (though evaluation failures are filtered). The system depends on foundation model quality for proposing meaningful changes. Archive management (when to prune, how to balance diversity vs.\ quality) is a non-trivial design decision. Self-modifying code introduces safety risks that are addressed through engineering safeguards (evaluation-based selection) but not formal verification.

\subsubsection{G\"odel Agent}

G\"odel Agent~\citep{yin2025godelagent} (ACL 2025, Peking University + UCSB) takes a more direct approach to self-reference, inspired by Schmidhuber's theoretical G\"odel Machine~\citep{schmidhuber2003godel}. While DGM maintains an archive of separate agent implementations, G\"odel Agent modifies a single running instance at runtime through Python monkey patching.

\textbf{Self-referential loop}: The agent operates through four steps:
\begin{enumerate}
\item \textbf{Runtime introspection}: The agent reads its own source code and current state, building a representation of its own behavior.
\item \textbf{Modification proposal}: The LLM proposes specific code changes (monkey patches) guided by high-level objectives and recent performance feedback. Formally: $A' = \text{LLM}(A.\text{code}, \text{feedback}, \text{objective})$.
\item \textbf{Safe application}: Patches are applied at runtime via Python's \texttt{exec()} mechanism, dynamically replacing or augmenting the agent's methods.
\item \textbf{Validation}: Modified code is tested on a validation set. If performance improves (i.e., $\text{score}(A') > \text{score}(A)$ on the validation set), the modification is accepted; otherwise, it is rolled back.
\end{enumerate}

\textbf{Results}: On HotPotQA (multi-hop question answering), G\"odel Agent achieves 8--15\% improvement over hand-designed agents. On ALFWorld (interactive text environments), improvement is significant. The agent demonstrates continuous improvement across task batches and discovers strategies that human designers did not anticipate, including novel tool usage patterns and reasoning strategies that differ from established prompting techniques.

\textbf{Extension to small models}: Polaris (arXiv:2603.23129) extends the G\"odel Agent concept to small language models, demonstrating that self-referential improvement is not limited to frontier-scale LLMs. This is significant because it suggests that self-evolution capabilities can be distributed beyond the few organizations with access to the largest models.

\textbf{Safety}: Rollback capability for failed modifications, validation before committing changes, and high-level objective constraints prevent drift. However, runtime self-modification introduces non-determinism, theoretical guarantees are weaker than formal G\"odel machine proofs, and the approach is Python-specific, limiting portability to other programming languages and runtime environments.

\subsubsection{Comparing the Three Approaches}

While all three systems draw inspiration from the idea of automated agent improvement, they differ fundamentally:

\begin{itemize}
\item \textbf{Population vs.\ single agent}: DGM maintains an archive of agents (population-based search), ADAS maintains an archive of architectural designs (search with accumulation), and G\"odel Agent modifies a single running instance (individual self-modification).
\item \textbf{Offline vs.\ online}: DGM and ADAS evaluate candidate modifications offline (generate, evaluate, then decide), while G\"odel Agent applies changes online at runtime.
\item \textbf{Code mechanism}: DGM generates complete agent implementations, ADAS generates forward functions (within a fixed base class), and G\"odel Agent applies targeted monkey patches.
\item \textbf{Open-endedness}: DGM's archive enables open-ended exploration; ADAS's archive grows but within the meta-agent search framework; G\"odel Agent's single-instance modification is more focused but potentially faster for incremental improvements.
\end{itemize}

All three approaches share the limitation that self-modification safety is addressed through engineering safeguards (rollback, validation) rather than formal verification. The question of how to provide rigorous guarantees for self-modifying systems remains open and represents a fundamental challenge for the field.

\subsection{Agent Workflow Evolution}
\label{sec:workflow-evolution}

Architecture evolution modifies the structural design of an agent. A complementary target is the agent's \emph{workflow}---the sequence of operations it performs, the tools it selects, and the strategies it employs for task decomposition and execution. Workflow evolution is less ambitious than architecture evolution but more directly applicable to production systems, where the agent's basic architecture is typically fixed but its operational patterns can be continuously refined.

\subsubsection{AgentEvolver: Evolutionary Tool Usage Optimization}

AgentEvolver (ModelScope/Alibaba) applies evolutionary optimization to the space of agent tool usage configurations. Rather than evolving the agent's reasoning architecture, AgentEvolver evolves the strategies by which the agent selects, sequences, and applies tools from a provided toolkit.

The system maintains a population of agent configurations, each specifying a different combination of tool selection heuristics, execution ordering, and error recovery strategies. LLM-driven mutation modifies these configurations---adjusting tool preferences, adding or removing tools from specific workflow stages, or changing the conditions under which tools are invoked. Quality-diversity search across tool usage patterns ensures that the population explores a range of strategies rather than converging to a single approach.

Results on standard agent benchmarks demonstrate that evolved tool usage strategies outperform both random tool selection and human-designed heuristics, particularly for tasks that require complex multi-tool sequences. The approach is complementary to architecture evolution: an agent with an evolved architecture and evolved tool usage can benefit from both levels of optimization simultaneously.

\subsubsection{SE-Agent: Multi-Trajectory RRR}

SE-Agent implements a Multi-trajectory Revision/Recombination/Refinement (RRR) approach that leverages information from multiple execution trajectories to guide code and workflow improvement. Rather than evolving a single program through sequential mutations (as FunSearch does), SE-Agent collects multiple trajectories---both successful and failed---and uses them collectively to extract improvement signal.

\textbf{Revision}: Failed trajectories are analyzed to extract error patterns. The LLM identifies recurring failure modes (incorrect API calls, wrong control flow, mistaken assumptions about data formats) and generates targeted fixes. This phase transforms failures into learning signal, analogous to how Reflexion converts execution failures into verbal feedback.

\textbf{Recombination}: Successful sub-trajectories---portions of execution traces that produced correct intermediate results---are identified and merged. The LLM combines the best elements from different successful attempts, creating novel workflow configurations that may outperform any individual trajectory. This recombination is analogous to genetic crossover but operates at the level of execution traces rather than code syntax.

\textbf{Refinement}: The combined solution is iteratively improved based on aggregated evaluation feedback. Multiple evaluation criteria (correctness, efficiency, code quality, robustness) guide the refinement process, producing solutions that are not merely correct but well-engineered.

Empirically, the combination of revision and recombination produces larger improvements than either alone, suggesting that learning from both failures and successes is more effective than learning from successes alone. This finding has implications for the design of self-evolving systems: the most informative training signal comes from the contrast between successful and failed attempts, not from either category in isolation.

\subsubsection{Contrasting Workflow and Architecture Evolution}

Workflow evolution occupies a middle ground between the fine-grained optimization of knowledge evolution and the radical restructuring of architecture evolution. Its key advantages are tractability and deployability: modifying an agent's tool usage patterns is less risky than rewriting its architecture, and the improvements are immediately applicable to production systems. However, workflow evolution is bounded by the quality of the available tools and the expressiveness of the workflow specification language.

An important open question is whether workflow evolution and architecture evolution can be combined synergistically. One might imagine a system where architecture evolution discovers high-level design patterns (e.g., ``multi-agent debate is effective for reasoning tasks''), and workflow evolution instantiates those patterns with task-specific tool selections and execution sequences. This hierarchical approach---architecture evolution for structure, workflow evolution for execution---could combine the generality of architecture search with the practicality of workflow optimization.

\subsection{Agent Memory and Learning}
\label{sec:agent-memory}

Beyond modifying architectures and workflows, a third axis of agent self-evolution targets the agent's knowledge representations---its prompts, tool descriptions, and internal memory systems. This section examines two systems that approach knowledge evolution from radically different angles: Agent Symbolic Learning, which treats agents as differentiable symbolic networks and applies backpropagation-inspired optimization in language space; and Absolute Zero, which eliminates all external data dependencies through self-play reinforcement learning.

\subsubsection{Agent Symbolic Learning}

Agent Symbolic Learning~\citep{zhou2024agentsymbolic} (NeurIPS 2024, AIWaves Inc.\ + Zhejiang University) proposes an elegant unification: treating agents as symbolic networks where the ``weights''---prompts, tool definitions, and pipeline connections---can be optimized through a procedure analogous to backpropagation, but operating entirely in natural language space.

\textbf{Agent as symbolic network}: An agent is parameterized as a computational graph with three types of learnable nodes:
\begin{itemize}
\item \textbf{Prompt nodes} ($\mathcal{P}$): System prompts, persona descriptions, task instructions, and few-shot examples. These are the ``weights'' that control how the agent interprets and responds to inputs.
\item \textbf{Tool nodes} ($\mathcal{T}$): Function definitions, tool descriptions, and usage guidelines. These define what the agent can do and how it understands its capabilities.
\item \textbf{Pipeline nodes} ($\mathcal{I}, \mathcal{O}$): Input/output connections between nodes that define the agent's computational flow---which outputs feed into which inputs, in what order, with what transformations.
\end{itemize}

\textbf{Learning procedure}: The optimization procedure mirrors neural network training with remarkable fidelity:

\textbf{Forward pass}: The agent executes on a task, producing a trajectory $\tau$ of actions, observations, and intermediate results.

\textbf{Language loss}: An LLM evaluates the trajectory and produces a natural language description of what went wrong:
\begin{equation}
\mathcal{L}_{\text{lang}} = \text{LLM}(\mathcal{P}_{\text{loss}}(\tau))
\end{equation}
This ``language loss'' is a textual summary of failure modes, missed opportunities, and suboptimal decisions---analogous to a scalar loss in neural network training but far more informative.

\textbf{Language gradient backpropagation}: Working backward from the output layer to the input, the system computes a ``language gradient'' for each layer---a natural language description of how to improve that specific component:
\begin{equation}
\nabla_{\text{lang}}^n = \text{LLM}(\mathcal{P}_{\text{gradient}}(\nabla_{\text{lang}}^{n+1}, \mathcal{I}_n, \mathcal{O}_n, \mathcal{P}_n, \mathcal{T}_n, \mathcal{L}_{\text{lang}}))
\end{equation}
This backward pass propagates improvement suggestions from the output (where the failure is most apparent) back through the computational graph, identifying which nodes contributed to the failure and how they should be modified.

\textbf{Weight update}: Three specialized optimizers update different components:
\begin{itemize}
\item \textbf{PromptOptimizer}: $\Delta\mathcal{P} = \text{LLM}(\mathcal{P}_{\text{update}}(\mathcal{P}, \nabla_{\text{lang}}))$---rewrites prompts to address identified weaknesses.
\item \textbf{ToolOptimizer}: $\Delta\mathcal{T} = \text{LLM}(\mathcal{P}_{\text{update}}(\mathcal{T}, \nabla_{\text{lang}}))$---refines tool descriptions and usage guidelines.
\item \textbf{PipelineOptimizer}: $\Delta\mathcal{I}, \Delta\mathcal{O} = \text{LLM}(\mathcal{P}_{\text{update}}(\mathcal{I}, \mathcal{O}, \nabla_{\text{lang}}))$---restructures the agent's computational flow.
\end{itemize}

\textbf{Results}: Agent Symbolic Learning demonstrates broad effectiveness across diverse benchmarks:
\begin{itemize}
\item \textbf{HotPotQA}: F1 of 39.1 (vs.\ 37.4 for DSPy, 36.2 for baseline agents)---a 8\% relative improvement.
\item \textbf{MATH}: 60.7\% accuracy (vs.\ 56.0\% for baseline, 48.4\% for DSPy) using GPT-4 backbone---a 8.4\% absolute improvement.
\item \textbf{HumanEval}: 73.2\% pass@1 (vs.\ 68.3\% baseline)---a 7.2\% relative improvement in code generation.
\item \textbf{Software Development}: Average score 3.8 on 1--4 executability scale (vs.\ 2.4 for agents, 1.6 for GPTs)---a 58\% relative improvement.
\item \textbf{Creative Writing}: 7.4 on 1--10 scale (vs.\ 6.8 for Tree of Thought)---demonstrating applicability beyond analytical tasks.
\end{itemize}

All improvements are achieved without any weight updates to the underlying LLM---all optimization occurs in the space of prompts, tools, and pipeline connections. This is significant because it means the approach can be applied to any LLM, including closed-source models where weight access is not available.

\textbf{Relationship to other paradigms}: Agent Symbolic Learning extends DSPy's prompt optimization concept to the full agent architecture, including tools and pipeline structure. It is related to Reflexion's verbal reinforcement learning but uses structured backpropagation through a computational graph rather than episode-level reflection. The approach precedes and informs code-level self-modification methods (DGM, G\"odel Agent) by demonstrating that agents can be meaningfully optimized through natural language ``gradients,'' establishing the principle that language-space optimization is a viable alternative to code-space modification.

\textbf{Limitations}: The method requires a strong LLM backbone (GPT-4 level) for gradient computation---weaker models produce less informative language gradients. The quality of optimization depends on the design of loss, gradient, and update prompt templates, introducing a manual engineering component. There are no theoretical convergence guarantees for optimization in language space. Each training step requires multiple LLM calls (forward + loss + backpropagation through all layers + weight update), making it computationally expensive.

\subsubsection{Absolute Zero: Zero-Data Self-Training}

The most extreme form of agent self-evolution eliminates all external dependencies: no human-curated training data, no external evaluation functions, no hand-designed curricula. Absolute Zero~\citep{zhao2025absolutezero} (NeurIPS 2025 award-winning, Tsinghua University / LeapLabTHU) achieves this through self-play reinforcement learning.

\textbf{Self-Play RLVR}: Absolute Zero introduces the Self-Play Reinforced Learning with Verifiable Rewards (Self-Play RLVR) paradigm. A single model simultaneously serves two roles:

\textbf{Task Proposer}: Generates new reasoning tasks (code problems, math puzzles, logic challenges) based on the current curriculum state. The proposer is rewarded for generating tasks that are solvable but challenging:
\begin{equation}
R_{\text{proposer}} \propto \text{difficulty}(t) \times \text{solvability}(t)
\end{equation}
This reward structure ensures that the proposer does not degenerate into generating trivially easy tasks (which would provide no learning signal) or trivially impossible tasks (which would provide no successful training examples).

\textbf{Task Solver}: Attempts to solve the proposed tasks. Solutions are verified by a code executor, providing a binary reward signal ($r \in \{0, 1\}$). Both roles are updated via reinforcement learning (PPO or GRPO), creating a self-improving loop: better tasks produce better training signal, which produces a better solver, which in turn enables the proposer to generate harder tasks (since it can now expect the solver to handle them).

\textbf{Key innovation}: The model is \emph{both} the curriculum designer AND the student. This dual role creates a natural curriculum that adapts to the model's current capability: as the solver improves, the proposer generates harder tasks, maintaining a consistent level of challenge throughout training. This is analogous to AlphaGo Zero's self-play mechanism, but applied to reasoning tasks rather than board games.

\textbf{Results}: AZR-Coder-7B, trained with zero external data, achieves state-of-the-art results among 7B-parameter models:
\begin{itemize}
\item \textbf{HumanEval+}: SOTA at 7B scale, surpassing models trained on curated datasets.
\item \textbf{MBPP+}: SOTA at 7B scale.
\item \textbf{Overall average}: SOTA at 7B scale across coding and math benchmarks.
\end{itemize}

A striking finding is \textbf{cross-domain transfer}: training only on self-generated code tasks produces competitive mathematical reasoning on GSM8K and MATH, despite zero mathematical training data. This suggests that the self-play process develops general reasoning capabilities that transfer across domains, not domain-specific tricks.

The scaling behavior follows a clear pattern: ``stronger models are better at making themselves stronger''---larger or more capable base models produce better self-play dynamics and achieve higher final performance. This finding has important implications for the future of self-evolving systems: as base models improve, the self-improvement loop becomes more effective, creating a positive feedback cycle. However, this scaling also raises safety concerns: if self-improvement capability scales with model capability, the most powerful models will also be the most capable of autonomous self-modification, amplifying both the potential benefits and the risks.

The self-play paradigm in Absolute Zero can be viewed as a form of ``curriculum bootstrapping'': the system starts with trivially easy tasks (which even a weak model can generate and solve) and progressively increases difficulty as the solver improves. This progressive curriculum is emergent rather than designed---it arises naturally from the dual reward structure (proposer rewarded for hard-but-solvable tasks, solver rewarded for correctness)---and it adapts continuously to the model's current capability level.

\textbf{Limitations}: Task quality depends on the proposer's current capability, creating a bootstrapping challenge (early training may produce trivial or unsolvable tasks). The code executor limits task types to verifiable programming problems, excluding domains without automated verification. Mode collapse---where the proposer and solver converge to trivial agreements---is a risk, though the dual-role reward structure mitigates it. The computational cost of dual-role RL training is significant, requiring distributed training infrastructure comparable to standard RLHF training runs.

\subsection{Multi-Agent Collaborative Evolution}
\label{sec:multi-agent-evo}

The systems discussed so far focus on evolving individual agents. A complementary approach leverages multi-agent collaboration as both the mechanism and the target of evolution. Multiple agents with specialized roles work together on tasks, and their collective performance drives the evolution of individual agents, team composition, and coordination strategies.

\subsubsection{AutoML-Agent: Hierarchical Multi-Agent AutoML}

AutoML-Agent~\citep{chen2024automlagent} (ICML 2025, DeepAuto-AI) demonstrates multi-agent collaborative evolution in the context of automated machine learning. The system decomposes the full ML pipeline into five specialized agents coordinated by a manager:

\textbf{Agent architecture}:
\begin{itemize}
\item \textbf{Prompt Agent}: Parses natural language task descriptions into structured JSON specifications.
\item \textbf{Agent Manager}: Orchestrates the workflow through a 7-state finite state machine (INIT $\to$ PLAN $\to$ ACT $\to$ PRE\_EXEC $\to$ EXEC $\to$ POST\_EXEC $\to$ REV). Plans multiple candidate pipelines in parallel and manages the revision cycle.
\item \textbf{Data Agent}: Retrieves and preprocesses data using a 6-level fallback strategy (HuggingFace $\to$ Kaggle $\to$ PyTorch $\to$ TensorFlow $\to$ UCI $\to$ OpenML $\to$ LLM-generated search).
\item \textbf{Model Agent}: Selects and configures models using a 3-level retrieval strategy (HuggingFace $\to$ Kaggle $\to$ PyTorch Hub).
\item \textbf{Operation Agent}: Generates executable Python code with automatic error repair (up to 5 iterations of sandbox execution and error feedback).
\end{itemize}

\textbf{Evolution mechanisms}: AutoML-Agent implements three levels of self-improvement:

\textit{Plan-level revision}: When all candidate plans fail, the Manager reflects on the failure reasons and generates new plans informed by the failure analysis. This is analogous to Reflexion's verbal feedback but applied to the planning stage rather than the execution stage.

\textit{Code-level auto-repair}: The Operation Agent iteratively fixes generated code based on execution errors, with up to 5 repair iterations. Each iteration feeds the full error traceback back to the LLM, which generates a corrected version. This mechanism is similar to SelfEvolve's self-debugging loop but integrated into a multi-agent framework.

\textit{Evol-Instruct augmentation}: The system includes an evolutionary instruction module that transforms training prompts through depth evolution (4 strategies: adding constraints, deepening problems, concretizing abstractions, increasing reasoning steps) and breadth evolution (creating rarer variants). This increases the diversity and difficulty of the tasks the agents train on, improving robustness.

\textbf{Additional innovations}: The system includes adversarial noise injection (generating irrelevant information to test agent robustness), role-augmented gradient prompting (progressively enhancing the agent's self-conception from ``helpful assistant'' to ``world's best [role]''), and RAG-based knowledge retrieval across four sources (Google, arXiv, PapersWithCode, Kaggle).

\textbf{Results}: AutoML-Agent supports 7 task types (image classification, text classification, tabular classification/regression/clustering, node classification, time series forecasting) with corresponding evaluation metrics (ACC, F1, RMSLE, RI). The multi-plan parallel execution with automatic revision significantly outperforms single-plan approaches, demonstrating the value of diverse candidate generation and failure-driven revision.

\textbf{Implementation details}: The system is implemented in Python 3.11, using vLLM 0.4.1 for efficient LLM inference with Mixtral-8x7B models fine-tuned via LoRA. The multi-agent coordination uses LangChain for LLM orchestration, and the evaluation pipeline generates complete Python scripts that are executed in subprocess isolation. The codebase comprises approximately 10K lines across the five agent modules, with the Agent Manager's state machine being the most complex component (handling plan generation, parallel execution, validation, and revision in a single control flow).

The RAG retrieval subsystem uses a hybrid approach: FAISS-based dense retrieval combined with BM25 sparse retrieval, followed by CrossEncoder re-ranking to select the most relevant knowledge. This hybrid approach is crucial for balancing semantic relevance (dense retrieval captures meaning) with keyword matching (sparse retrieval handles specific technical terms like library names and function signatures).

\textbf{Insights for self-evolving systems}: AutoML-Agent demonstrates several design patterns that are applicable to self-evolving agent systems more broadly. First, the multi-plan parallel approach---generating diverse candidate solutions and selecting the best---is a form of quality-diversity search applied at the pipeline level. Second, the failure-driven revision cycle (reflect on failure, regenerate plans) is a form of reflexive improvement that mirrors Reflexion's approach but applied to the planning stage. Third, the hierarchical decomposition into specialized agents with distinct responsibilities provides a modular architecture that enables localized improvement: the Data Agent can be improved independently of the Model Agent, and the Manager's planning strategy can be optimized without affecting the individual agents.

\subsubsection{SelfEvolve: Self-Evolving Code Generation}

SelfEvolve~\citep{jiang2023selfevolve} (Shanghai Jiao Tong University + Shanghai AI Lab) demonstrates a simpler but effective form of self-evolution for code generation: a two-stage pipeline where the LLM first generates its own API documentation, then iteratively debugs its generated code using execution feedback.

\textbf{Stage 1: Self-generated knowledge}: Rather than relying on external documentation (which may be incomplete, outdated, or poorly matched to the task), SelfEvolve prompts the LLM to generate necessary API documentation from its parametric knowledge:
\begin{equation}
P(Y|K) = \prod p_\theta(Y_i | Y_{<i}, X, K)
\end{equation}
where $X$ is the task description and $K$ is the self-generated documentation. This addresses a common failure mode: LLMs often hallucinate API usage when they lack precise documentation, generating syntactically plausible but semantically incorrect code.

\textbf{Stage 2: Iterative self-refinement}: Generated code is executed in a Python interpreter sandbox with test cases. If execution fails, the full error traceback is fed back to the LLM, which revises the code:
\begin{equation}
P(Y'|X,Y,K,e) = p_\theta(Y'|X,Y,e) \times p_\theta(Y|X,K)
\end{equation}
where $e$ is the error message. This loop repeats until the code passes or a maximum iteration count is reached.

\textbf{Results}: On DS-1000 (data science code), SelfEvolve achieves 57.2 pass@1, a 15.8\% relative improvement over the ChatGPT baseline (49.4). On HumanEval, it reaches 85.98 pass@1 (vs.\ 74.39 for ChatGPT), approaching GPT-4's 89.95. On TransCoder (C++ to Python translation), it achieves 90.4\% accuracy (vs.\ 88.3\% for ChatGPT).

SelfEvolve represents an early but important form of self-evolution: the system improves its own output through feedback from its own execution environment, without external evaluation or human intervention. It is a direct precursor to later, more sophisticated self-evolution frameworks, establishing the principle that execution feedback is a viable training signal for code generation systems.

\subsection{A Unified View: Mapping to the Five Evolution Loops}
\label{sec:agent-unified}

The systems surveyed in this section can be organized along two axes: \textbf{what} evolves and \textbf{how} it evolves. We can also map each system to the Five Evolution Loops taxonomy introduced in Section~\ref{sec:taxonomy}, revealing which loop types are most prevalent in current agent self-evolution research.

\subsubsection{Mapping to the Five Loops}

\textbf{Specification-to-Execution Loop}: AutoML-Agent exemplifies this loop, translating natural language goals (``classify images of butterflies'') into complete ML pipelines. SelfEvolve also instantiates this loop, converting problem descriptions into executable code through self-generated knowledge and iterative debugging. ADAS's meta-agent can be viewed as a meta-level specification-to-execution system: the specification is ``design a good agent,'' and the execution is the generated agent code.

\textbf{Search Loop}: ADAS searches the space of agent architectures (Turing-complete Python programs using \texttt{LLMAgentBase}). DGM performs open-ended search through an archive of agent implementations. OpenEvolve and the broader evolutionary code systems (Section~\ref{sec:evolutionary-code}) search program spaces using LLM-driven variation operators.

\textbf{Evaluator Loop}: FunSearch's automated evaluators, Absolute Zero's code executor, and SelfEvolve's sandbox all provide automated evaluation that drives the evolution loop. The quality of self-evolution is fundamentally bounded by the quality of the evaluation signal: without reliable evaluators, selection pressure cannot be effectively applied.

\textbf{Reflection Loop}: Reflexion stores verbal feedback in a memory buffer, Agent Symbolic Learning propagates language gradients through a computational graph, and ADAS's dual-reflexion mechanism analyzes proposals for errors. Self-Refine's GENERATE $\to$ CRITIQUE $\to$ REFINE loop is the simplest instantiation of this pattern. The reflection loop is present in virtually all self-evolving agent systems, suggesting that self-analysis is a fundamental capability for autonomous improvement.

\textbf{Population Loop}: DGM maintains an open-ended archive of agents, AlphaEvolve uses MAP-Elites quality-diversity search, FunSearch employs an island model with periodic migration, and LLaMEA evolves populations of optimization algorithms. The population loop provides the diversity maintenance that prevents convergence to local optima, enabling open-ended exploration of the design space.

\textbf{Weight evolution} (Absolute Zero) modifies the underlying model parameters through self-play reinforcement learning. This is the only target that changes the model's internal representations, as opposed to its external behavior. It is also the most computationally expensive, requiring distributed training infrastructure.

\subsubsection{Evolution Mechanisms}

The systems also differ in their evolution mechanisms:

\textbf{Search-based} (ADAS, DGM): A meta-agent or evolutionary algorithm proposes candidate designs, which are evaluated and selected. This approach explores a broad space but is computationally expensive. ADAS uses a meta-agent (GPT-4o) to propose architectures; DGM uses an LLM to propose code modifications to archive members.

\textbf{Gradient-based} (Agent Symbolic Learning): Language-space gradients guide optimization through the agent's computational graph. This is more targeted than search but depends on the quality of language gradient computation, which in turn depends on the LLM backbone's capability.

\textbf{Self-play} (Absolute Zero): The agent generates its own training data and evaluation signal through a dual-role setup. This eliminates external dependencies but is limited to verifiable domains (currently, programming tasks with code executor verification).

\textbf{Reflexive} (Reflexion, Self-Refine): The agent reflects on its own failures and generates improvement guidance. This is the simplest mechanism but may not discover fundamentally novel strategies; it tends to refine existing approaches rather than invent new ones.

\subsubsection{Emerging Research Directions}

The analysis reveals several promising directions for future research:

\textbf{Combining evolution targets}: Current systems focus on a single evolution target (architecture, workflow, knowledge, memory, or weights). A more powerful approach would combine multiple targets---for example, evolving an agent's architecture while simultaneously optimizing its prompts and accumulating experiential memory. Agent Symbolic Learning's three-component optimization (prompts, tools, pipeline) points in this direction, but no system yet combines architecture evolution with weight evolution and memory accumulation.

\textbf{Transfer across evolution mechanisms}: Insights from one evolution mechanism could inform others. For example, the language-gradient computation in Agent Symbolic Learning could guide the proposals in DGM's archive evolution, providing more targeted mutations. Similarly, the self-play curriculum in Absolute Zero could generate training tasks that are specifically designed to improve an agent's weakest architectural components.

\textbf{Population-based agent evolution}: The rarity of population-based methods in agent self-evolution (only DGM among the systems surveyed) contrasts with their prevalence in evolutionary code systems. Applying MAP-Elites or island models to agent architecture search could enable more open-ended exploration of the agent design space, potentially discovering qualitatively different agent architectures that single-trajectory search would miss.

\textbf{Formal verification for self-modifying agents}: The safety challenge of self-modifying systems requires more rigorous approaches than engineering-level safeguards. Formal methods from programming language theory (type systems, contract verification, program logics) could provide stronger guarantees about the behavior of self-modifying agents, enabling safe deployment in high-stakes applications.

\subsubsection{The Self-Evolution Spectrum}

We can organize the surveyed systems along a ``self-evolution spectrum'' from narrow to broad:

\textbf{Narrow self-evolution} (Self-Refine, SelfEvolve): The system improves its outputs through iterative feedback, but the improvement mechanism is fixed and the scope of improvement is limited to the current task instance. No persistent learning occurs across tasks.

\textbf{Moderate self-evolution} (Reflexion, Agent Symbolic Learning): The system accumulates knowledge across episodes (Reflexion's memory buffer) or optimizes persistent components (Symbolic Learning's prompts, tools, pipeline). Improvement persists across tasks, but the system's fundamental architecture remains fixed.

\textbf{Broad self-evolution} (ADAS, DGM, G\"odel Agent): The system modifies its own architecture or codebase, potentially discovering fundamentally new designs. Improvement occurs at the structural level, not just the behavioral level, and the scope of possible improvements is open-ended.

\textbf{Complete self-evolution} (Absolute Zero): The system generates its own training data, evaluation signal, and improvement objectives. No external dependencies remain---the system is entirely self-contained and self-improving. This represents the theoretical endpoint of the self-evolution spectrum.

The spectrum is not merely a ranking of capability; it reflects a tradeoff between power and control. Narrow self-evolution is safe and predictable but limited in scope. Complete self-evolution is maximally powerful but raises the most serious safety and alignment concerns. The practical deployment of self-evolving agents will likely require finding a point on this spectrum that balances capability with controllability.

\subsection{Limitations and Open Challenges for Agent Self-Evolution}
\label{sec:agent-limitations}

Despite rapid progress, self-evolving agent systems face significant challenges that the current literature has not fully addressed:

\textbf{Evaluation reliability}: All systems rely on benchmark-based evaluation to guide evolution. However, benchmark improvement does not necessarily correlate with genuine capability gain. Agents may evolve to exploit benchmark-specific patterns (answer distribution biases, prompt format regularities) rather than developing general reasoning ability. DGM's SWE-bench improvement from 20\% to 50\% is impressive, but the generalizability of the evolved strategies to real-world software engineering tasks remains an open question.

\textbf{Stability of self-modification}: Self-modifying systems risk destabilization: a sequence of individually beneficial modifications may collectively degrade performance. G\"odel Agent's rollback mechanism addresses this locally, but there is no guarantee against gradual drift. DGM's archive-based approach is more robust (each modification is evaluated against the parent), but the computational cost grows with archive size.

\textbf{Scalability}: Current evaluations are limited to relatively narrow benchmarks. ADAS uses ARC, DROP, GPQA, MGSM, and MMLU; DGM uses SWE-bench and Polyglot. Whether these approaches scale to the complexity of real-world agent applications---multi-day workflows, large codebases, ambiguous objectives---is unclear.

\textbf{Safety and alignment}: Self-evolving agents that modify their own code raise fundamental safety questions. A system that can rewrite its own behavior is, by definition, harder to constrain. Current safety mechanisms (rollbacks, validation sets, objective constraints) are engineering-level mitigations, not formal guarantees. As agent self-evolution moves toward practical deployment, alignment between evolved behavior and human intent becomes increasingly critical.

\textbf{Theoretical foundations}: The field lacks formal frameworks for reasoning about self-evolving systems. Under what conditions does agent self-modification converge to improved behavior? What are the theoretical limits of open-ended agent evolution? These questions remain largely unaddressed, and the field currently relies on empirical evidence rather than principled design.

\textbf{Resource requirements}: All systems surveyed require significant compute: ADAS and DGM use GPT-4 class models for the meta agent; Absolute Zero requires dual-role RL training with distributed infrastructure; Agent Symbolic Learning needs multiple LLM calls per training step (forward + loss + backpropagation + update). Democratizing agent self-evolution requires more efficient methods---for example, distilled meta-agents that can propose architectures without requiring frontier-scale LLMs.

\textbf{Composability of evolution methods}: Current systems employ a single evolution mechanism (search, gradient, self-play, or reflexion). However, the most powerful self-evolving systems would likely combine multiple mechanisms. Imagine a system that uses architecture search (ADAS) to discover an initial agent design, language-gradient optimization (Symbolic Learning) to refine its prompts and tools, self-play (Absolute Zero) to continuously improve its reasoning capabilities, and population-based evolution (DGM) to maintain diversity across evolving agent lineages. The composability of these mechanisms---how they interact, whether they are compatible, and whether combining them yields more than the sum of their parts---is an important open question.

\textbf{The meta-evolution question}: A fundamental question lurking behind all agent self-evolution research is whether the process can be made fully recursive. Current systems have a fixed meta-level: ADAS's meta-agent is GPT-4o, which does not improve during the search. DGM's foundation model is Claude or GPT, which is used but not evolved. To achieve truly autonomous self-evolution, the meta-level itself must be subject to improvement---the system that designs agents must itself be improvable. This recursive requirement connects to Schmidhuber's original G\"odel Machine concept and represents the theoretical frontier of the field.

These limitations connect to the broader open problems discussed in Section~\ref{sec:open-problems}, particularly the evaluation bottleneck (Section~\ref{sec:evo-limitations}), the safety challenge, and the gap between benchmark performance and real-world utility. The transition from evolutionary code discovery (Section~\ref{sec:evolutionary-code}) to agent self-evolution represents a shift from optimizing the \emph{tools} that AI uses to optimizing the \emph{agents} that use them---a shift that amplifies both the potential and the risks of self-evolving AI.
